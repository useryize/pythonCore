## 📖 二、知识讲解

### 2.1 元组的创建与单元素元组的逗号陷阱

**一句话定义**：元组（`tuple`）是**有序、不可变、可重复**的序列容器；它和列表的接口几乎一样，但**一旦创建就不能改**。

**创建方式**：

```python
empty = ()                                # ✅ 空元组：必须有逗号，否则 () 只是空括号
empty2 = tuple()                          # ✅ 等价写法
single = (1,)                             # ✅ 单元素元组：必须带逗号
multi = (1, 2, 3)                         # ✅ 多元素元组
a = 1, 2                                  # ✅ 不写括号，右侧逗号让 a 成为元组
print(single, multi, a)
# 期望输出: (1,) (1, 2, 3) (1, 2)
```

⚠️ **头号陷阱：`(1)` 不是元组，是整数 1**：

```python
print(type((1)).__name__, type((1,)).__name__)
# 期望输出: int tuple

print(len((1,)))
# 期望输出: 1
```

**为什么 Python 要这么设计？** 在 C、Java 里 `(1)` 就是「加了个括号的整数 1」。如果 Python 把 `(1)` 也解释成元组，那所有从 C/Java 转过来的代码都会出错。所以 Python **必须保持这个兼容性**，于是用「逗号」作为「升级成元组」的显式信号——逗号在语法上是多余的，所以它不会破坏任何已有代码。

**⚠️ 函数返回时这个坑最隐蔽**：

```python
def f1():        # ❌ 忘了逗号，返回的是整数 5
    return 5

def f2():        # ✅ 返回单元素元组
    return (5,)

print(type(f1()).__name__, type(f2()).__name__)
# 期望输出: int tuple
```

这个 bug 很难发现，因为函数定义处看不出问题。调用方写 `a, b = f1()` 时会报 `TypeError: cannot unpack non-iterable int object`（整数不可迭代）——注意**不是** `ValueError`；而 `a, b = f2()` 报的是 `ValueError: not enough values to unpack`（元素不够）。**两种错误的含义完全不同**，排查时要区分。

**⚠️ 另一个容易混淆的点：逗号在不同位置的含义不同**

```python
a = 1, 2                                  # 赋值右侧的逗号 → a 是元组
# 但函数调用里的逗号是【参数分隔符】
def f(x, y):                              # 这里是两个参数，不是一个元组
    return x + y
print(f(1, 2))
# 期望输出: 3
```

> 💡 记住这个规律：**逗号在「赋值/返回」时造元组，在「调用」时是参数分隔**。判断方法：看逗号外面有没有括号把它包成元组。

### 2.2 不可变性：三个真正有价值的好处

**一句话定义**：元组创建后，其**元素的位置和数量都无法改变**——不能赋值、不能增、不能删。

```python
t = (1, 2, 3)
print(t.count(2), t.index(2), len(t), t[::-1])
# 期望输出: 1 1 3 (3, 2, 1)
```

⚠️ 任何修改尝试都会抛 `AttributeError` 或 `TypeError`：

```python
t = (1, 2, 3)
print(hasattr(t, 'append'))
# 期望输出: False
```

⚠️ 注意**切片返回新元组，不改原对象**（和列表一致）：

```python
t = (1, 2, 3)
_ = t[::-1]
print(t)
# 期望输出: (1, 2, 3)
```

**⭐ 但「不可变」真正的价值不是安全，而是下面三件事**：

**好处 1：可哈希 → 能当字典键和集合元素**

哈希表要求键**不能变**，否则你放进去之后哈希值对不上，就永远找不回来了。元组不可变，天然满足这个要求。

**好处 2：可安全共享 → 多个地方引用同一份，谁也改不坏**

```python
DEFAULT_CONFIG = ("utf-8", "r", 32)       # 一个全局默认配置

def read_config() -> tuple[str, str, int]:
    """多个调用方共享同一份配置，谁也改不坏它。"""
    return DEFAULT_CONFIG

print(read_config() is DEFAULT_CONFIG)
# 期望输出: True
```

如果这里用列表，任何一个调用方 `cfg = read_config(); cfg[0] = "gbk"` 都会**污染全局默认值**，影响其他所有模块。这是真实项目中非常常见的 bug。

**好处 3：可作默认参数 → 不会像列表那样被逐次污染**

```python
def add_item(item: str, bucket: tuple[str, ...] = ()) -> tuple[str, ...]:
    """默认元组不可变，每次调用都从【同一个起点】开始，不会累积。"""
    return bucket + (item,)

print(add_item("a"), add_item("b"))
# 期望输出: ('a',) ('b',)
```

对比列表版本（这是**真实 bug**）：

```python
def add_item_bad(item: str, bucket: list[str] = []) -> list[str]:
    """⚠️ 默认列表在【函数定义时】只创建一次，被所有调用共享！"""
    bucket.append(item)
    return bucket

first = add_item_bad("a")                    # 先保存「结果」
second = add_item_bad("b")
print(first, second)
# 期望输出: ['a', 'b'] ['a', 'b']
print(f"两次返回的是同一个对象: {first is second}")
```

⚠️ **为什么这是 bug（注意上面输出的恐怖之处）**：默认参数值在**函数定义时求值一次**，之后不管调用多少次，都用**同一个列表对象**。

所以 `first` 这个「第一次调用的结果」**也会被第二次调用改掉**——`first` 和 `second` 是同一个对象，都变成了 `['a', 'b']`。这意味着你**即使把返回值保存下来了，也躲不过污染**。而元组版本每次都从 `()` 重新开始，第二次是 `('b',)`，完全干净。

> 💡 这条在 L13-L17（函数专题）还会深入讲。**记住结论就够了：默认参数用元组或 `None`，永远别用列表或字典。**

### 2.3 元组与列表的取舍（含一个反直觉的实测结论）

很多教程说「元组比列表省内存」。这个说法**只对了一半**，实测一下你会发现更有意思的真相。

**先看实测结果**：

```python
import sys

BENCH = 200_000
tup = tuple(range(BENCH))
exact = list(tup)                          # 用 list(tuple) 构造：已知长度

built = []                                 # 逐个 append：长度未知
for i in range(BENCH):
    built.append(i)

print(f"元组            : {sys.getsizeof(tup):,}")
print(f"列表(精确尺寸)  : {sys.getsizeof(exact):,}  差 {sys.getsizeof(exact) - sys.getsizeof(tup)} 字节")
print(f"列表(append长起): {sys.getsizeof(built):,}  差 {sys.getsizeof(built) - sys.getsizeof(tup):,} 字节")
```

实测输出：

```text
元组            : 1,600,040
列表(精确尺寸)  : 1,600,056  差 16 字节
列表(append长起): 1,624,056  差 24,016 字节
```

**⭐ 这个结果的真正含义**（比「元组更省内存」精确得多）：

1. **元组长度固定，底层内存永远「刚刚好」**，一点不浪费。
2. **列表用 `list(range(...))` 这种「已知长度」的构造时，也是精确尺寸**，此时和元组只差 16 字节（对象头的差异），几乎一样大。
3. **只有用 `append` 一点点长起来的列表，才会预留约 12% 的空闲空间**（L08 讲过的超额分配），这才是大列表内存差的主要来源。

**所以「元组更省内存」的真正收益在「小而多的对象」上**：

```python
print(sys.getsizeof((1,) * 1), sys.getsizeof([1] * 1))
print(sys.getsizeof(tuple(range(10))), sys.getsizeof(list(range(10))))
# 期望输出: 48 64
# 期望输出: 120 136
```

如果你要创建**十万个**小元组而不是十万个 10 元素列表，每省 16 字节就是省 1.6 MB——这才有意义。

**创建速度对比**：

```python
import time

t0 = time.perf_counter()
_ = [tuple(range(200_000)) for _ in range(20)]
t1 = time.perf_counter()
_ = [list(range(200_000)) for _ in range(20)]
t2 = time.perf_counter()

print(f"tuple: {(t1 - t0) * 1000:.1f} ms, list: {(t2 - t1) * 1000:.1f} ms")
```

实测约 `53 ms` vs `87 ms`。元组更快，因为构造时**不用考虑「以后还要不要加元素」的扩容问题**。

**⭐ 取舍决策表**：

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 数据确定不会改 | **元组** | 可哈希 + 更小 + 更快 |
| 要当字典键 / 集合元素 | **元组** | 列表不可哈希 |
| 作函数默认参数 | **元组** | 列表会被逐次污染 |
| 需要频繁增删改 | **列表** | 元组没有 `append` |
| 大量小对象 | **元组** | 每个省几十字节 |
| 一个大列表且长度已知 | 差别很小 | 两者内存几乎一样 |

> 💡 **实用默认策略**：**默认用元组，只有确实需要增删时才用列表**。这个习惯能同时获得性能和哈希性两个好处。

### 2.4 元组与列表互转，以及 zip 返回的元组

```python
lst = [1, 2, 3]
tpl = tuple(lst)                          # list → tuple
back = list(tpl)                          # tuple → list
print(tpl, back, type(tpl).__name__, type(back).__name__)
# 期望输出: (1, 2, 3) [1, 2, 3] tuple list
```

⚠️ **注意 `tuple()` 是浅拷贝**（和 L08 的 `list()` 一样）：里面的列表元素仍是共享的。

**⭐ `zip()` 返回的正是元组**（L07 讲过 `zip`，现在说清它的产出类型）：

```python
pairs = list(zip(["a", "b"], [1, 2]))
print(pairs, type(pairs[0]).__name__)
# 期望输出: [('a', 1), ('b', 2)] tuple
```

**为什么 `zip` 产出元组而不是列表**：`zip` 的语义是「把第 i 个元素**配成一对**」，而「一对」天然是固定的、不可变的组合。用元组表达这个语义既省事又准确——你不会想在遍历 zip 结果时往那一对里 `append` 什么东西。

**实战：用元组当复合键**：

```python
locations = {("北京", 39.9): "BJ", ("上海", 31.2): "SH"}
print(locations[("上海", 31.2)])
# 期望输出: SH
```

`(城市, 纬度)` 是一个**不可变的复合标识**，正好符合哈希键的要求。

### 2.5 元组作为字典键：可哈希性的判定规则

**一句话定义**：**元组可哈希 ⟺ 它的每一个元素都可哈希**。

```python
print(hash((1, 2, 3)) is not None)
# 期望输出: True
print(hash(([1], 2)))
# 期望输出: 抛 TypeError: unhashable type: 'list'
```

**完整的判定表**：

| 元组 | 可哈希？ | 原因 |
| --- | --- | --- |
| `(1, 2, 3)` | ✅ | 数字不可变 |
| `('a', 'b')` | ✅ | 字符串不可变 |
| `((1, 2), (3, 4))` | ✅ | 嵌套的元组也可哈希（递归成立） |
| `(True, None)` | ✅ | 布尔和 `None` 都不可变 |
| `([1], 2)` | ❌ | 含列表 → 列表不可哈希 |
| `({'k': 1},)` | ❌ | 含字典 → 字典不可哈希 |

**为什么这个规则是这样**：哈希值的计算是「把每个元素的哈希值按固定公式混合」。如果某个元素不可哈希，混合公式就无从算起，所以整个元组也不可哈希。

**集合自动去重**：

```python
unvisited = {(0, 0), (1, 1), (2, 2), (0, 0)}
print(sorted(unvisited))
# 期望输出: [(0, 0), (1, 1), (2, 2)]
```

`(0, 0)` 出现两次，集合只保留一个——这就是「可哈希 + 不可变」的组合威力：**哈希表靠哈希值定位，哈希值要求键不变**。

### 2.6 函数返回多值与四种解包语法

**「返回多值」的真相**：Python 函数**只能返回一个对象**。所谓「返回多个值」，实际返回的是**一个元组**，调用方再解包。

```python
def get_min_max(data: list[int]) -> tuple[int, int]:
    """返回最小值和最大值——本质是返回一个元组。"""
    return min(data), max(data)

result = get_min_max([5, 2, 9, 1, 7])
print(result, type(result).__name__)
# 期望输出: (1, 9) tuple
```

**四种解包写法**：

```python
lo, hi = (1, 9)                            # 1. 位置解包：按顺序一一对应
lo, _ = (1, 9)                             # 2. 下划线占位不关心的位置
first, *rest = [1, 2, 3, 4]                # 3. 星号收集「剩下的所有」
a, (b, c) = 1, (2, 3)                      # 4. 嵌套解包：按结构展开
print(lo, hi, first, rest, a, b, c)
# 期望输出: 1 9 1 [2, 3, 4] 1 2 3
```

⚠️ **解包数量不匹配会报错**：

```python
try:
    x, y, z = (1, 2)
except ValueError as exc:
    print(exc)
# 期望输出: not enough values to unpack (expected 3, got 2)
```

**星号丢弃剩余值**（Python 3.0+）：

```python
head, *_ = (1, 9)
print(head)
# 期望输出: 1
```

> 💡 **解包是 Python 最有「多返回值」味道的语法**，但要注意：**解包要求两边结构严格对应**。如果返回的数据结构会变，用索引或 `dict.get` 更稳妥。

### 2.7 命名元组：让不可变从负担变成优势

**一句话定义**：`collections.namedtuple` 创建一个**元组的子类**——它保留了元组的所有优点（不可变、可哈希、省内存），同时**给每个位置起了名字**。

```python
from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])
p = Point(3, 4)
print(p, p.x, p.y, p[0], p[1])
# 期望输出: Point(x=3, y=4) 3 4 3 4
```

注意它的 `repr` 是 `Point(x=3, y=4)`——**比裸元组可读太多了**。

**⭐ 为什么它比普通元组好**：

```python
plain = (3, 4)
print(f"普通元组: {plain}")
# 期望输出: 普通元组: (3, 4)
```

`(3, 4)` 你要靠注释或文档才知道 `3` 是 x 还是 y。而 `Point(x=3, y=4)` 一眼就能读懂。

**常用辅助方法**：

```python
print(p._asdict())                  # 转成字典
print(p._replace(x=10))             # 基于它造新对象
print(p._fields)                    # 字段名元组
# 期望输出: {'x': 3, 'y': 4}
# 期望输出: Point(x=10, y=4)
# 期望输出: ('x', 'y')
```

⚠️ **命名元组也是不可变的**：

```python
try:
    p.x = 99
except AttributeError as exc:
    print(exc)
# 期望输出: can't set attribute
```

`_replace` 返回的是**新对象**，原对象不变（和 `copy.deepcopy` 的思路一样，不原地修改）：

```python
print(p)
# 期望输出: Point(x=3, y=4)
```

**它仍然是元组**，所以按值比较、可以当字典键：

```python
print(Point(1, 2) == (1, 2))
# 期望输出: True
print({Point(0, 0): "原点"}[Point(0, 0)])
# 期望输出: 原点
```

**⚠️ 但命名元组不能加字段**——字段在**定义时**就固定了：

```python
P2 = namedtuple("P2", ["x", "y"])
print(P2._fields)
# 期望输出: ('x', 'y')
```

需要加字段时，用 `_replace` 造一个新类型，或者在阶段四学 `dataclasses`（它功能更强：能写默认值、能加方法）。

### 2.8 常见坑

**⚠️ 坑 1：单元素元组忘逗号**（本课头号陷阱，见 2.1）

```python
bad = (42)
good = (42,)
print(type(bad).__name__, type(good).__name__, len(good))
# 期望输出: int tuple 1
```

**⚠️⚠️ 坑 2：元组「不可变」但元素可能可变**

这是最容易误解的点。准确的说法是：**元组不可变，指的是「元素的位置和数量不能改」，不是「元素的内容不能改」。**

```python
t = ([1, 2], [3, 4])
print(t)
# 期望输出: ([1, 2], [3, 4])
```

元组本身换不了元素：

```python
try:
    t[0] = [9]
except TypeError as exc:
    print(exc)
# 期望输出: 'tuple' object does not support item assignment
```

⚠️ 但**能改元素的内容**：

```python
t[0].append(99)
print(t)
# 期望输出: ([1, 2, 99], [3, 4])
```

**为什么「元组不可变」还算数**：因为字典和集合**只关心「键本身不会变」**。`([1,2],[3,4])` 这样的元组**不可哈希**，所以根本当不了字典键——Python 用「不可哈希」这个机制，把这类「内容可能变」的元组**排除在哈希键之外**了。

> 💡 **准确表述**：元组的不可变性是**浅层**的。它保证「元素的引用不能被替换」，而不是「元素指向的内容不能变」。二者结合，才让哈希键这件事变得安全。

**⚠️ 坑 3：默认参数用列表**（见 2.2 好处 3）

**⚠️ 坑 4：以为命名元组可以随便改**

```python
Point = namedtuple("Point", ["x", "y"])
p = Point(1, 2)
print(hasattr(p, "x"), hasattr(p, "z"))
# 期望输出: True False
```

`z` 字段不存在，因为它在定义时就没被声明。

### 2.9 实战：用命名元组表示一个坐标点

```python
from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])


def distance_squared(a: Point, b: Point) -> float:
    """计算两点距离的平方（不开根号，够用且更快）。

    ⚠️ 注意：`(3-0)**2 + (4-0)**2` 的结果是【整数】25，不是 25.0。
       标注 float 却不转 float 是个常见疏漏，所以这里显式转换。
    """
    return float((a.x - b.x) ** 2 + (a.y - b.y) ** 2)


# 用命名元组当字典键，天然去重
points = [Point(0, 0), Point(3, 4), Point(0, 0), Point(3, 4)]
unique: dict[Point, int] = {}
for i, pt in enumerate(points):
    unique.setdefault(pt, i)             # 保留第一次出现的下标

print(f"去重后 {len(unique)} 个点: {sorted(unique)}")
# 期望输出: 去重后 2 个点: [Point(x=0, y=0), Point(x=3, y=4)]

origin = Point(0, 0)
print(f"origin 到 Point(3,4) 的距离平方 = {distance_squared(origin, Point(3, 4))}")
# 期望输出: origin 到 Point(3,4) 的距离平方 = 25.0
```

**这个例子的价值**：如果用普通元组 `(0, 0)`，你就得靠注释解释每个数字的含义；用 `Point(x=0, y=0)`，代码**自己说明了自己**，而且天然可哈希、能去重、能当字典键。

## 📝 六、本课小结

- **`(1)` 是整数而 `(1,)` 才是元组**，原因是**语言兼容性**——C/Java 里 `(1)` 就是整数 1，Python 不能改变这个含义，于是用「逗号」作为升级成元组的显式信号。
- **逗号的含义看位置**：赋值/返回时造元组，函数调用时是**参数分隔符**。这也导致 `assert (1, 2) == (1, 2)` 会被解析成 `assert (cond, "消息")`，必须写 `assert ((1, 2)) == (1, 2)`。
- **不可变性的真正价值不是「安全」，而是三个具体好处**：可哈希（能当字典键）、可安全共享（多处引用不会被改坏，避免污染全局默认值）、可作默认参数（不会逐次累积）。
- **默认参数用列表是真实 bug**：默认参数值在**函数定义时求值一次**，之后所有调用共享同一个列表对象，所以第二次调用会看到第一次留下的数据。用元组或 `None` 修复。
- **「元组更省内存」这个说法只对了一半**。实测显示：`list(range(...))` 这种已知长度的构造是**精确尺寸**，和元组只差 16 字节；只有逐个 `append` 长起来的列表才会预留约 12% 空间。真正的收益在**小而多的对象**上。
- **元组可哈希 ⟺ 每一个元素都可哈希**，因为哈希值要按固定公式混合各元素的哈希值。`(1,2,3)` ✅、`((1,2),(3,4))` ✅、`([1],2)` ❌。
- **`zip()` 每次产出的元素是元组**，因为「配成一对」是固定组合，不该被修改——这正是元组表达这个语义的恰当之处。
- **「函数返回多值」实际返回的是一个元组**，调用方用四种语法解包：位置解包、下划线占位、星号收集、星号丢弃，外加嵌套解包。注意解包**要求两边结构严格对应**，否则 `ValueError`。
- **`namedtuple` 是元组的子类**，兼得不可变 + 可哈希 + 省内存，同时**给每个位置起了名字**，`repr` 是 `Point(x=3, y=4)` 而非 `(3, 4)`。用 `_replace` 返回新对象而非原地修改。
- **元组的不可变是「浅层」的**：元素的**引用**不能被替换，但元素**指向的内容**可以变（`t[0] = x` 失败，`t[0].append()` 成功）。Python 用「含可变元素的元组不可哈希」这个机制，把这类对象排除在哈希键之外——这才是安全性的真正保证。
- **实用默认策略**：默认用元组，只有确实需要增删时才用列表。这个习惯同时获得性能和哈希性两个好处。

> **一句话总结**：元组是「**为了不可变而设计的列表**」——它的价值不在于「不能改」这件事本身，而在于不可变**解锁了哈希键、安全共享、默认参数**这三项列表拿不到的能力。选对容器，本质上是在回答「**这份数据会被修改吗？会不会被当成键来查？**」这两个问题。

**关键点 1：哈希缓存元组子类（第 9 题的核心）**

思路：`namedtuple` 的 `__hash__` 每次调用都要**遍历所有元素重算**。如果元素多且被反复哈希（比如反复放进 set），缓存结果能省下大量计算。

```python
from collections import namedtuple


class HashedPoint(namedtuple("HashedPoint", ["x", "y"])):
    """带哈希缓存的命名元组：第一次算完就存起来，后续直接复用。

    ⭐ 适用场景：一个对象会被反复放进 set 或当字典键查询（哈希被调用很多次）。
    ⚠️ 不适用场景：对象【可哈希性会变】——但元组不可变，所以这个前提天然成立。
    """

    _hash_cache: int | None = None      # ⚠️ 不能写成可变默认值，这里只是声明注解

    def __hash__(self) -> int:
        """第一次调用时真的计算，之后直接返回缓存值。"""
        if self._hash_cache is None:
            # ⚠️ 这里必须绕过缓存，否则会无限递归
            object.__setattr__(self, "_hash_cache", tuple.__hash__(self))
        return self._hash_cache


def bench_hash_cache() -> None:
    """实测哈希缓存的加速比。"""
    import time

    n = 10_000
    plain = [namedtuple("P", "x y")(i, i) for i in range(n)]
    cached = [HashedPoint(i, i) for i in range(n)]

    t0 = time.perf_counter()
    for p in plain:
        hash(p)                          # 每次都重算
    t1 = time.perf_counter()
    for p in cached:
        hash(p)                          # 第一次算，后面都读缓存
    t2 = time.perf_counter()

    print(f"namedtuple  : {(t1 - t0) * 1000:.2f} ms")
    print(f"哈希缓存版  : {(t2 - t1) * 1000:.2f} ms")
    print(f"加速比      : {(t1 - t0) / (t2 - t1):.2f} 倍")
```

```python
"""基础题第 3 题：元组与列表的实测对比。"""

import sys
import time

SIZES = (10, 1_000, 200_000)


def build_three_ways(n: int) -> tuple[tuple, list, list]:
    """返回 (元组, 精确尺寸列表, append 构建的列表)。"""
    t = tuple(range(n))
    exact = list(range(n))                  # 已知长度 → 精确尺寸
    built: list[int] = []                   # 长度未知 → 触发超额分配
    for i in range(n):
        built.append(i)
    return t, exact, built


def memory_table() -> None:
    """3 种规模 × 3 种构造的内存实测。"""
    print("【内存实测】")
    print(f"  {'规模':>8} {'元组':>12} {'列表(精确)':>14} {'差':>10} "
          f"{'列表(append)':>14} {'差':>10}")
    for n in SIZES:
        t, exact, built = build_three_ways(n)
        ts, es, bs = sys.getsizeof(t), sys.getsizeof(exact), sys.getsizeof(built)
        print(f"  {n:>8} {ts:>12,} {es:>14,} {es - ts:>10,} {bs:>14,} {bs - ts:>10,}")
    print("\n  ⭐ 关键结论：")
    print("    · 精确尺寸构造的列表（元组→列表 / list(range)）只比元组多 16 字节（对象头）")
    print("    · 只有逐个 append 长起来的列表才会超额分配约 12%")
    print("    · 所以「元组更省内存」的真正收益在【小而多的对象】上，不是大列表上")


def speed_benchmark() -> None:
    """创建速度对比。"""
    print("\n【创建速度】")
    n, times = 200_000, 20
    t0 = time.perf_counter()
    _ = [tuple(range(n)) for _ in range(times)]
    t1 = time.perf_counter()
    _ = [list(range(n)) for _ in range(times)]
    t2 = time.perf_counter()
    print(f"  创建 {times} 个 {n:,} 元素的容器：")
    print(f"    元组: {(t1 - t0) * 1000:.1f} ms")
    print(f"    列表: {(t2 - t1) * 1000:.1f} ms")
    print(f"    元组快 {(t2 - t1) / (t1 - t0):.2f} 倍 —— 不用考虑后续扩容")


def ten_thousand_objects() -> None:
    """10 万个小容器：这才是元组的真正收益场景。"""
    print("\n【10 万个小容器的总内存差】")
    count = 100_000
    tuples = [tuple(range(10)) for _ in range(count)]
    lists = [list(range(10)) for _ in range(count)]
    t_total = sum(sys.getsizeof(x) for x in tuples)
    l_total = sum(sys.getsizeof(x) for x in lists)
    print(f"  10 万个 10 元素元组: {t_total / 1024 / 1024:.2f} MB")
    print(f"  10 万个 10 元素列表: {l_total / 1024 / 1024:.2f} MB")
    print(f"  差 {(l_total - t_total) / 1024 / 1024:.2f} MB  ← 这才是有意义的节省")


def slice_speed() -> None:
    """切片速度对比。"""
    print("\n【切片速度】")
    big_t = tuple(range(100_000))
    big_l = list(range(100_000))
    t0 = time.perf_counter()
    for _ in range(1_000):
        _ = big_t[::-1]
    t1 = time.perf_counter()
    for _ in range(1_000):
        _ = big_l[::-1]
    t2 = time.perf_counter()
    print(f"  元组切片 1000 次: {(t1 - t0) * 1000:.1f} ms")
    print(f"  列表切片 1000 次: {(t2 - t1) * 1000:.1f} ms")
    print("  两者接近：切片都要新建对象并逐个拷贝元素")
```

**第 4 题「命名元组实战」的关键设计**：

```python
from collections import namedtuple
import json

Point = namedtuple("Point", ["x", "y"])
Rect = namedtuple("Rect", ["x", "y", "w", "h"])
Person = namedtuple("Person", ["name", "age", "email"])


def distance(a: Point, b: Point) -> float:
    """两点欧氏距离。用 a.x 而不是 a[0]——这就是可读性的价值。"""
    return ((a.x - b.x) ** 2 + (a.y - b.y) ** 2) ** 0.5


def contains(rect: Rect, pt: Point) -> bool:
    """点是否在矩形内（不含边界）。"""
    return (rect.x <= pt.x < rect.x + rect.w
            and rect.y <= pt.y < rect.y + rect.h)


def intersects(r1: Rect, r2: Rect) -> bool:
    """两个矩形是否相交（AABB 相交判定）。"""
    return not (r1.x + r1.w <= r2.x or r2.x + r2.w <= r1.x
                or r1.y + r1.h <= r2.y or r2.y + r2.h <= r1.y)


def to_json(pt: Point) -> str:
    """_asdict() 转字典 → json。注意这是【序列化方向】。"""
    return json.dumps(pt._asdict(), ensure_ascii=False)


def from_json(s: str) -> Point:
    """**dict 还原。用 * 解包成位置参数——这是命名元组的标准还原方式。"""
    return Point(**json.loads(s))


def person_str(p: Person) -> str:
    """友好输出。不能改类，就用模块级函数（namedtuple 的 repr 不够友好）。"""
    return f"{p.name}（{p.age}岁，{p.email}）"


class RecordStore:
    """⭐ 验证命名元组能直接当字典键——这是元组哈希能力的直接体现。"""

    def __init__(self) -> None:
        self._data: dict[str, dict] = {}

    def add(self, kind: str, record: tuple) -> None:
        """kind 作为分类，record 直接当字典键（不需转字符串）。"""
        self._data.setdefault(kind, {})[record] = True

    def count(self, kind: str) -> int:
        return len(self._data.get(kind, {}))


if __name__ == "__main__":
    store = RecordStore()
    store.add("point", Point(0, 0))
    store.add("point", Point(3, 4))
    store.add("point", Point(0, 0))          # 重复 → 自动覆盖
    print(f"存入 3 个坐标，去重后 {store.count('point')} 个   "
          f"← 证明命名元组按值哈希去重")

    print(to_json(Point(3, 4)))
    print(from_json(to_json(Point(3, 4))))
    print(person_str(Person("张三", 20, "z@x.com")))
```

**第 4 题第 7 条要求的「对比实验」结论**：把 `Point` 换成裸元组后，`distance` 要写成 `((a[0]-b[0])**2 + (a[1]-b[1])**2)**0.5`——**四个魔数下标**，读代码的人必须回头查文档才知道哪个是 x 哪个是 y。这就是命名元组存在的理由。

```python
# 复合键实战
data: dict[tuple[str, int], float] = {}


def add(city: str, year: int, value: float) -> None:
    """(城市, 年份) 作复合键，天然支持多维度查询。"""
    data[(city, year)] = value


def query(city: str, year: int) -> float | None:
    return data.get((city, year))


add("北京", 2023, 1.5)
add("北京", 2024, 2.5)
add("上海", 2024, 3.5)
print(query("北京", 2024))                   # 2.5  O(1)
print(sorted(data))                        # 所有键，字典序
```

**为什么复合键很实用**：`data[("北京", 2024)]` 一次哈希查询就定位了「城市+年份」这个二维坐标。如果用嵌套字典 `data["北京"][2024]`，需要**两次**查询，而且外层不存在时会 `KeyError`。复合键把它压成了一次原子查询。

> 元组最大的价值是「能当键」。那么**键值映射**该用什么结构？答案是字典。
