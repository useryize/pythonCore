# 作业 01：环境与工程

## 作业说明

这份作业练的是「Python 工程的地基能力」。

很多人写 Python 写了一两年，仍然说不清三件事：我的代码到底跑在哪个解释器上、`sys.path` 里到底装了些什么、为什么 `print("中文")` 正常而 `print("🚀")` 直接崩。文档里 `01_env/` 下的三个配套文件——`01_venv_demo.py`、`02_path_and_encoding.py`、`03_script_vs_module.py`——演示的恰恰都是这类「平时用不上、出事时排查不了」的知识：解释器与虚拟环境检测、`sys.path` 搜索路径、跨平台路径常量、编码三要素、换行符归一化、`__name__` 守卫、导入缓存、`__package__` 与相对导入、动态导入。

它们看起来不像「知识点」，更像「环境知识」。但真实工程里 80% 的「诡异报错」——ModuleNotFoundError、UnicodeEncodeError、命令行直接跑没事被导入就出事、中文路径找不到文件——根因都在这一层。

做完这份作业，你应当能独立完成：

- 给自己的运行环境出一份可复核的「体检报告」，而不是凭感觉判断
- 在中文 Windows 环境下写出不会因编码崩掉的脚本，并能用字节级证据证明读写一致
- 用面向对象的路径 API 处理路径，避开字符串拼接的各种坑
- 解释清楚 `if __name__ == "__main__":` 为什么是「约定」而不是「语法」，以及它什么时候可以不写
- 面对「同一个文件直接运行和被导入表现不一样」这类问题，知道该从哪里下手查

本作业**不考察**你记住多少 API 名称，**只考察**你能不能用观测手段得出结论。

### 第 1 题：给运行环境出一份体检报告 ⭐☆☆

**题目描述**

新建 `q01_env_report.py`，输出一份分 5 段的运行环境体检报告。

关键约束（这是本题真正的考点）：

1. **判断「是否在虚拟环境中」，必须比较 `sys.prefix` 与 `sys.base_prefix`**，不能读环境变量 `VIRTUAL_ENV` 来下结论——环境变量可以被人为设置或删除，它不是证据。

### 第 2 题：跨平台路径工具箱 ⭐☆☆

**题目描述**

新建 `q02_path_toolkit.py`，实现一组路径工具函数。**要求全部基于 `pathlib.Path`，禁止使用字符串拼接或 `os.path.join` 完成路径拼接**。

需要实现的函数：

| 函数 | 职责 |
|---|---|
| `describe(path)` | 返回一个描述对象，包含：是否存在的绝对路径、父目录、文件名（不含后缀）、后缀（含点）、是否为目录、路径是否在当前盘符下 |
| `join_under(base, *parts)` | 在 `base` 之下安全拼接多段路径，并对每一段做安全检查 |
| `scan_tree(root, max_depth)` | 遍历目录树，统计文件数/目录数/按后缀分组的文件数，遇到超过 `max_depth` 的层级就停止深入 |
| `rename_suffix(path, old, new)` | 批量把目录下某后缀的文件换成新后缀，返回成功改名的文件名列表 |

安全要求：`join_under` 遇到「包含盘符」「以分隔符开头」「包含 `..`」这三类危险片段时，必须拒绝并给出明确原因，不能静默通过。

**输入/输出示例**

```
$ python q02_path_toolkit.py
演示目录：D:/tmp/演示目录/子目录
  存在      : True
  父目录    : D:\tmp\演示目录
  文件名    : 报告
  后缀      : .txt
  是目录    : False
危险片段检测：
  ('C:', 'Windows')   -> 拒绝：包含盘符
  ('/etc',)           -> 拒绝：以分隔符开头，会跳出 base
  ('..', '..')        -> 拒绝：包含上级目录跳转
  ('子目录',)         -> 接受
目录扫描（深度上限 2）：
  文件 5 / 目录 3
  按后缀: {.txt: 3, '.md': 1, '.log': 1}
后缀替换 .txt -> .md，成功 3 个：
  ['报告.md', '日志.md', '说明.md']
```

**验收标准**

- [ ] 所有路径拼接均由 `Path` 的 `/` 运算符完成，代码中不出现 `"\\" +` 或 `+ "\\"` 之类的拼接
- [ ] `scan_tree` 在遇到权限不足的目录时不会整体崩溃，而是跳过并在结果中体现
- [ ] `join_under` 的拒绝规则对 Windows 与 POSIX 两种分隔符都生效（代码需在 Linux/macOS 上也能正确拒绝）
- [ ] `rename_suffix` 遇到重名冲突时有明确策略（覆盖 / 跳过 / 报错），且该策略在文档字符串中写明
- [ ] 所有输出含中文，且在 GBK 控制台下执行不报编码错误

**涉及知识点**

`pathlib.Path`、`/` 运算符`、`mkdir / iterdir / with_name / rglob`、`os.sep 与 os.pathsep`、`stem / suffix / name / parent`、`sys.stdout 编码`

### 第 3 题：编码三要素实验与中文读写校验 ⭐⭐☆

**题目描述**

新建 `q03_encoding_lab.py`，把「编码」这件事彻底搞明白。你要写一个实验脚本，分 6 段输出，每段都要有**可复核的实验数据**，不能只打印结论。

要输出的 6 段内容：

1. **源码编码**：打印本文件自身的编码声明、`sys.getdefaultencoding()`、`__file__` 所在路径。
2. **标准输出编码**：打印 `sys.stdout.encoding` 与 `sys.stdout.errors`，并在**同一条语句里**打印一个中文串和一个 emoji，记录哪一步先崩。
3. **文件 I/O 默认编码**：用 `locale.getpreferredencoding()` 与 `open()` 不指定 encoding 时的实际编码做对照。
4. **UTF-8 往返校验**：往临时目录写一个含中英文与 emoji 的文本文件，用二进制模式读回原始字节，再用 UTF-8 解码，逐字节比对是否与写入内容一致。
5. **显式指定 encoding 的必要性**：写同一个文件两次，一次 `encoding="utf-8"`，一次「依赖平台默认」，然后用二进制模式读出两者的字节序列做 hex 对比。
6. **控制台兜底策略**：在 emoji 打印会崩的前提下，给出一个能正常输出 emoji 的方案并验证它有效。

**关键约束**：第 4、5 段的校验**必须基于字节**，不能基于「读回来看起来一样」。中文编码问题的隐蔽性正来自于「看起来一样」。

**输入/输出示例**

```
[2] 标准输出编码
    sys.stdout.encoding = gbk
    sys.stdout.errors   = strict
    打印中文 "你好，世界"  -> 成功
    打印 emoji "🚀"       -> 失败，异常类型 = UnicodeEncodeError
[4] UTF-8 往返校验
    写入文本：你好，world 🚀
    写入字节数：17
    读回字节数：17
    字节完全一致：True
    字节 hex 前缀：e4bda0e5a5bdef
[5] 显式 encoding 的必要性
    utf-8 版本 头 16 字节：e4bda0e5a5bdefbc8ce4b896
    默认版本 头 16 字节：4f60e4bda0e5a5bd
    两者字节一致：False
```

**验收标准**

- [ ] 第 2 段中 emoji 的失败是真实抛出的异常（可用异常捕获记录异常类型），不是靠 `isprintable()` 之类的方式预判
- [ ] 第 4 段的「字节一致」判定比较的是原始字节序列，长度与内容都要参与比较
- [ ] 第 5 段能证明「不写 encoding」与「写 encoding="utf-8"」在中文 Windows 上产生不同字节
- [ ] 第 6 段的方案在 GBK 控制台下验证通过，且方案本身不依赖修改系统区域设置
- [ ] 整个脚本用 `python q03_encoding_lab.py` 直接运行即可，不依赖任何 IDE 或启动参数

**涉及知识点**

`编码三要素（源码/声明/IO）`、`locale.getpreferredencoding`、`sys.stdout.encoding 与 errors`、`str.encode / bytes.decode`、`open(..., encoding=...)`、`临时目录 tempfile`、`bytes 与 hex 对比`、`errors= 容错策略`

### 第 4 题：文本规范化工具（换行符 + 编解码容错）⭐⭐⭐

**题目描述**

新建 `q04_text_normalizer.py`，实现一个「脏文本清洗器」，用来处理从 Windows / Linux / 老旧系统各处采集来的文本。

需要实现 4 个函数：

| 函数 | 职责 |
|---|---|
| `normalize_newlines(text, target)` | 把文本中的 `\r\n`、`\r` 统一成 `target` 指定的换行符 |
| `read_text_auto(path)` | 读文件，**自动侦测**原文件的换行风格并归一化；返回 `(文本, 侦测到的原始风格)` |
| `decode_bytes(data, policy)` | 对一段字节做解码，`policy` 取 `strict` / `ignore` / `replace` / `surrogateescape` 之一 |
| `decode_report(data, policy)` | 在 `decode_bytes` 基础上，额外报告：原始字节数、解码后字符数、丢失字节数、替换字符位置列表 |

**关键约束**：

1. `read_text_auto` 的换行风格侦测**必须在二进制模式下完成**。用文本模式读会先被 Python 的通用换行翻译（universal newlines）改写，你就永远看不到原始风格了——这正是本题最有价值的一个坑。
2. `decode_bytes` 的 4 种 `policy` 必须真实产生不同的结果，并能证明：`strict` 在遇到非法字节时抛异常而不是静默丢数据。
3. `decode_report` 的「丢失字节数」要能区分「被忽略的字节」和「被替换成一个 U+FFFD 的字节」两种不同情况。

**输入/输出示例**

```
$ python q04_text_normalizer.py
[1] 换行归一化
    输入 repr: 'A\r\nB\rC\nD'
    归一为 \n : 'A\nB\nC\nD'
    归一为 \r\n: 'A\r\nB\r\nC\r\nD'
[2] 换行风格侦测（二进制模式）
    文件 head.hex = 410d0a420d0a43
    侦测到的风格   = CRLF   （CRLF 2 次 / LF 0 次 / CR 0 次）
[3] 编解码容错
    原始 bytes : b'\xe4\xbd\xa0\xe5\xa5\xbd\xff'
    strict     : 抛出 UnicodeDecodeError（不能静默丢数据）
    ignore     : '你好'            丢失字节 1 个
    replace    : '你好�'          替换 1 处，位置 [3]
    surrogateescape: '你好\udcff'  可通过 encode(errors='surrogateescape') 原样还原
[4] 往返还原校验
    decode(surrogateescape) -> encode(surrogateescape) == 原始 bytes : True
```

**验收标准**

- [ ] `normalize_newlines` 对 `\r`、`\n`、`\r\n` 三种输入混合的情况处理正确，且不产生 `\r\r\n` 这类畸形结果
- [ ] `read_text_auto` 在二进制模式下完成风格侦测，代码中不存在先文本读取再推断风格的写法
- [ ] `strict` 策略下非法字节触发的是 `UnicodeDecodeError`，而不是被 `try/except` 吞掉后返回空串
- [ ] `decode_report` 能分别统计「被 ignore 丢弃的字节数」与「被 replace 替换的字节数」，两者不相等时报告要能体现
- [ ] `surrogateescape` 策略实现了完整的「解码—修改—重新编码」往返，且往返后与原始字节完全相等

**涉及知识点**

`文本模式 vs 二进制模式`、`universal newlines 翻译`、`\n 与 \r\n 与 \r`、`str.encode / bytes.decode`、`errors= strict/ignore/replace/surrogateescape`、`open(..., newline=...)`、`bytes.hex()`

### 第 5 题：一个文件，两种身份 ⭐⭐☆

**题目描述**

新建 `q05_dual_identity.py`，这是一个**既是程序又是库**的文件，你要亲手验证它在不同身份下的两种行为。

要求：

1. 文件顶部用一个模块级计数器，统计本模块顶层代码被执行了多少次（每次执行顶层代码时 +1）。
2. 文件提供一个函数 `get_execution_report()`，返回：`__name__` 的当前值、`__package__` 的当前值、顶层执行次数、该模块在 `sys.modules` 中的键名（如果已被导入）。
3. 文件提供一个函数 `bootstrap()`，在被导入时才需要执行的一段逻辑（例如打印一行「本模块以库的身份被加载了」）。
4. 用 `if __name__ == "__main__":` 守卫，把「作为程序运行」的逻辑与「作为库提供能力」的逻辑分开。

然后再新建一个验证脚本 `q05_verify.py`，它必须完成以下实验并打印结论：

- **实验 A**：在验证脚本里导入 `q05_dual_identity` 两次以上，打印顶层执行次数，证明「重复导入不会重复执行顶层代码」，并解释这个结论依赖于哪个内置数据结构。
- **实验 B**：在验证脚本里导入之后，打印 `__name__`，证明它**不等于** `'__main__'`。
- **实验 C**：用 `importlib` 动态导入 `q05_dual_identity`，打印这次导入后 `sys.modules` 中新增/复用的键。
- **实验 D**：用 `subprocess` 启动子进程分别以「直接运行」「`-m` 模块方式」「`-c` 内联导入」三种方式执行，打印三者的 `__name__` 与顶层执行次数差异。
- **实验 E**：在验证脚本里尝试用相对导入（`from . import q05_dual_identity`）导入，打印结果并解释原因。

**输入/输出示例**

```
$ python q05_verify.py
[实验 A] 重复导入测试
  连续导入 3 次，顶层执行次数 = 1
  结论依据：sys.modules 缓存表，同名模块只会被执行一次
[实验 B] __name__ 的取值
  直接运行验证脚本时验证脚本.__name__ = '__main__'
  被导入模块.__name__ = 'q05_dual_identity'
  是否等于 '__main__' : False
[实验 C] 动态导入
  importlib.import_module 前 sys.modules 中有该模块：True
  本次导入是复用缓存：True
[实验 D] 三种执行方式对照
  python q05_dual_identity.py      -> __name__ = '__main__'      顶层执行次数 = 1
  python -m q05_dual_identity     -> __name__ = '__main__'      顶层执行次数 = 1
  python -c "import q05_..."      -> __name__ = 'q05_dual_identity' 顶层执行次数 = 1
[实验 E] 相对导入
  结果：ImportError / SystemError
  原因：直接运行与 -c 方式下 __package__ 为空字符串，相对导入没有包上下文
```

**验收标准**

- [ ] 第 1、2、3、4 项要求的功能均已实现，且 `bootstrap()` 的输出只出现一次
- [ ] 「顶层执行次数」在实验 A 中无论导入多少次都恒为 1，且代码中未使用 `importlib.reload` 之类手段人为干预
- [ ] 实验 D 的三种执行方式均通过 `subprocess` 真实执行并捕获输出，不是在本进程里假装
- [ ] 实验 E 的失败是真实发生的异常（不是预先判断后打印的假象）
- [ ] 文件中不存在「模块顶层直接执行有副作用的业务逻辑」的情况

**涉及知识点**

`__name__` 与 `if __name__ == "__main__"`、`sys.modules 导入缓存`、`__package__ 与 __relative_import__`、`绝对导入 vs 相对导入`、`importlib 动态导入`、`subprocess 三种执行方式`、`模块顶层只做定义不做执行`

### 第 6 题：可控输出与临时工作区 ⭐☆☆

**题目描述**

新建 `q06_workspace_tool.py`，实现一个「沙箱工作区」工具，用于在不污染当前目录的前提下跑一些会产生副作用的代码。

需要实现：

1. `capture(func, *args, **kwargs)`：执行 `func` 并捕获它的全部标准输出与标准错误，返回 `(返回值, stdout 文本, stderr 文本)`。
2. `capture(...)` 必须保证：无论 `func` 是否抛异常，执行结束后**标准输出流都恢复正常**，且异常能继续向外传播或被包装后抛出。
3. `workspace(prefix)`：一个上下文管理器，在临时目录里创建工作区，退出时自动清理；工作区路径通过 `with` 语句暴露给调用方使用。
4. 在 `workspace` 里完成一个子任务：把一段文本写成 UTF-8 文件，再用二进制读回校验字节一致，最后把校验结果作为 `with` 块的返回值传出。

**关键约束**：

- 捕获实现**不能**用「把输出重定向到临时文件再读回」以外的方式偷懒（比如不能用 `sys.stdout = io.StringIO()` 这种会让被捕获函数里的 `sys.stdout.flush()` / 子进程行为失真的做法就宣称完成）。如果你用了 `StringIO`，必须额外说明它与 `sys.stdout.reconfigure` 两种方案在**子进程输出、缓冲刷新、第三方库持有流引用**三个场景上的差异。
- `capture` 对一个会 `print` 后立刻抛异常的函数，行为要明确且有文档说明。

```python
def clean(text):

    return result

    cleaned = clean(raw)
    show(cleaned)

    f.write(cleaned)
    f.close()
    sys.exit(0)


main()
```

### 第 9 题：环境报告生成器（综合收尾）⭐⭐☆

**题目描述**

新建 `q09_env_report_gen.py` 与 `q09_checker.py`，把前 8 题的能力整合成一个真正能用的工程小工具。

`q09_env_report_gen.py` 的职责：

1. 生成一份结构化的环境体检数据（解释器、虚拟环境、`sys.path`、关键环境变量、跨平台常量、默认编码），以 `dict` 形式返回。
2. 支持两种输出目标：`--console`（打印到控制台）与 `--file <路径>`（写入文件，UTF-8，末尾换行符统一为 `\n`）。
3. 文件写入后立刻用二进制模式读回校验字节一致，不一致则以非 0 退出码结束。
4. 支持 `--strict` 开关：开启时，任何一项体检项「无法确认」都以非 0 退出码结束（例如 `sys.path` 中有条目无法归类）。

`q09_checker.py` 的职责：

- 用**三种方式**（直接运行 / `-m` / `-c` 内联导入）执行 `q09_env_report_gen.py`，解析三者的输出并打印对照表。
- 在其中一种方式下故意制造一次编码错误（例如输出一个当前控制台不支持的字符），验证 `--strict` 的退出码行为。

**关键约束**：命令行参数解析要放在 `if __name__ == "__main__":` 块内，但参数解析所用的库必须在文件顶层导入——这个「哪些导入放顶层、哪些放函数内」的取舍要在代码注释或文档字符串中说明理由。

**输入/输出示例**

```

    python -m q09_env_report_gen --console   0    28   '__main__'
    python -c "import q09_env_report_gen..."  1    0    'q09_env_report_gen'
[2] --strict 行为验证
    故意输出不支持字符时，退出码 = 2（非 0），符合预期

    写入字节数 = 1024
```

**验收标准**

- [ ] 三种执行方式均通过 `subprocess` 真实执行，退出码与输出行数被程序解析并打印成表
- [ ] `--file` 模式下的字节一致性校验真实执行，不一致时进程以非 0 码退出
