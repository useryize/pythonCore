**建议用时**：4~6 小时

### 第 1 题：订单状态机 ⭐⭐☆

**题目描述**

某电商系统的订单有 7 种状态：待支付、已支付、已发货、已收货、已取消、退款中、已退款。请实现一个订单状态机，要求：

- 只允许合法的状态流转（待支付→已支付→已发货→已收货；待支付→已取消；已支付→退款中→已退款）
- 任何非法流转都要被明确拒绝，并告知调用方「当前状态是什么、目标状态是什么、允许的目标状态有哪些」
- 每种非法流转要能被调用方**分类处理**：一类是「用户操作失误」（该给友好提示），一类是「程序内部状态错乱」（该报警）。请让调用方能只捕获第一类

**输入/输出示例**

```
# 合法流转
order = Order("SO2024001", State.PENDING_PAYMENT)
order.transfer_to(State.PAID)          # 成功，无输出
order.transfer_to(State.SHIPPED)        # 成功

# 非法流转（用户失误）
order.transfer_to(State.PAID)
# 应输出类似：订单 SO2024001 当前状态为「已发货」，不能变更为「已支付」。
#            当前允许的变更为：已收货

# 非法流转（用户失误的另一种）
order.cancel()
# 已发货的订单不能取消

# 非法流转（程序内部错误）
# 某处代码错误地对已收货订单调用了发货方法
try:
    order.ship()
except <你定义的「程序错误」异常>:
    logger.critical("状态机被非法调用", extra={"order": order.id})
```

**验收标准**
- [ ] 定义了自己的异常基类，并且至少派生出 2 个子类表示「用户失误」与「程序内部错误」两类
- [ ] 调用方可以只捕获用户失误类异常，而程序错误类异常会向上传播
- [ ] 非法流转的报错信息中包含订单号、当前状态、目标状态、当前合法后继状态四项信息
- [ ] 异常对象的 `__str__` 输出是可读的、给最终用户看的文案，而不是 `ValueError: 3`
- [ ] 代码中没有任何 `except Exception: pass` 之类的写法
- [ ] 状态流转成功后，旧状态不会被修改（说明你是返回新对象还是原地修改，以及为什么这么选）

**涉及知识点**
`try/except/else/finally`、`自定义异常继承`、`raise from 异常链`、`isinstance` 多态匹配

### 第 2 题：健壮的文件转换器 ⭐⭐☆☆

**题目描述**

### 第 5 题：代码审查题 —— 异常被当成控制流程 ⭐⭐⭐☆☆

**题目描述**

下面的代码实现「读取配置，找不到就用默认值」。功能看似正常，但在一次线上故障复盘中被认定为根本原因。请审查这段代码的问题。

```python
class ConfigManager:
    def __init__(self, defaults):
        self.defaults = defaults
        self.cache = {}

    def get(self, key):
        try:
            return self.cache[key]
        except KeyError:
            pass
        except Exception as e:
            print(f"读取出错: {e}")
            pass

        try:
            value = self._load_from_file(key)
        except FileNotFoundError:
            value = self.defaults.get(key)
        except PermissionError as e:
            print(f"无权限: {e}")
            value = None
        except Exception as e:
            print(f"未知错误: {e}")
            raise

        self.cache[key] = value
        return value

    def _load_from_file(self, key):
        with open(self.path) as f:
            return json.load(f)[key]

    def get_or_create(self, key):
        try:
            return self.get(key)
        except KeyNotFound:
            value = self.defaults[key]
            self.cache[key] = value
            return value
```

**输入/输出示例**

```
调用方代码：

其中 get() 在「文件存在但 key 不存在」时的实际行为：
  KeyError 被 except KeyError: pass 吃掉 → 走到下面 → FileNotFoundError 也捕获不到
  → KeyError("retry_count") 从 _load_from_file 抛出，没人接，向上传播

调用方看到的是一个「从哪冒出来的 KeyError」，
而不是一个语义清晰的「配置项 retry_count 不存在」。
```

**验收标准**
- [ ] 指出 **6 处以上**问题，每处说明业务后果（不只是代码风格问题）
- [ ] 明确指出：用异常做正常的流程控制（「用户没配这个项」是常态，不该走异常路径）会带来什么代价
- [ ] 明确指出 `except Exception: pass` 与 `print` 混用会导致什么问题（可观测性丢失、KeyError 与真实错误无法区分）
- [ ] 指出 `get_or_create` 里捕获的 `KeyNotFound` 这个异常**在代码中从未被定义或抛出**，属于死代码
- [ ] 指出 `self.path` 从未被赋值的问题
- [ ] 给出了修复方向：将「不存在」与「出错」在类型层面区分开的思路（不写代码），并说明为什么要用自定义异常或返回值而不是内置 KeyError
- [ ] 说明了 `cache[key] = None` 这种「缓存了空值」的后果，以及它如何导致故障难以复现

**涉及知识点**
`try/except/pass` 反模式、异常与Result 模式的边界、自定义异常的设计、异常控制流的开销、可观测性（`logging` vs `print`）、缓存与空值

### 第 7 题：设计一套崩溃诊断机制 ⭐★★★☆
