## 1. 代码风格规范：PEP 8 与命名约定

### 1.1 PEP 8 关键条款速记

```python
# 12-01_pep8.py
# 缩进：4 个空格，不要用 Tab
# 行宽：79 字符（代码行），注释/文档字符串 72
# 空行：模块级 2 行，类之间 2 行，函数之间 2 行，方法之间 1 行
# import：分三组，stdlib / 第三方 / 本地，中间空一行，且字母序


import os
import sys
from collections import defaultdict
from typing import Optional

import requests
from flask import Flask

from mypackage.utils import helper


# 函数名、变量名、参数名：snake_case（小写 + 下划线）
def calculate_total_price(unit_price: float, quantity: int) -> float:
    return unit_price * quantity


# 类名：CamelCase（每个单词首字母大写）
class ShoppingCart:
    # 常量：UPPER_CASE
    MAX_ITEMS = 100

    # 私有属性：前导单下划线（约定为内部使用）
    # 双下划线 __x 会触发 name mangling（编译期改名，防子类冲突）
    def __init__(self) -> None:
        self._items: list[str] = []
        self.__count = 0

    @property
    def count(self) -> int:
        """购物车商品数量（用 @property 让读取时像属性）。"""
        return self.__count

    @staticmethod
    def is_valid_quantity(n: int) -> bool:
        """静态方法：无 self 无 cls。"""
        return 0 < n <= ShoppingCart.MAX_ITEMS

    @classmethod
    def create_empty(cls) -> "ShoppingCart":
        """类方法：第一个参数是 cls，常用于替代构造器。"""
        return cls()


# 特殊方法：前后双下划线
class Money:
    def __init__(self, amount: float, currency: str = "CNY") -> None:
        self.amount, self.currency = amount, currency

    def __repr__(self) -> str:
        return f"Money({self.amount}, {self.currency!r})"

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Money):
            return NotImplemented          # 关键：返回 NotImplemented 而非 False
        return (self.amount, self.currency) == (other.amount, other.currency)

    def __hash__(self) -> int:
        return hash((self.amount, self.currency))

    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise ValueError("货币单位不同")
        return Money(self.amount + other.amount, self.currency)


print(Money(10) + Money(5.5))              # Money(15.5, 'CNY')
print(ShoppingCart.create_empty().count)   # 0
```

### 1.2 命名约定速查表

| 对象 | 风格 | 示例 |
|---|---|---|
| 模块 / 包 | `snake_case` | `data_parser`, `my_package` |
| 类 / 异常 | `CapWords` | `HttpClient`, `ValueError`, `MyError` |
| 函数 / 方法 / 变量 / 属性 | `snake_case` | `get_user`, `max_retry_count` |
| 常量 | `UPPER_CASE` | `MAX_SIZE`, `DEFAULT_TIMEOUT` |
| 内部/受保护 | `_leading` | `_cache`, `_validate()` |
| 强内部 | `__leading` | `__init__`, `__count` |
| 特殊方法 | `__dunder__` | `__repr__`, `__enter__` |
| 包内导入 | 绝对导入为主 | `from mypkg.mod import f` |
| 类型变量 | `T`, `K`, `V` | `T = TypeVar("T")` |
| 布尔变量 | `is_/has_/can_` 前缀 | `is_valid`, `has_key` |
| 集合 | 复数名 | `items`, `names`, `results` |

## 2. 格式化与静态检查工具链

### 2.1 三件套分工

| 工具 | 类型 | 职责 | 是否改代码 |
|---|---|---|---|
| **ruff** | linter + formatter（Rust 编写，极快） | 风格规范 + 常见错误检查 | ✅ check 会修 |
| **black** | formatter | 格式化（也可由 ruff format 替代） | ✅ |
| **mypy** | 静态类型检查 | 类型错误 | ❌ |

现代推荐组合：**`ruff`（lint + format）+ `mypy`（类型）**，`black` 可选保留。ruff 比 flake8 + black + isort 快 10~100 倍。

```python
# 12-04_mypy_demo.py
def greet(name: str) -> str:
    return f"Hello {name}"


# ✅ 通过检查
print(greet("Tom"))

# ❌ 这些都会被 mypy 报错（但 Python 运行时才崩或行为诡异）
# greet(123)                    # arg-type: 期望 str 得到 int
# print(greet())                # call-arg: 缺少必需参数
# n: int = "hello"              # assignment: int = str
# return 42                     # return-value: 应返回 str
#
# 更隐蔽的：
def total(items: list[int]) -> int:
    return sum(items)


total(["1", "2"])    # ❌ list-arg: 期望 list[int] 收到 list[str]
total([1, 2, None])  # ❌ list-item: None 不是 int

# Optional 需要显式判空（这是 mypy 最有价值的功能之一）
def find(key: str) -> str | None:
    return None if key else key


def use() -> str:
    return find("a")     # ❌ return-value: Optional[str] 不能当 str 返回

def use_ok() -> str:
    v = find("a")
    if v is None:
        return ""         # ✅ 显式处理 None
    return v
```

## 3. 单元测试

### 3.1 unittest vs pytest 对比

| 维度 | `unittest` | `pytest` |
|---|---|---|
| 出处 | 标准库 | 第三方（`pip install pytest`） |
| 写法 | 继承 `TestCase`，方法名 `test_*` | 写普通函数，名字 `test_*` |
| 断言 | `self.assertEqual(a, b)` | `assert a == b`（失败自动打印中间值） |
| 复用/参数化 | 需继承 mixin 或写循环 | `conftest.py` + `@pytest.mark.parametrize` |
| 夹具 | `setUp` / `tearDown` | fixture（可分层、可按需、参数化） |
| Mock | `unittest.mock`（够用） | `pytest-mock` 插件语法更简洁 |
| 插件生态 | 基本没有 | 极其丰富（cov、mock、asyncio、benchmark） |
| 执行发现 | 需要 `discover` | 自动发现 |
| IDE 支持 | 原生良好 | 良好 |

**结论**：`unittest` 无依赖、够用，适合简单项目和教学；`pytest` 生态强、表达力高，是事实上的行业标准。

```python
# 12-05_unittest_style.py
import unittest
from unittest.mock import patch


def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("除数不能为 0")
    return a / b


class TestDivide(unittest.TestCase):
    def setUp(self):
        """每个测试方法前执行。"""
        self.a, self.b = 10, 2

    def tearDown(self):
        """每个测试方法后执行。"""
        pass

    def test_normal(self):
        self.assertEqual(divide(self.a, self.b), 5.0)
        self.assertAlmostEqual(divide(1, 3), 0.333333, places=6)

    def test_zero_division(self):
        with self.assertRaises(ZeroDivisionError):
            divide(1, 0)

    def test_param_like_loop(self):
        """unittest 没有 parametrize，只能循环 + subTest。"""
        for a, b, expected in [(4, 2, 2), (9, 3, 3), (1, 1, 1)]:
            with self.subTest(a=a, b=b):
                self.assertEqual(divide(a, b), expected)


if __name__ == "__main__":
    unittest.main()
```

```python
# 12-06_pytest_style.py
import pytest
from typing import Any


def divide(a: float, b: float) -> float:
    if b == 0:
        raise ZeroDivisionError("除数不能为 0")
    return a / b


# ---------- 基本写法 ----------
def test_divide():
    assert divide(10, 2) == 5.0
    assert divide(1, 3) == pytest.approx(0.3333333, rel=1e-6)   # 浮点比较


def test_zero_division():
    with pytest.raises(ZeroDivisionError, match="除数不能为 0"):
        divide(1, 0)


# ---------- 参数化 ----------
@pytest.mark.parametrize("a,b,expected", [
    (10, 2, 5.0),
    (9, 3, 3.0),
    (1, 1, 1.0),
    pytest.param(-1, 2, -0.5, id="negative"),
    pytest.param(0, 5, 0.0, id="zero"),
])
def test_divide_param(a, b, expected):
    assert divide(a, b) == expected


# 多组参数（笛卡尔积）
@pytest.mark.parametrize("a", [1, 2])
@pytest.mark.parametrize("b", [3, 4])
def test_divide_matrix(a, b):
    assert divide(a, b) > 0


# ---------- fixture：函数级与类级作用域 ----------
@pytest.fixture
def sample_user() -> dict[str, Any]:
    """每个测试函数都会拿到一份全新的数据。"""
    return {"name": "Tom", "age": 30}


@pytest.fixture
def user_db(sample_user):
    """fixture 可以依赖其他 fixture，实现分层复用。"""
    db = {sample_user["name"]: sample_user}
    return db


def test_user(sample_user):
    assert sample_user["name"] == "Tom"


def test_db(user_db):
    assert user_db["Tom"]["age"] == 30


# ---------- fixture 参数化（能做 unittest 做不到的事） ----------
@pytest.fixture(params=["fast", "slow"], ids=["快模式", "慢模式"])
def client(request):
    speed = request.param
    return {"speed": speed}


def test_client_speed(client):
    assert client["speed"] in ("fast", "slow")


# ---------- yield fixture：自动清理 ----------
@pytest.fixture
def temp_file(tmp_path):
    """tmp_path 是 pytest 内置 fixture，提供临时目录。"""
    f = tmp_path / "data.txt"
    f.write_text("hello", encoding="utf-8")
    yield f                       # 测试运行到这里
    f.unlink(missing_ok=True)     # 测试结束后执行（类似 tearDown）


def test_temp_file(temp_file):
    assert temp_file.read_text(encoding="utf-8") == "hello"


# ---------- 跳过与预期失败 ----------
import sys

@pytest.mark.skip(reason="待实现")
def test_skipped():
    assert False


@pytest.mark.skipif(sys.version_info < (3, 10), reason="需要 Python 3.10+")
def test_skipif():
    assert True


@pytest.mark.xfail(reason="已知 bug，修复前预期失败")
def test_xfail():
    assert divide(1, 0) == 0
```

### 3.3 conftest.py：pytest 的灵魂

`conftest.py` 是 pytest 的**魔法文件**，作用域为所在目录及所有子目录。

```python
# 12-07_conftest.py
# 放在项目根目录（与 pyproject.toml 同级）
import pytest
import os
from pathlib import Path


@pytest.fixture(scope="session", autouse=True)
def env_setup():
    """session 级：整个测试会话只跑一次，且自动执行。"""
    os.environ["APP_ENV"] = "test"
    os.environ.setdefault("DB_URL", "sqlite:///:memory:")
    yield
    print("测试环境清理完毕")


@pytest.fixture(scope="module")
def db():
    """module 级：同模块内共享，注意不要跨模块共享可变状态。"""
    conn = {"connected": True, "data": {}}
    yield conn
    conn["connected"] = False


@pytest.fixture
def tmp_workspace(tmp_path: Path):
    """tmp_path 是内置 fixture，函数级，自动清理。"""
    (tmp_path / "input").mkdir()
    (tmp_path / "output").mkdir()
    return tmp_path


def pytest_addoption(parser):
    """添加命令行选项：pytest --slow"""
    parser.addoption("--slow", action="store_true", help="运行慢速测试")


def pytest_configure(config):
    """pytest 初始化时调用，可注册自定义 marker。"""
    config.addinivalue_line("markers", "slow: 标记为慢速测试")


def pytest_collection_modifyitems(config, items):
    """按 marker 筛选/排序测试。"""
    if config.getoption("--slow"):
        return
    skip_slow = pytest.mark.skip(reason="需要 --slow")
    for item in items:
        if "slow" in item.keywords:
            item.add_marker(skip_slow)
```

### 3.4 mock：隔离外部依赖

```python
# 12-08_mock.py
import pytest
from unittest.mock import patch, MagicMock, Mock, call, sentinel


class UserService:
    """假设它内部要调数据库和发邮件——测试时都 mock 掉。"""

    def __init__(self, db, mailer):
        self.db, self.mailer = db, mailer

    def register(self, name):
        user_id = self.db.insert({"name": name})
        self.mailer.send(f"Welcome {name}", to=user_id)
        return user_id


# ---------- 1) 完全手动创建替身 ----------
def test_register_manual():
    db = Mock()
    db.insert.return_value = 42                    # 配置返回值
    mailer = Mock()

    svc = UserService(db, mailer)
    assert svc.register("Tom") == 42

    # 断言交互
    db.insert.assert_called_once_with({"name": "Tom"})
    mailer.send.assert_called_once_with("Welcome Tom", to=42)


# ---------- 2) patch：替换真实模块里的对象 ----------
def test_register_patch(tmp_path):
    db = MagicMock()
    db.insert.return_value = 7
    mailer = MagicMock()

    with patch("mypkg.calculator.open", mock_open(read_data="x")) as m_open:
        pass    # 示例：patch 内模块的函数

    svc = UserService(db, mailer)
    svc.register("Amy")
    assert db.insert.call_count == 1


# ---------- 3) 用 monkeypatch（pytest 内置，无需 import）----------
def test_monkeypatch_env(monkeypatch):
    monkeypatch.setenv("API_KEY", "test-key")
    monkeypatch.delenv("UNUSED", raising=False)
    monkeypatch.setattr("mypkg.calculator.Calculator.div", lambda s, a, b: 0)

    import os
    assert os.environ["API_KEY"] == "test-key"


# ---------- 4) 副作用：side_effect ----------
def test_side_effect():
    db = Mock()
    db.insert.side_effect = [1, 2, RuntimeError("db down")]   # 依次返回

    assert db.insert() == 1
    assert db.insert() == 2
    with pytest.raises(RuntimeError):
        db.insert()

    # 也可以直接指定要调用的函数
    db2 = Mock()
    db2.insert.side_effect = lambda row: len(row) * 100
    assert db2.insert({"a": 1}) == 100


# ---------- 5) autospec：按真实签名约束，防止拼错 ----------
def test_autospec():
    db = Mock()
    calc = __import__("mypkg.calculator", fromlist=["Calculator"]).Calculator()
    spec = pytest.importorskip("mypkg.calculator")

    from mypkg.calculator import Calculator
    svc = UserService(db, Mock())
    # 用 spec 化的 mock：调用不存在的参数会直接报错
    with patch.object(Calculator, "div") as m:
        m.side_effect = ValueError
        with pytest.raises(ValueError):
            calc.div(1, 0)


# ---------- 6) 记录调用顺序 ----------
def test_call_order():
    flow = Mock()
    flow.step("start")
    flow.step("stop")
    assert flow.method_calls == [call.step("start"), call.step("stop")]


# ---------- 7) sentinel：不会与真实值冲突的独特标记 ----------
def test_sentinel():
    db = Mock()
    db.insert.return_value = sentinel.unexpected
    svc = UserService(db, Mock())
    assert svc.register("X") is sentinel.unexpected
```

**Mock 家族的取舍**

| 类型 | 行为 | 用在哪 |
|---|---|---|
| `Mock` | 基本调用记录 | 只需要返回值/断言调用 |
| `MagicMock` | 支持魔术方法（`len()`、`__iter__`、`with`） | 默认首选 |
| `AsyncMock` | 异步函数（Python 3.8+） | 测 `async def` |
| `patch` | 上下文管理器/装饰器，替换真实对象 | 隔离模块依赖 |
| `monkeypatch` | pytest 内置，作用域自动回收 | 改属性/环境变量/模块成员 |
| `fake` / `fake_factory` | 行为近似但不严格 | 需要一定逻辑（如 fake redis） |

**何时不该 mock**：不要 mock 你自己写的纯函数（没意义）；不要过度 mock 导致测试与实现耦合（改一行就全红）；第三方 HTTP 调用、数据库、时间、随机数才是 mock 的合理目标。

## 4. pre-commit：把检查前移

### 4.1 为什么需要

CI 跑全量检查慢且晚，问题发现得晚。pre-commit 在**每次 `git commit` 时**自动跑，改到一半就能发现问题，改完再提交，CI 只做最终把关。

### 4.2 安装与配置

```bash
pip install pre-commit
pre-commit install          # 生成 .git/hooks/pre-commit
pre-commit run --all-files  # 手动跑一遍全部文件
pre-commit autoupdate       # 更新 hook 版本
```

```yaml
# .pre-commit-config.yaml
default_language_version:
  python: python3.12

repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace        # 删行尾空格
      - id: end-of-file-fixer          # 确保文件以换行结尾
      - id: check-yaml                 # 校验 YAML 语法
      - id: check-toml                 # 校验 TOML 语法
      - id: check-added-large-files    # 阻止提交 >500KB 的文件
      - id: check-merge-conflict       # 检查残留的冲突标记
      - id: detect-private-key         # 防止误提交私钥！
      - id: mixed-line-ending
        args: [--fix=lf]

  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.0
    hooks:
      - id: ruff                 # lint 并自动修复
        args: [--fix, --exit-non-zero-on-fix]
      - id: ruff-format          # 格式化

  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.14.0
    hooks:
      - id: mypy
        files: ^src/
        additional_dependencies: [types-requests]
        args: [--strict, --ignore-missing-imports]

  - repo: local                  # 自定义 hook
    hooks:
      - id: pytest
        name: pytest
        entry: pytest -q --tb=short
        language: system
        pass_filenames: false
        files: ^(tests/|src/)
        stages: [pre-push]
```

**要点**

- `rev` 必须指定具体版本标签，pre-commit 会缓存环境，别用浮动分支。
- `entry` 用 `language: system` 表示用当前虚拟环境（不用单独建环境，更快）。
- 把耗时长的钩子（如 pytest、mypy）放在 `pre-push` 阶段，`pre-commit` 阶段只放快的。
- 钩子失败会**中止提交**，这是设计意图。实在需要绕过，用 `git commit --no-verify`（慎用）。

## 5. Git 协作规范

### 5.1 分支模型

**Git Flow（适合有明确版本发布的产品）**

```
main (稳定生产)
  └─ develop (集成)
       ├─ feature/xxx
       ├─ release/1.2.0 ──> main (打 tag v1.2.0)
       └─ hotfix/xxx ───> main + develop
```

**Trunk-Based Development（适合持续交付/小团队，CI 必备）**

```
main ──●──●──●──●──●──>   短生命周期分支，频繁合并
       \     /
        feat/123 (24-48h 内合并)
```

选型：团队 >10 人或需要多版本并行维护 → Git Flow；小型团队每日多次发布 → Trunk-Based。

**分支命名约定**

| 类型 | 前缀 | 示例 |
|---|---|---|
| 功能 | `feat/` | `feat/user-login` |
| 修复 | `fix/` | `fix/token-expiry` |
| 热修 | `hotfix/` | `hotfix/db-corruption` |
| 发布 | `release/` | `release/v1.2.0` |
|  chore/构建/依赖 | `chore/` | `chore/bump-deps` |
| 重构 | `refactor/` | `refactor/auth-module` |
| 文档 | `docs/` | `docs/api-guide` |

团队也可直接用 `type(scope): subject` 形式：`feat(auth): add refresh token`。

### 5.2 提交信息规范

用 **Conventional Commits**：

```
<type>(<scope>): <subject>

[optional body: 详细说明、动机、影响]

[optional footer: BREAKING CHANGE: ... / Closes #123]
```

```bash
git commit -m "feat(auth): add JWT refresh token rotation"
git commit -m "fix(calculator): avoid ZeroDivisionError on empty input

Previously divide(1, 0) raised an uncaught ZeroDivisionError which
crashed the API worker. Now returns ValueError with a clear message.

Closes #1234"
git commit -m "refactor!: drop Python 3.8 support

BREAKING CHANGE: minimum version is now 3.9"
```

`type` 类型：`feat`（新功能）、`fix`（修 bug）、`refactor`（重构，不改行为）、`perf`（性能）、`docs`、`test`、`build`、`ci`、`chore`、`style`（纯格式）。

**铁律**

1. **一个提交只做一件事**。不要把修 bug 和改格式混在一起。
2. **提交信息写给 6 个月后的自己看**：解释"为什么"，不只说"改了什么"。
3. **不要提交到 main**（除非团队用 Trunk-Based 且有强制保护分支）。
4. 提交要频繁——小步快跑，比攒一天提交一次好 review。

```bash
# 保护分支：禁止直接 push 到 main
git push origin -u feature/xxx       # 推到自己的分支
gh pr create --fill --base main       # 创建 PR
# 管理员设置 main 为 protected：必须走 PR + 至少 1 个 approve + CI 通过
```

### 5.3 常用协作命令

```bash
# ---------- 分支管理 ----------
git fetch --all --prune          # 拉取并清理已删除的远程分支
git switch -c feat/login         # 创建并切换（新版；老版本 git checkout -b）
git switch -                     # 切回上一个分支
git branch -vv                   # 看分支跟踪状态
git branch -d feat/login         # 删除已合并的分支（安全）
git branch -D feat/login         # 强制删除（未合并也删，慎用）

# ---------- 同步 ----------
git fetch origin
git rebase origin/main           # 把自己的提交移到最新 main 之上（历史线性）
git push --force-with-lease      # rebase 后强推（比 --force 安全，会检查远端是否被别人推过）

# ---------- 清理 ----------
git restore --staged file.py     # 撤销 git add，但保留改动
git restore file.py              # 丢弃工作区改动（危险）
git reset --soft HEAD~1          # 撤销上一次提交，改动仍在暂存区
git stash push -m "msg"          # 临时存起来
git stash pop                    # 取回
git reflog                       # 找回"丢失"的提交

# ---------- 排查 ----------
git log --oneline --graph --all -20
git blame -L 10,20 file.py       # 谁改了这段
git bisect start HEAD v1.0       # 二分查找引入 bug 的提交
git diff main...HEAD              # 本分支相对 main 的改动
git diff --stat main...HEAD
```

### 5.4 Code Review 检查清单

提交 PR 前自检，能省掉大量来回：

- [ ] 代码能跑通，相关测试已加并通过
- [ ] 测试覆盖了正常路径和边界/异常路径
- [ ] 变量/函数命名自解释，无 `a`、`tmp2`、`doStuff`
- [ ] 没有硬编码的魔法值（用常量或配置）
- [ ] 没有 `print()` 残留（用 `logging`）
- [ ] 没有注释掉的死代码
- [ ] 错误处理得当：不是吞异常
- [ ] 不引入不必要的依赖
- [ ] 改动范围聚焦（不夹带无关的重构）
- [ ] 性能敏感路径没引入额外的循环或拷贝
- [ ] 公共函数/类的 docstring 已更新

### 6.1 日志：四种级别与最佳实践

```python
# 12-10_logging.py
import logging
import logging.config
import sys
import os
from pathlib import Path


def setup_logging(level: str = "INFO", log_file: str | None = None) -> logging.Logger:
    """配置根 logger，返回应用 logger。"""
    log_format = "%(asctime)s | %(levelname)-8s | %(name)s | %(filename)s:%(lineno)d | %(message)s"
    formatter = logging.Formatter(log_format, datefmt="%Y-%m-%d %H:%M:%S")

    handlers: list[logging.Handler] = []

    # 控制台
    console = logging.StreamHandler(sys.stdout)
    console.setFormatter(formatter)
    handlers.append(console)

    # 文件（自动轮转）
    if log_file:
        Path(log_file).parent.mkdir(parents=True, exist_ok=True)
        file_handler = logging.handlers.RotatingFileHandler(
            log_file, maxBytes=10 * 1024 * 1024, backupCount=5, encoding="utf-8"
        )
        file_handler.setFormatter(formatter)
        handlers.append(file_handler)

    logging.basicConfig(
        level=getattr(logging, level.upper()),
        format=log_format,
        handlers=handlers,
        force=True,          # Python 3.8+：覆盖已有配置
    )

    # 降噪：第三方库日志级别调高
    logging.getLogger("urllib3").setLevel(logging.WARNING)
    logging.getLogger("sqlalchemy.engine").setLevel(logging.WARNING)

    return logging.getLogger("myapp")


logger = setup_logging("DEBUG", "logs/app.log")

logger.debug("调试信息，默认不输出（除非级别是 DEBUG）")
logger.info("服务启动于 127.0.0.1:8080")
logger.warning("磁盘使用率 {0:.1%}", 0.85)          # ✅ 惰性格式化
logger.error("数据库连接失败", exc_info=True)          # 带完整堆栈
logger.critical("磁盘已满，服务终止")

# ---------- 结构化字段 ----------
logger.info("user login", extra={"user_id": 42, "ip": "10.0.0.1"})


# ---------- 模块级 logger：不要在模块顶层建 logger ----------
# 正确做法
log = logging.getLogger(__name__)     # 每个模块一个 logger，便于分级控制
log.info("calculator: 1 + 2 = %s", 3)

# ❌ 错误：log = logging.getLogger()  → 拿到 root logger，会受全局配置干扰
# ❌ 错误：log = setup_logging()      → 每个模块都重复配置，handler 重复


# ---------- 异常处理中的经典错误 ----------
def fetch_data():
    try:
        result = {"a": 1}
        return result["missing"]        # KeyError
    except KeyError:
        logger.exception("取数据失败")   # ✅ 用 exception / exc_info=True
        raise                          # 重新抛出，让上层决定
    except Exception:
        logger.exception("未知错误")
        return None                     # 或静默降级


# ---------- 为什么不建议自己封装 print ----------
# 1) print 无级别、无时间、无文件位置
# 2) 无法按模块控制输出
# 3) 无自动轮转
# 4) 难以统一收集到 ELK / CloudWatch
```

**日志级别选择**

| 级别 | 用于 | 生产是否开启 |
|---|---|---|
| `DEBUG` | 开发调试细节（SQL 语句、循环内变量） | ❌ |
| `INFO` | 关键业务事件：启动、请求处理、任务完成 | ✅ |
| `WARNING` | 异常但可自愈：重试成功、参数用默认值 | ✅ |
| `ERROR` | 功能失败需人工介入：请求失败、任务异常 | ✅ |
| `CRITICAL` | 服务不可用：数据库全挂、磁盘满 | ✅ |

日志规范：一条日志讲清**一件事**；用 `%s` 惰性占位（`logger.info("x=%s", x)`）而非 f-string（省格式化开销）；不要记录密码、token、身份证、信用卡等敏感信息。

### 6.2 配置分层

原则：**代码不硬编码任何环境相关的东西**，配置按"默认值 → 环境变量 → 配置文件 → 命令行"逐层覆盖。

```
优先级（从低到高）：
  代码内默认值  <  .env 文件  <  环境变量  <  配置文件  <  命令行参数
```

```python
# 12-11_config.py
"""配置三层：默认 -> 环境变量 -> .env 文件（仅开发）。"""
import os
from pathlib import Path
from dataclasses import dataclass, field


BASE_DIR = Path(__file__).resolve().parent.parent
ENV_FILE = BASE_DIR / ".env"


def _load_dotenv(path: Path = ENV_FILE) -> None:
    """极简 .env 加载器（生产环境建议用 python-dotenv）。"""
    if not path.exists():
        return
    for raw in path.read_text(encoding="utf-8").splitlines():
        line = raw.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        key, _, value = line.partition("=")
        key, value = key.strip(), value.strip().strip("'\"")
        # setdefault：真实环境变量优先级更高，不被 .env 覆盖
        os.environ.setdefault(key, value)


_load_dotenv()


def _get(key: str, default: str | None = None) -> str:
    val = os.getenv(key)
    if val is None:
        if default is not None:
            return default
        raise RuntimeError(f"缺少必需的环境变量：{key}")
    return val


def _get_bool(key: str, default: bool = False) -> bool:
    return os.getenv(key, str(default)).strip().lower() in ("1", "true", "yes", "on")


def _get_int(key: str, default: int) -> int:
    return int(os.getenv(key, str(default)))


def _get_list(key: str, default: str = "") -> list[str]:
    return [s.strip() for s in os.getenv(key, default).split(",") if s.strip()]


@dataclass(frozen=True)
class Settings:
    """应用配置。类型在这里被强制转换，避免全项目都是 str。"""

    app_name: str = field(default_factory=lambda: _get("APP_NAME", "myapp"))
    env: str = field(default_factory=lambda: _get("APP_ENV", "dev"))
    debug: bool = field(default_factory=lambda: _get_bool("DEBUG", False))

    host: str = field(default_factory=lambda: _get("HOST", "127.0.0.1"))
    port: int = field(default_factory=lambda: _get_int("PORT", 8080))

    db_url: str = field(default_factory=lambda: _get(
        "DATABASE_URL", "sqlite:///./app.db"))
    redis_url: str = field(default_factory=lambda: _get(
        "REDIS_URL", "redis://localhost:6379/0"))

    log_level: str = field(default_factory=lambda: _get("LOG_LEVEL", "INFO"))
    allowed_origins: list[str] = field(
        default_factory=lambda: _get_list("ALLOWED_ORIGINS", "http://localhost:3000"))

    def is_prod(self) -> bool:
        return self.env == "prod"

    @property
    def safe_dump(self) -> dict:
        """日志输出时脱敏。"""
        d = {f.name: getattr(self, f.name) for f in self.__dataclass_fields__.values()}
        d["db_url"] = "***" if self.db_url else ""
        return d


settings = Settings()

if __name__ == "__main__":
    print("配置加载完成：")
    for k, v in settings.safe_dump.items():
        print(f"  {k:16s} = {v}")
    print("DEBUG 开关:", settings.debug)
    print("生产环境?", settings.is_prod())
```

## 7. 依赖锁定

### 7.1 为什么必须 pin 版本

```bash
# ❌ 不可复现：半年后装到的 torch 可能是完全不同的版本
pip install requests
```

```bash
# ✅ 精确指定
pip install requests==2.32.3

# ✅ 只锁定直接依赖（不传递）
pip install requests==2.32.3

# ✅ 导出当前环境所有包（临时快照）
pip freeze > requirements.lock.txt
```

`pip freeze` 的问题是：它分不清哪些是**直接依赖**、哪些是**传递依赖**，全部写进 requirements 会导致上游更新时你必须手动维护。

### 7.2 pip-tools：编译出干净锁文件

```bash
pip install pip-tools

# requirements.in —— 只写直接依赖，手写
cat > requirements.in <<'EOF'
fastapi==0.115.0
uvicorn[standard]==0.32.0
pydantic==2.9.0
requests==2.32.3
EOF

# 编译：解析传递依赖并锁定所有版本 + hash
pip-compile --generate-hashes -o requirements.txt requirements.in

# 升级某个包
pip-compile --upgrade-package requests -o requirements.txt requirements.in

# 安装（用 hash 校验防篡改）
pip install --require-hashes -r requirements.txt
```

`requirements.in`（手写，进版本库）/ `requirements.txt`（自动生成，进版本库）/ 两者都提交。

### 7.3 现代方案：`uv`（推荐，快 10-100 倍）

```bash
pip install uv

# 创建项目
uv init myproject && cd myproject
uv add fastapi uvicorn pydantic          # 添加依赖并写入 pyproject.toml + uv.lock
uv add "requests>=2.32"
uv add --dev pytest pytest-cov ruff mypy  # 开发依赖

# 同步（严格按锁文件）
uv sync
uv sync --frozen            # CI 里用，保证与锁文件完全一致
uv lock --upgrade-package requests

# 运行
uv run pytest
uv run python -m mypkg
```

`uv.lock` 是跨平台、精确到版本和 hash 的锁文件，**必须**提交到版本库。

### 7.4 其他方案对比

| 方案 | 优点 | 适用 |
|---|---|---|
| `pip-tools` | 纯 pip 工作流，轻量 | 已有 pip 项目 |
| `uv` | 极快，自带 venv/pyproject/lock | **新项目首选** |
| `poetry` | 依赖 + 打包一体，规范 | 需要发包到 PyPI |
| `pipenv` | `Pipfile` 风格，概念直观 | 团队偏好 |
| `conda` | 能管理非 Python 依赖（CUDA 等） | 科学计算/深度学习 |

### 7.5 requirements 文件分工

```
requirements.in     # 手写：直接依赖
requirements.txt    # pip-compile 生成：全部锁定 + hash（生产环境用这个）
requirements-dev.txt  # 开发依赖：pytest/ruff/mypy（本地用）
```

### 9.1 docstring 三种风格

```python
# 12-13_docstrings.py
"""
模块级 docstring。

描述模块用途，通常放在文件第一行（编码声明之后）。
"""
from typing import Optional


def calculate(items: list[float], discount: float = 0.0) -> float:
    """计算带折扣的总价。

    Args:
        items: 商品价格列表。
        discount: 折扣比例，0.1 表示 9 折，取值范围 [0, 1)。

    Returns:
        折后总价（浮点）。

    Raises:
        ValueError: 当 discount 不在 [0, 1] 范围内。
        TypeError: 当 items 中含有非数值类型。

    Example:
        >>> calculate([100.0, 50.0], discount=0.2)
        120.0

    Note:
        本函数不做四舍五入，精度问题由调用方处理。
    """
    if not 0.0 <= discount <= 1.0:
        raise ValueError("discount 必须在 [0,1] 之间")
    total = sum(items)
    return total * (1 - discount)


class ShoppingCart:
    """购物车。

    Attributes:
        max_items: 单车最大商品数。
    """

    max_items: int = 100

    def __init__(self, max_items: Optional[int] = None) -> None:
        """初始化购物车。

        Args:
            max_items: 覆盖类默认的最大商品数。
        """
        self._items: list[str] = []
        if max_items:
            self.max_items = max_items

    def add(self, item: str) -> None:
        """向购物车添加商品。

        Args:
            item: 商品名称。

        Raises:
            ValueError: 购物车已满时。
        """
        if len(self._items) >= self.max_items:
            raise ValueError("购物车已满")
        self._items.append(item)
```

### 10.2 分层原则

```
API 层（routes/handler）  →  业务层（services）  →  数据层（repositories）
     参数校验/序列化              核心业务规则              SQL / HTTP / 文件
```

依赖方向**必须单向朝内**：API 层依赖业务层，业务层依赖数据层，数据层不依赖任何上层。这样：
- 业务逻辑可以被 CLI、API、定时任务复用；
- 替换数据库只动数据层；
- 测试时 mock 数据层即可，不用启动数据库。

```python
# 12-14_layers.py
"""示例：一个清晰分层的最小实现。"""
import abc
from dataclasses import dataclass, field
from datetime import datetime, timezone


# ============ 数据层 ============
@dataclass
class User:
    id: int
    name: str
    email: str
    created_at: datetime


class UserRepository(abc.ABC):
    """抽象接口：业务层只依赖它，不依赖具体实现。"""

    @abc.abstractmethod
    def get(self, user_id: int) -> User | None: ...

    @abc.abstractmethod
    def save(self, user: User) -> User: ...

    @abc.abstractmethod
    def find_by_email(self, email: str) -> User | None: ...


class InMemoryUserRepository(UserRepository):
    """内存实现：测试和演示用，不依赖外部服务。"""

    def __init__(self) -> None:
        self._store: dict[int, User] = {}
        self._next_id = 1

    def get(self, user_id: int) -> User | None:
        return self._store.get(user_id)

    def save(self, user: User) -> User:
        if user.id == 0:
            user.id = self._next_id
            self._next_id += 1
        user.created_at = datetime.now(timezone.utc)
        self._store[user.id] = user
        return user

    def find_by_email(self, email: str) -> User | None:
        return next((u for u in self._store.values() if u.email == email), None)


# ============ 业务层 ============
class UserService:
    """业务规则集中在这里，不关心数据从哪来、结果发给谁。"""

    def __init__(self, repo: UserRepository) -> None:
        self.repo = repo

    def register(self, name: str, email: str) -> User:
        if self.repo.find_by_email(email):
            raise ValueError(f"邮箱 {email} 已被注册")
        if "@" not in email:
            raise ValueError("邮箱格式不合法")
        return self.repo.save(User(id=0, name=name, email=email))

    def get(self, user_id: int) -> User | None:
        return self.repo.get(user_id)


# ============ 接口层 ============
class UserCLI:
    """把业务结果转成用户可读的输出。"""

    def __init__(self, service: UserService) -> None:
        self.service = service

    def register(self, name: str, email: str) -> int:
        try:
            user = self.service.register(name, email)
            return user.id
        except ValueError as e:
            print(f"错误：{e}")
            return -1


# ============ 组装 ============
if __name__ == "__main__":
    repo = InMemoryUserRepository()
    cli = UserCLI(UserService(repo))

    uid = cli.register("张三", "zhang@example.com")
    print(f"创建用户 id={uid}")

    uid2 = cli.register("张三", "zhang@example.com")     # 重复邮箱
    print(f"第二个结果 id={uid2}（-1 表示失败）")

    print("查询 id=1:", repo.get(1))
```

**预期输出**

```
创建用户 id=1
错误：邮箱 zhang@example.com 已被注册
第二个结果 id=-1（-1 表示失败）
查询 id=1: User(id=1, name='张三', email='zhang@example.com', created_at=...)
```

## 11. 性能优化清单

### 11.1 第一原则：先测量，再优化

> 「premature optimization is the root of all evil」—— Donald Knuth
> 「We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up the remaining 3%.」
> —— Donald Knuth, *Structured Programming with go to Statements*

**优化的正确顺序**：

1. **测量** → 找出真正的瓶颈（不是猜）
2. **确认瓶颈可优化** → 有些问题是 I/O 或算法复杂度，重写代码没用
3. **小步改动** → 每次改一处，测一次
4. **验证收益** → 基准测试证明更快
5. **保持可读性** → 优化不该让代码难维护到无法再优化

```python
# 12-15_benchmark.py
"""测量代码耗时：先要有一个可靠的计时工具。"""
import time
from functools import wraps
from typing import Callable, Any


def timeit(func: Callable[..., Any]) -> Callable[..., Any]:
    """装饰器：测函数耗时（微基准，慎用于短函数）。"""

    @wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()     # 高精度，纳秒级单调时钟
        result = func(*args, **kwargs)
        elapsed = time.perf_counter() - start
        print(f"  {func.__name__}: {elapsed * 1000:.3f} ms")
        return result

    return wrapper


def bench(n: int = 100_000, repeats: int = 5):
    """重复多次取最小值——减少 GC 和调度噪声的影响。"""
    def decorator(fn):
        results = []
        for _ in range(repeats):
            start = time.perf_counter()
            for _ in range(n):
                fn()
            results.append(time.perf_counter() - start)
        best = min(results)
        print(f"  {fn.__name__}: 最好 {best * 1000:.3f} ms "
              f"(平均 {sum(results) / repeats * 1000:.3f} ms)")
        return fn
    return decorator


if __name__ == "__main__":
    import random
    data = [random.random() for _ in range(10_000)]

    @bench(n=10, repeats=5)
    def version_listcomp():
        return [x * 2 for x in data]

    @bench(n=10, repeats=5)
    def version_loop():
        result = []
        for x in data:
            result.append(x * 2)
        return result

    @bench(n=10, repeats=5)
    def version_map():
        return list(map(lambda x: x * 2, data))
```

**预期输出**（数量级示例）

```
  version_listcomp: 最好 0.75 ms (平均 0.80 ms)
  version_loop: 最好 1.90 ms (平均 1.95 ms)
  version_map: 最好 0.90 ms (平均 0.95 ms)
```

```bash
import cProfile, pstats, io

def profile_function(fn, *args, **kwargs):
    pr = cProfile.Profile()
    pr.enable()
    result = fn(*args, **kwargs)
    pr.disable()
    s = io.StringIO()
    ps = pstats.Stats(pr, stream=s).sort_stats("cumulative")
    ps.print_stats(15)
    print(s.getvalue())
    return result
```

**输出解读**

```
   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
      500    0.021    0.00    1.234     0.00 process.py:45(process_data)
      500    0.002    0.00    1.100     0.00 db.py:22(execute)
      500    0.000    0.00    1.090     0.00 db.py:18(_connect)
     5000    0.450    0.00    0.980     0.00 json.py:298(decode)
```

关键列：

- **ncalls**：调用次数
- **tottime**：函数自身耗时（不含子调用）
- **cumtime**：累计耗时（**含**子调用）——找瓶颈看这个
- 如果 `cumtime` 高但 `tottime` 低 → 问题在它调用的函数里，继续往下看
- `500 次 _connect` 耗时 1.09s → 连接没复用，应该用连接池！

**排序方式选择**：`tottime`（自身最慢）、`cumtime`（累计最慢）、`ncalls`（调用最多，常是优化目标）。

### 11.3 优化手段速查（从易到难）

```python
# 12-16_perf_demo.py
"""同一个任务的多种写法与性能对比。"""
import time
import sys


def bench(label: str, fn, n: int = 200_000):
    t = time.perf_counter()
    for _ in range(n):
        fn()
    print(f"  {label:32s} {(time.perf_counter() - t) * 1000:7.2f} ms")


if __name__ == "__main__":
    # ---------- 1) 循环内属性查找 → 局部变量 ----------
    def v1(data):
        r = []
        for x in data:
            r.append(x * 2)
        return len(r)

    def v2(data):
        append = r.append          # 提前绑定方法
        r = []
        for x in data:
            append(x * 2)
        return len(r)

    print("局部变量绑定:")
    data = list(range(1000))
    bench("for + append", lambda: v1(data), n=500)
    bench("for + 局部绑定 append", lambda: v2(data), n=500)

    # ---------- 2) 推导式 / 生成器 ----------
    print("\n构建容器:")
    def loop_build():
        out = []
        for i in range(10000):
            if i % 2 == 0:
                out.append(i * i)
        return out

    bench("for + if + append", loop_build, n=20)
    bench("列表推导式", lambda: [i * i for i in range(10000) if i % 2 == 0], n=20)

    # ---------- 3) 成员检查 ----------
    print("\n成员检查:")
    small = set(range(1000))
    bench("in list (1000)", lambda: 500 in list(range(1000)), n=20_000)
    bench("in set", lambda: 500 in small, n=20_000)      # O(1) vs O(n)
    # set 快几十倍是典型案例

    # ---------- 4) 字符串拼接 ----------
    print("\n字符串拼接:")
    parts = [f"part{i}" for i in range(1000)]
    bench("+= 拼接", lambda: "".join(p + "-" for p in parts), n=20)
    bench("join", lambda: "-".join(parts), n=20)         # 数量级差距

    # ---------- 5) 避免不必要的拷贝 ----------
    print("\n容器拷贝:")
    big = list(range(10000))
    bench("list(big)", lambda: list(big), n=2000)
    # 需要拷贝时才拷贝；只读就直接传引用

    # ---------- 6) 生成器：数据量大时省内存 ----------
    print("\n惰性求值:")
    bench("sum(list)", lambda: sum([x for x in range(100000)]), n=20)
    bench("sum(生成器)", lambda: sum(x for x in range(100000)), n=20)
    # 内存上生成器几乎为 0 成本（O(1) 空间）
```

**优化手段清单（按性价比排序）**

| 手段 | 原理 | 收益 | 可读性代价 |
|---|---|---|---|
| 改进算法复杂度 | O(n²)→O(n log n) | **百~万倍** | 需重新设计 |
| 用内置 C 实现 | `sum`/`sorted`/`any`/`itertools` | 10~100 倍 | 几乎无 |
| 用第三方加速库 | numpy / pandas / polars | 10~1000 倍 | 需学习 |
| 缓存计算结果 | `lru_cache` | 视重复率 | 轻微 |
| 批处理减少 I/O | `executemany` / 批量请求 | 10~100 倍 | 轻微 |
| 用 `map`/`filter`/推导式 | C 层迭代 | 1.2~3 倍 | 无 |
| 局部变量绑定 | 减少属性查找 | 1.1~1.3 倍 | 轻微 |
| 用生成器代替列表 | 省内存 | 内存胜 | 无 |
| 调整进程/线程 | 绕过 GIL | 视任务 | 架构级 |

### 11.4 常见性能反模式

| 反模式 | 问题 | 修正 |
|---|---|---|
| 在循环里 `append` 调 `len()` | O(n²) | 提前算好长度或用 `enumerate` |
| 循环内用 `in list` 检查成员 | O(n) → O(n·m) | `set` 或 `dict` |
| 循环内 `s += "x"` 拼字符串 | 每次新建对象，O(n²) | `''.join(list)` |
| 无条件 `list()` 包生成器 | 全量载入内存 | 直接迭代生成器 |
| 在热循环里用 `try/except` 做控制流 | 无异常时几乎免费，但别用来做普通分支 | 用 `if` |
| 缓存无界 | 内存无限增长 | `lru_cache(maxsize=...)` |
| 大量小对象 + 频繁创建 | GC 压力 | 用 `__slots__`、对象池 |
| I/O 在循环里串行 | 浪费并发 | `ThreadPoolExecutor`/`asyncio` |
| 重复计算相同表达式 | 浪费 CPU | `lru_cache` 或预计算 |
| 递归过深 | 栈溢出 | 改迭代或 `sys.setrecursionlimit` |
| 用 `sorted` 代替 `list.sort` | 额外拷贝 | `x.sort()` 原地排序 |
| `dict` 遍历中修改它 | `RuntimeError` | 遍历 `list(d.keys())` |
| 过度使用 `__getattr__` | 慢且难调试 | 显式属性 |
| 大量用 `dict` 代替类 | 失去类型检查和 IDE 提示 | `dataclass` |

```python
# 12-17_antipatterns.py
"""反模式示例：这些写法在数据量大时会出问题。"""

data = list(range(10_000))

# ❌ 反模式 1：循环内建列表做成员检查
def contains_slow(target):
    for _ in range(1000):
        if target in list(data):      # 每次都重建一个 10000 元素的列表！
            pass


# ✅ 修正：建一次集合
_index = set(data)
def contains_fast(target):
    for _ in range(1000):
        if target in _index:          # O(1)


# ❌ 反模式 2：+= 拼字符串
def concat_slow():
    s = ""
    for i in range(10_000):
        s += str(i)                  # 每次创建新字符串
    return len(s)


# ✅ 修正：join
def concat_fast():
    return len("".join(str(i) for i in range(10_000)))


# ❌ 反模式 3：无界缓存
_cache = {}
def unbounded_cache(n):
    if n not in _cache:
        _cache[n] = n ** 2           # 永远不清理
    return _cache[n]


# ✅ 修正：用 lru_cache
import functools
@functools.lru_cache(maxsize=128)
def bounded_cache(n):
    return n ** 2


# ✅ __slots__ 省内存（大量小对象时）
class Point:
    __slots__ = ("x", "y")           # 不能有 __dict__，省 50%+ 内存
    def __init__(self, x, y):
        self.x, self.y = x, y


if __name__ == "__main__":
    import time
    t = time.perf_counter(); contains_slow(500); print(f"contains_slow: {(time.perf_counter()-t)*1000:.1f} ms")
    t = time.perf_counter(); contains_fast(500); print(f"contains_fast: {(time.perf_counter()-t)*1000:.1f} ms")
    # contains_slow 会慢几个数量级
```

### 11.5 优化前的检查清单

在动手改代码之前，先问自己：

1. **瓶颈真的在 Python 代码里吗？** 用 `py-spy top` 看一眼，可能 90% 时间在等数据库。
2. **是算法问题还是实现问题？** O(n²) 改 O(n) 是本质改进；微优化只是 20%。
3. **数据量到底多大？** 处理 100 条记录和 100 万条，优化收益天差地别。
4. **有现成的库吗？** numpy/pandas/polars/requests 往往比手写快一个数量级。
5. **这个优化会不会让代码难懂太多？** 收益 5% 但可读性大跌 → 不值得。
6. **优化后有基准测试证明吗？** 没有测量就没有优化。
7. **是不是可以用更强的机器解决？** 并行/升配可能比改代码划算。

## 本节小结

- **风格**：PEP 8 定 4 空格、79/100 列；命名遵循 snake_case / CapWords / UPPER_CASE 约定。
- **工具链**：`ruff`（lint + format，快如闪电）+ `mypy`（类型检查）+ `pre-commit`（提交时自动执行）。别再手动检查代码风格。
- **测试**：`pytest` 是首选；`fixture` 实现分层复用，`parametrize` 覆盖多组输入，`mock`/`monkeypatch` 隔离外部依赖，`conftest.py` 是魔法文件。覆盖率看分支、别刷数字。
- **Git**：短生命周期分支 + Conventional Commits + PR Review；一个提交只做一件事。
- **配置**：默认值 → `.env` → 环境变量 → 命令行，逐层覆盖；**绝不提交 `.env`**，只提交 `.env.example`。
- **依赖**：`uv` 或 `pip-tools` 生成锁文件并提交，保证可复现；生产用 `uv sync --frozen`。

- **文档**：docstring 写"是什么 + 为什么"，README 提供 5 分钟上手路径，必备 LICENSE/CONTRIBUTING。

- **性能**：先测量再优化；`cProfile` 找热点，`py-spy` 排查线上；优先改算法复杂度，其次用内置/第三方库，最后才微优化。

## 自测题

1. 为什么 ruff 能替代 flake8 + black + isort？如何配置让 ruff 在 `pre-commit` 时自动修复并检查？

<details>
<summary>参考答案</summary>

ruff 用 Rust 编写，单个二进制，速度是传统 Python linter 的 10~100 倍，同时集成三大工具的能力：

- **lint**（≈ flake8 + pylint + pycodestyle + pyupgrade）
- **format**（≈ black，兼容其绝大多数风格）
- **import 排序**（isort）

配置：

```toml
# pyproject.toml
[tool.ruff.lint]
select = ["E", "W", "F", "I", "N", "UP", "B", "SIM"]
```

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.0
    hooks:
      - id: ruff
        args: [--fix, --exit-non-zero-on-fix]
      - id: ruff-format
```

`--fix` 自动修复可修的问题；`--exit-non-zero-on-fix` 保证「虽然被修了但仍要中止提交」，让开发者在提交前 review 改动。注意不要同时启用 black 和 `ruff format`，两者会互相打架。

</details>

2. `fixture` 的 scope 有哪些？它们的区别是什么？什么时候该用 session 级 fixture？

<details>
<summary>参考答案</summary>

四种 scope：

| scope | 生效范围 | 执行次数 |
|---|---|---|
| `function`（默认） | 每个测试函数 | 每次都新建 |
| `class` | 每个测试类 | 每个类一次 |
| `module` | 每个测试模块 | 每个文件一次 |
| `package` | 每个包 | 每个包一次 |
| `session` | 整个测试会话 | **全程一次** |

用 session 级 fixture 的场景：**初始化代价极高、且全程只读共享**的东西——数据库容器启动、加载大型模型/数据集、构建一次连接池。

```python
@pytest.fixture(scope="session")
def docker_db():
    container = start_postgres_container()   # 慢，约 5-10s
    yield container
    container.stop()
```

不适合 session 级的：返回可变对象且测试会修改它的 fixture（比如 `sample_user` dict）——测试间会互相污染，此时必须用 function 级。

依赖规则：高 scope 的 fixture **不能**依赖低 scope 的 fixture（会造成隐式的函数级重置）。

</details>

3. 为什么说「测试覆盖率 100% 不代表代码正确」？你会怎么设计一个有意义的测试策略？

<details>
<summary>参考答案</summary>

**为什么 100% 不够**

1. **覆盖 ≠ 验证**：执行到一行代码不代表断言了正确结果。
   ```python
   def test_useless():
       calculate(1, 2)          # 有覆盖率，断言呢？
   ```
2. **断言方向错误也算覆盖**：代码执行 `return a - b`，测试断言 `result is not None`，通过了但逻辑是错的。
3. **缺少负向测试**：只测了 happy path，没测边界（空列表、0、负数、超长输入）、异常路径。
4. **缺少集成测试**：单元测试全绿，但模块间协作时序/事务/编码出错。
5. **分支覆盖缺口**：`if` 只测了 True 分支，覆盖率工具可能因语句计数而不报缺失。
6. **测试自己可能有 bug**（复制粘贴错误、双向断言）。

**有意义的策略**

1. **测试金字塔**：大量快速单元测试 + 适量集成测试 + 少量端到端测试。
2. **先写测试（至少核心逻辑 TDD）**，因为事后补的测试会"验证实现"而非"验证需求"。
3. **重点覆盖**：核心业务逻辑、边界条件、所有异常分支、回归 bug（先写一个失败的测试复现 bug，再修）。
4. **用参数化**把等价类一次覆盖：`0/1/-1/超大值/空/None`。
5. **关注分支覆盖率**：`pytest --cov-branch`，比语句覆盖率信息量大。
6. **变异测试**验证测试强度：`mutmut` 会故意改坏代码，如果测试全过说明断言不够强。
7. 把 `fail_under` 设在 70~85%，别硬刷 100%。
8. **CI 阻断**：覆盖率下降必须有意识地决定，而不是被数字绑架。

</details>

4. 为什么 `set` 的成员检查比 `list` 快那么多？如何把一个 O(n) 的查找优化到 O(1)？

<details>
<summary>参考答案</summary>

**原理**

- `list` 用**连续内存数组**存储，内部靠连续布局实现 O(1) 下标访问。检查 `x in list` 必须从头逐个比较，**O(n)**。
- `set` 基于**哈希表**：元素按 `hash(value)` 定位到桶，直接比较/计算，**期望 O(1)**。

极端情况：`set` 遇到大量哈希冲突（如整数哈希碰撞）会退化，但 CPython 有开放寻址 + 随机扰动保护，通常不会成为问题。

**优化方法**

```python
data = [3, 1, 4, 1, 5, 9, 2, 6]

# ❌ O(n) 每次循环
for x in big_list:
    if x in some_list:      # 1000 × 10000 = 1000 万次比较
        ...

# ✅ O(1)
index = set(some_list)     # 一次构建 O(n)
for x in big_list:
    if x in index:          # 1000 次哈希查找
        ...
```

前提：list 元素必须**可哈希**（不可变类型）。若元素是 list/dict，就没法建 set。

同理，`dict` 用于"存在性 + 取值"：

```python
counts = {}
for word in words:
    counts[word] = counts.get(word, 0) + 1     # O(1)，比 in + 索引快
# 或直接用 Counter
from collections import Counter
counts = Counter(words)                          # C 实现，最快
```

</details>

5. 为什么不能把 `.env` 提交到仓库？`.env` 和环境变量到底是什么关系？

<details>
<summary>参考答案</summary>

**不能提交的原因**

1. `.env` 里存的是**密钥和凭据**：`SECRET_KEY`、数据库密码、API Token、第三方云 AK/SK。一旦提交进 Git 历史，即使后来删除文件，**历史记录里依然可被检索到**（`git log -p` 或 GitHub 的 commit diff 都能看到）。清理历史的代价极高（要 `git filter-repo` 并强制推送，所有协作者必须重新 clone）。
2. 不同环境（本地 / CI / 预发 / 生产）的配置不同，提交会导致**环境差异无法通过配置解决**，违背"代码与环境分离"。
3. 泄露的凭据可能被自动爬虫扫到并滥用。

**正确做法**

1. `.env` 加入 `.gitignore`。
2. 提供 `.env.example`（只有键名、无真实值，或值是占位符）提交到仓库，告诉别人需要配什么。
3. 生产/共享环境由**部署平台注入环境变量**（K8s Secret、Docker `--env-file`、CI 的 secrets、平台控制台）。

**两者的关系**

`.env` **不是**标准机制，它只是一个"文本文件形式的键值对"，需要工具（如 `python-dotenv`）在启动时读取并写入 `os.environ`：

```
优先级：真实环境变量 > .env 文件 > 代码默认值
```

所以本地开发用 `.env` 方便，服务器上直接设真实环境变量——**代码读的都是 `os.environ`**，来源对调用方透明。这就是「配置与代码分离」。

</details>

6. 什么是「构建一次，到处运行」？为什么不能在每个环境重新构建 Docker 镜像？

<details>
<summary>参考答案</summary>

**含义**：把源码编译成**唯一的一个不可变产物**（Docker 镜像 / wheel 包 / 二进制），然后把这个**同一份产物**逐级推送到测试环境、预发环境、生产环境。它对每个环境来说完全相同，只有运行时配置（环境变量）不同。

**为什么不能每环境重建**

1. **不保证一致**：不同机器、不同时间构建，基础镜像 digest、依赖解析结果、时间戳都可能不同——本地能跑、线上崩的经典原因。
2. **太慢**：每次构建要几分钟到几十分钟，多环境叠加就是几小时。
3. **无法回滚**：如果不知道线上跑的是哪个产物，出问题无法精确回退。
4. **可审计性差**：无法回答"生产上跑的是哪版代码、哪个 commit"，因为没有可追溯的产物标识。
5. **构建不等于部署**：构建成功只说明能编译，测试通过才说明能用。每环境重建等于每环境都在做"未经测试的改动"。

**实现要点**

- CI 统一构建一次：`docker build -t registry/app:git-sha-123 .`
- 推送镜像仓库，各环境只做 `docker pull` + 启动
- 用 commit SHA 或版本号作为 tag（**不要用 `latest`**，无法追溯）
- 环境差异全部走环境变量 / ConfigMap / Secret

</details>

7. 用 cProfile 分析你的程序，`tottime` 和 `cumtime` 分别表示什么？看到某个函数 cumtime 很高但 tottime 很低说明什么？

<details>
<summary>参考答案</summary>

```bash
python -m cProfile -s cumtime your_script.py
```

- **tottime**：函数体自身消耗的时间，**不包含**它调用的其他函数。
- **cumtime（cumulative）**：函数体自身 + 所有被调用函数的累计时间。

**cumtime 高但 tottime 低说明什么**

这个函数本身写得很快（CPU 没花在自己身上），但它**调用的下游函数很慢**。例如：

```
   ncalls  tottime  cumtime  filename:lineno(function)
      500    0.021    1.234    process.py:45(process_data)
      500    0.002    1.100    db.py:22(execute)      <- 瓶颈在这里
     5000    0.450    0.980    json.py:298(decode)
```

解读流程：

1. 先按 `cumtime` 排序找到最耗时的顶层函数（`process_data` 累计 1.234s）。
2. 看它 `tottime` 只有 0.021s → 说明**它自己不是瓶颈**，问题在它调用的东西。
3. 沿调用链往下找 `cumtime` 最高且 `tottime` 也高的那一层（这里是 `json.decode`：tottime 0.45s）。
4. 针对性优化——比如把 500 次独立的 JSON 解码改成批量、或换成更快的解析库。

反之，如果一个函数 **tottime 很高而 cumtime ≈ tottime**（没调用耗时的东西），那就是它自己的算法/实现有问题，应该考虑改算法复杂度或换实现。

</details>

8. 你的服务 P99 延迟从 20ms 突然涨到 2s，用 cProfile 分析发现时间主要花在 `sqlalchemy` 的连接创建上。你会怎么改？

<details>
<summary>参考答案</summary>

`cProfile` 显示时间在连接创建，说明是 **N+1 式建连**问题——每次查询都新开连接，TCP 握手 + TLS + 认证的开销远超实际查询。

**修改方案**

1. **引入连接池**（这是根治手段）：

```python
from sqlalchemy import create_engine

engine = create_engine(
    DATABASE_URL,
    pool_size=20,           # 常驻连接数（注意别超过数据库 max_connections）
    max_overflow=10,        # 超出时临时新建的上限
    pool_timeout=30,        # 池满时等待秒数，超时抛异常
    pool_recycle=1800,      # 30 分钟回收，防止 MySQL 的 wait_timeout 断连
    pool_pre_ping=True,     # 取连接前 ping，检测已失效连接
    echo=False,             # 生产环境别开 SQL 日志！
)
```

2. **会话级作用域**：把 `sessionmaker(bind=engine)` 作为 FastAPI/Flask 的依赖或请求级上下文，不要在业务函数里新建 session。

3. **修 N+1 查询**：真正的问题往往不是建连慢，而是循环里逐条查询。用 `selectinload` / `joinedload` 预加载，或改成批量 `IN` 查询。

4. **加缓存**：热点只读数据加 Redis 或 `functools.lru_cache`，直接避开数据库。

5. **加观测**：给连接池加 `pool` 指标监控（`pool_checkout`、`pool_size`），设连接数告警；打开 `pool_logging_name` 便于定位。

6. **验证**：`pool_pre_ping=True` 后连接失效会静默重建，不再出现 "server has gone away"；`pool_recycle` 防止长时间空闲后第一次请求变慢（这也是 P99 突然涨的常见诱因——空闲连接被数据库单方面关闭，重建时集中爆发）。

</details>
