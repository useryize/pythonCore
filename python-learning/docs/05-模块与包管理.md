## 一、模块（module）是什么

在 Python 里，**一切皆对象**，而**模块就是包含 Python 代码的 `.py` 文件**。模块的作用是：

- **拆分**：把上千行代码拆成若干可维护的文件。
- **复用**：同一个模块可以被多个项目反复使用。
- **隔离**：模块各自拥有独立的全局命名空间。

标准库本身就是几百个模块组成的（`os.py`、`json.py`、`csv.py`……），第三方库也是同样的组织方式。

一个最小模块 `math_tools.py`：

```python
# math_tools.py
"""一组数学小工具。"""

PI = 3.14159

def add(a, b):
    """返回 a + b。"""
    return a + b

def sub(a, b):
    """返回 a - b。"""
    return a - b

VERSION = "1.0.0"
```

### 1.1 模块的三个特殊属性

| 属性 | 含义 | 典型用途 |
| --- | --- | --- |
| `__name__` | 模块名（导入时为点分路径，直接运行时为 `"__main__"`） | 主程序入口判断 |
| `__file__` | 模块源文件路径 | 定位资源文件 |
| `__doc__` | 模块文档字符串 | `help()` 输出 |

```python
# demo.py
import math_tools
print(math_tools.__name__)   # 预期输出: math_tools
print(math_tools.__file__)   # 预期输出: .../math_tools.py
print(math_tools.__doc__)    # 预期输出: 一组数学小工具。
```

## 二、三种导入语法

```python
import math_tools                    # 导入模块本身
from math_tools import add, sub      # 从模块中导入名字
from math_tools import add as plus   # 导入并重命名
import math_tools as mt              # 模块重命名
import os.path                       # 点号导入：绑定 os，os.path 可用
from os import path                  # 只导入 path 这个名字
```

### 2.1 关键差异：命名空间里多出了什么

```python
import math_tools
print(add)            # NameError! add 没有被导入到当前命名空间
print(math_tools.add)  # OK

from math_tools import add
print(add)            # OK，add 直接可用
print(math_tools)     # 除非同时 import 了，否则 NameError
```

面试常考点：**`import a.b` 不会把 `b` 这个名字引入当前作用域**。

```python
import os.path
# 上面等价于 import os，然后 os.path 作为属性存在

print(os.path.join("a", "b"))   # 预期输出: a\b  (Windows) 或 a/b (POSIX)
```

### 2.2 `import` 的三种底层行为

```python
import a.b.c
```

1. 检查 `sys.modules` 里是否已有 `a.b.c`；
2. 若无，先递归导入父包 `a`、`a.b`；
3. 执行模块代码（**只执行一次**，结果缓存）；
4. 把模块对象绑定到当前命名空间的 `a` 上。

关键推论：**模块只会被执行一次**。重复 import 不会重复执行模块顶层代码。

```python
# counter.py
print("模块被加载了")
count = 0
```

```python
# test_reimport.py
import counter
import counter
import counter
# 预期输出（只有一行）:
# 模块被加载了
```

### 2.3 `import *` 为什么不推荐

```python
from math_tools import *   # 不推荐
```

问题：

- 污染命名空间，名字来源不可控；
- 覆盖当前模块已有名字；
- 静态分析工具（pyflakes）难以追踪；
- PEP 8 明确建议避免。

即使要用，也要用 `__all__` 明确导出哪些名字（见下文包部分）。

## 三、模块搜索路径 `sys.path`

Python 导入一个模块时，会**按顺序**在 `sys.path` 的每个目录里查找。

```python
import sys
for i, p in enumerate(sys.path):
    print(i, p)
```

典型输出（各平台略有不同）：

```
0                 # 当前脚本所在目录（注意：是脚本目录，不是 cwd！）
1 /usr/lib/python312.zip
2 /usr/lib/python3.12
3 /usr/lib/python3.12/lib-dynload
4 .../site-packages        # 第三方库安装位置
```

### 3.1 查看模块从哪来

```python
import json
print(json.__file__)      # 该模块的实际路径
```

### 3.2 sys.path 规则与常见坑

1. **首项是脚本所在目录**。所以 `python sub/main.py` 时，`sub` 目录里的模块找不到，必须改成项目根目录运行 `python -m sub.main`。
2. **当前工作目录不是自动加入的**（首项是脚本目录）。交互式解释器里首项是空字符串 `''`，代表 cwd。
3. **不要用 `sys.path.append()` hack**，一旦多个项目都有同名模块就会互相污染。

```python
# 反例（生产环境禁止）
import sys
sys.path.append("/home/me/myproject/lib")
import utils     # 别人电脑上没有这个路径，导入直接失败
```

### 3.3 临时修正的正确做法

```python
import sys, os
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
```

但更推荐的是**使用包 + `python -m`**：

```bash
python -m myproject.cli      # 此时 sys.path[0] 是当前目录，导入稳定
```

### 3.4 PYTHONPATH 环境变量

```bash
PYTHONPATH=/opt/mylibs python main.py    # Linux/macOS
set PYTHONPATH=C:\mylibs                 # Windows CMD
$env:PYTHONPATH="C:\mylibs"             # PowerShell
```

`PYTHONPATH` 会被插入到 `sys.path` 靠前的位置。

## 四、自定义模块与包

### 4.1 单文件模块

新建 `myapp/calc.py`：

```python
# myapp/calc.py
def add(a, b):
    return a + b
```

同级目录新建 `main.py`：

```python
# main.py
from myapp.calc import add
print(add(1, 2))   # 预期输出: 3
```

运行方式（两种都能工作，但推荐第二种）：

```bash
cd myapp
python main.py          # 可以
cd ..
python -m myapp.main   # 推荐，更稳定
```

### 4.2 包（package）

包 = **一个目录** + `__init__.py`。`__init__.py` 的存在让 Python 把该目录识别为包（Python 3.3+ 之后即使没有也能作为命名空间包导入，但**强烈建议保留 `__init__.py`**）。

结构：

```
myapp/
├── __init__.py
├── calc.py
└── utils/
    ├── __init__.py
    └── text.py
```

`myapp/__init__.py`：

```python
"""myapp 包的入口。"""

__version__ = "1.0.0"

from .calc import add          # 相对导入，把名字暴露到包顶层

__all__ = ["add", "__version__"]
```

`myapp/utils/__init__.py`：

```python
from .text import slugify
__all__ = ["slugify"]
```

这样使用：

```python
import myapp
print(myapp.__version__)   # 预期输出: 1.0.0
print(myapp.add(1, 2))     # 预期输出: 3

from myapp.utils import slugify
print(slugify("Hello World"))   # 预期输出: hello-world
```

### 4.3 `__init__.py` 到底该写什么

原则：**尽量轻**。

| 该做 | 不该做 |
| --- | --- |
| 定义包级常量（`__version__`） | 重量级计算 |
| 导入并汇总常用子模块名字 | 大量 import（拖慢启动） |
| 用 `__all__` 声明公开 API | 执行 I/O、启动服务 |
| 提供包级函数 | 引入不必要的第三方依赖 |

反面案例的典型症状是 `import myapp` 要等 3 秒，因为 `__init__.py` 里 `import torch`。

### 4.4 绝对导入 vs 相对导入

```python
# 绝对导入：从项目根出发，清晰，推荐
from myapp.utils.text import slugify

# 相对导入：从当前包出发，限制在包内部（只能在包内使用）
from .text import slugify          # 同级模块
from ..utils import slugify        # 上一级包
from ...top import thing           # 上上级
```

- `.` = 当前包
- `..` = 父包
- `...` = 祖父包

面试常考点：**相对导入只能用在包内**。直接 `python calc.py` 执行一个用相对导入的模块会报 `ImportError: attempted relative import with no known parent package`。

### 4.5 导入路径不要跨越包边界

```python
# 错误：不要这样在包内导入其他包的"私有"模块
from ..other_pkg.internal import thing
```

如果确实需要共享，应该把 `thing` 提升到公共包（如 `myapp/common/`），由两边共同导入。这能避免包之间的隐性耦合。

### 4.6 模块与包的导入性能小知识

```python
import math          # 内置模块，走 C 实现，秒级导入
import myapp.utils   # 纯 Python 包，会执行 __init__.py 和各子模块
```

如果只是要一个常量，可以考虑把它放在包的 `__init__.py` 或单独的轻量模块里，避免拖慢启动。大项目里 `import torch` 动辄几秒就是典型例子。

## 五、`if __name__ == "__main__"`

直接运行文件时 `__name__ == "__main__"`；被导入时 `__name__ == "myapp.calc"`。

```python
# demo_main.py
def main():
    """真正的入口函数。"""
    print("程序开始运行")

if __name__ == "__main__":
    main()
```

为什么要这么写（**面试高频题**）：

1. 直接 `python demo_main.py` 时会执行 `main()`，程序能跑。
2. 被 `import demo_main` 时**不会**自动执行 `main()`，只提供函数定义，避免了"导入即运行"的副作用。

更好的写法是**先定义、后判断、把逻辑收进 `main()`**：

```python
def parse_args():
    return "hello"

def main():
    print(parse_args())

if __name__ == "__main__":
    main()
```

### 5.1 `python -m module` 的差异

```bash
python demo_main.py
# __name__ == "__main__"，sys.path[0] = demo_main.py 所在目录

python -m demo_main
# __name__ == "__main__"，sys.path[0] = 当前工作目录
```

差异 2：`python -m` **不会**把包自身的目录加进 `sys.path`，因此能更准确地暴露"你用了裸导入而不是相对导入"的问题。

## 六、循环导入

### 6.1 问题复现

```
app/
├── __init__.py
├── a.py       # from app.b import B
├── b.py       # from app.a import A
└── main.py    # import app.a
```

```python
# a.py
from app.b import B

class A:
    def __init__(self):
        self.b = B()
```

```python
# b.py
from app.a import A

class B:
    def __init__(self):
        self.a = A()
```

`python -m app.main` 时报：

```
ImportError: cannot import name 'B' from partially initialized module 'app.b' (most likely due to a circular import)
```

原因：导入 `app.a` → 执行 `from app.b import B` → 开始导入 `app.b` → 执行 `from app.a import A`，但此时 `app.a` 还在执行中、还没定义 `A`，于是失败。

### 6.2 四种解法（按推荐程度排序）

**解法一：把导入下沉到函数内部（最常用、最有效）**

```python
# a.py
class A:
    def create_b(self):
        from app.b import B   # 延迟导入，执行到这里才导入
        return B()
```

原理：把"导入时机"推迟到真正需要的时候，此时两个模块都已加载完毕。标准库 `importlib`、`matplotlib.pyplot` 都这么干。

**解法二：使用 TYPE_CHECKING 避免运行期循环依赖**

```python
# a.py
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    from app.b import B     # 只在类型检查时导入，运行期不执行

class A:
    def make(self):
        from app.b import B
        return B()
```

**解法三：合并模块**

如果 A 和 B 强耦合又互相引用，说明它们本来就是一个内聚单元，直接合并进同一个模块，从根本上消除循环。

**解法四：重构依赖方向**

```
重构前:  a → b → a          （环）
重构后:  a → b → c          （无环，c 是底层）
```

把公共部分下沉成第三个模块 `common.py`，让依赖变成单向。

### 6.3 排查循环导入的小技巧

```bash
python -X importtime -m app.main 2> importtime.log   # 查看导入耗时，找出重模块
python -v -m app.main                             # 打印每次 import 的完整过程
```

或直接在模块顶部加 `print(__name__, "开始")` / `print(__name__, "结束")`，跑一遍看顺序即可定位环。

## 七、项目目录结构规范

一个常见的现代 Python 项目布局：

```
myproject/
├── pyproject.toml          # 项目元数据 + 依赖 + 构建配置（现代标准）
├── README.md
├── .gitignore
├── .env.example
├── src/                    # 源码放 src 下，避免"测试代码被意外导入"
│   └── myapp/
│       ├── __init__.py
│       ├── __main__.py     # 支持 python -m myapp
│       ├── cli.py
│       ├── config.py
│       ├── core/
│       │   ├── __init__.py
│       │   └── engine.py
│       └── utils/
│           ├── __init__.py
│           └── text.py
├── tests/
│   ├── test_engine.py
│   └── conftest.py
├── docs/
└── scripts/
```

### 7.1 为什么用 `src/` 布局

1. **防止"偷导入"**：测试时 `import myapp` 只会命中安装后的包，不会误命中当前目录的源码。
2. 与 setuptools / uv / hatch 的默认行为一致。
3. 让项目根目录保持干净，只有配置和文档。

### 7.2 `src` 布局下的运行方式

```bash
# 方式一：先安装再运行（推荐）
pip install -e .
python -m myapp

# 方式二：开发期临时设置
PYTHONPATH=src python -m myapp

# 方式三：uv（会自动处理）
uv run python -m myapp
```

### 7.3 `pyproject.toml` 最小示例

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "myapp"
version = "0.1.0"
description = "一个示例项目"
requires-python = ">=3.10"
dependencies = [
    "requests>=2.31",
]

[project.scripts]
myapp = "myapp.cli:main"     # 安装后可直接在命令行敲 myapp

[project.optional-dependencies]
dev = ["pytest", "ruff", "mypy"]
```

用 `pip install -e ".[dev]"` 即可安装开发依赖。

## 八、标准库 vs 三方库

### 8.1 判断优先级

1. **标准库能做 → 用标准库**（零依赖、永远可用）。
2. 标准库做不了且很复杂 → 找成熟的三方库。
3. 只有极特殊性能/业务需求 → 自己写。

| 需求 | 标准库方案 | 常见三方库 |
| --- | --- | --- |
| HTTP 请求 | `urllib.request` | `requests`, `httpx` |
| 日期时间 | `datetime` | `arrow`, `pendulum` |
| 数据校验 | `dataclasses` + 手写 | `pydantic` |
| CLI 解析 | `argparse` | `click`, `typer` |
| 测试 | `unittest` | `pytest` |
| 虚拟环境 | `venv` | `uv`, `poetry` |
| 格式美化 | `json.tool` | `black`, `ruff format` |
| 静态检查 | — | `ruff`, `pylint`, `mypy` |

### 8.2 判断第三方库好不好用

- 最近 6 个月是否有更新；
- 文档与类型标注是否完整；
- 下载量与 issue 响应速度；
- 依赖树是否干净（`pip show <pkg>` 看 `Requires`）；
- 是否符合标准库已有能力。

## 九、打包与依赖工具

### 9.1 setuptools（老牌标准）

历史上 Python 的事实标准，基于 `setup.py` 或 `setup.cfg`。现代项目一般通过 `pyproject.toml` 声明：

```bash
pip install setuptools wheel
python -m build            # 产出 dist/*.whl 和 *.tar.gz
pip install dist/myapp-0.1.0-py3-none-any.whl
pip show myapp             # 查看安装了哪些文件
```

### 9.2 uv（新一代，推荐）

Rust 编写，比 pip 快一到两个数量级。

```bash
# 安装
pip install uv            # 或 curl -LsSf https://astral.sh/uv/install.sh | sh

# 创建项目（自动生成 src 布局 + pyproject.toml）
uv init myproject --package

# 添加依赖（同时更新 pyproject.toml 和 uv.lock）
uv add requests
uv add --dev pytest ruff

# 同步环境
uv sync

# 运行
uv run python -m myapp
uv run pytest

# 安装为脚本
uv tool install ruff
```

亮点：自动管理虚拟环境、支持 Python 版本锁定、`uv.lock` 保证全团队一致。

### 9.3 hatch（现代构建后端）

```bash
pip install hatch
hatch new myproject         # 生成项目
hatch build                 # 构建
hatch run test              # 定义好的环境任务
```

也在 `pyproject.toml` 里作为构建后端使用：

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

### 9.4 三者如何选择

| 场景 | 建议 |
| --- | --- |
| 学习、写脚本 | `venv` + `pip` 足够 |
| 个人项目 | `uv`（依赖 + 环境 + 运行一体） |
| 要发布到 PyPI 的库 | `hatchling` 或 `setuptools` 作为构建后端 |
| 维护既有 setup.py 老项目 | 继续 setuptools，逐步迁移到 pyproject.toml |

## 十、导入相关常见面试题速答

1. **`from a import b` 和 `import a` 的区别？**
   前者把 `b` 直接绑定到当前作用域；后者只绑定 `a`，需写 `a.b`。

2. **模块被执行几次？** 一次。`sys.modules` 缓存模块对象。

3. **修改导入结果的方法？** 修改 `sys.modules['a.b'] = fake_obj`，或设置 `a.b = fake_obj`。测试里常用 monkeypatch。

4. **如何查看某个名字从哪里导入？**
   ```python
   import inspect, os
   print(inspect.getfile(os.path.join))
   ```

5. **`import a.b` 后 `b` 在当前命名空间吗？** 不在，只有 `a`。要用 `a.b`。

6. **`__init__.py` 可以为空吗？** 可以，但建议至少写 docstring 和 `__all__`。

7. **为什么相对导入不能在直接运行的脚本里用？** 因为脚本不是包的一部分，没有父包上下文。

8. **`python -m` 和 `python file.py` 有什么区别？**
   `sys.path[0]` 分别是当前目录和脚本目录；前者更利于包内相对导入和跨平台行为一致。

9. **循环导入怎么排查？**
   `python -v` 打印导入过程，或在模块首尾加打印观察进入顺序。

10. **`__all__` 的作用？**
    声明 `from x import *` 时导出哪些名字；同时被 IDE 当作公开 API 的依据。

## 本节小结

- 模块即 `.py` 文件，模块只被执行一次，缓存在 `sys.modules`。
- 三种导入语法的区别在于"往当前命名空间绑定哪个名字"。
- `sys.path` 决定去哪里找模块，首项是脚本目录；生产代码不要用 `sys.path.append` hack，用包和 `python -m`。
- 包 = 目录 + `__init__.py`；`__init__.py` 要轻，只放元数据与公开 API 汇总。
- 相对导入（`.`/`..`）只能在包内使用，且不要跨越包边界。
- `if __name__ == "__main__":` + `main()` 函数是所有可执行脚本的标准写法。
- 循环导入有四种解法：函数内延迟导入、TYPE_CHECKING、合并模块、重构依赖方向；**延迟导入是最常用的**。
- 项目用 `src/` 布局 + `pyproject.toml` 管理；工具链上 `uv` 值得优先学习。

## 自测题

<details>
<summary>1. 为什么把 `sys.path.append('/some/path')` 写进项目代码是坏习惯？给出更好的方案。</summary>

**答案：**
`sys.path.append` 依赖特定机器上的绝对路径，别人克隆代码后该路径不存在，导入直接失败；且一旦有同名模块，多项目互相污染；静态工具也无法追踪。

更好方案：
1. 把代码组织成包（目录 + `__init__.py`）；
2. 用 `pip install -e .` 或 `PYTHONPATH=src` 安装/配置；
3. 用 `python -m` 运行，让包内相对导入生效；
4. 使用 `uv` 等工具自动处理路径。
</details>

<details>
<summary>2. `import a.b` 和 `from a import b` 有何区别？`from a import b` 什么时候会失败？</summary>

**答案：**
- `import a.b`：导入 `a` 及其子模块 `a.b`，但当前命名空间只多出 `a`，使用要写 `a.b`。
- `from a import b`：只把 `b` 绑定到当前命名空间，`b` 是 `a.b` 中存在的名字。

失败情况：
1. `a` 内部不存在名为 `b` 的属性（子模块未导入、或名字拼错）；
2. `a/__init__.py` 中 `from .b import ...` 时如果该子模块因循环导入尚未完成，`b` 属性还不存在。
</details>

<details>
<summary>3. 写出 a.py 与 b.py 互相导入产生 ImportError 的最简例子，并给出两种解法。</summary>

**答案：**

```python
# a.py
from b import B
class A:
    pass
```
```python
# b.py
from a import A
class B:
    pass
```
```python
# main.py
import a   # ImportError: cannot import name 'A' from partially initialized module 'a'
```

解法一：延迟导入到函数内部
```python
# a.py
class A:
    def make(self):
        from b import B
        return B()
```
解法二：下沉公共部分，合并成同一模块，或把公共类型放到 `common.py` 让依赖单向。
</details>

<details>
<summary>4. `if __name__ == "__main__":` 解决了什么问题？如果去掉会怎样？</summary>

**答案：**
区分"直接运行该文件"与"被导入"。直接运行时 `__name__` 为 `"__main__"`，执行 `main()`；被导入时为模块路径名，不执行 `main()`。

若去掉，被别的模块导入时就会立即执行顶层代码，产生副作用（例如发请求、读文件、启动服务），使模块无法安全复用，也难以测试。
</details>

<details>
<summary>5. 为什么推荐 `src/` 布局而不是把包直接放项目根目录？</summary>

**答案：**
1. 防止"偷导入"：测试中 `import myapp` 只会命中已安装的包，不会误命中源码目录，导致测试的不是真正安装的代码；
2. 项目根目录干净，只放配置与文档；
3. 与 setuptools / hatch / uv 的默认约定一致；
4. 避免模块被脚本目录污染，多个项目嵌套时不易冲突。
</details>

<details>
<summary>6. 什么是模块搜索路径？如何让 `myapp` 里的 `myapp/utils/__init__.py` 中的 `from .text import slugify` 生效？</summary>

**答案：**
`sys.path` 是一个目录列表，Python 按顺序在其中查找待导入的模块/包（首项是运行脚本所在目录，交互式环境为空串即 cwd）。

要让相对导入生效：
1. `utils` 必须属于一个包：路径为 `myapp/utils/__init__.py`；
2. 必须以包的方式被导入，即 `from myapp.utils.text import slugify`，而不是直接 `python utils/__init__.py`；
3. 项目根目录要在 `sys.path` 中（`pip install -e .`、`PYTHONPATH=.` 或 `python -m myapp.cli`）。
</details>

<details>
<summary>7. `__init__.py` 里应该写什么、不该写什么？为什么？</summary>

**答案：**
该写：模块 docstring、`__version__` 等包级常量、`__all__`、常用子模块名字的重导出。
不该写：重量级计算、大量 import、I/O 操作、启动服务、引入重型第三方依赖。

原因：`import myapp` 会执行 `__init__.py`，这里的内容影响所有导入该包的地方，写得越重，启动越慢，且副作用难以控制。导入应保持轻量。
</details>

<details>
<summary>8. `python -m myproject.cli` 与 `python myproject/cli.py` 在导入行为上有什么区别？</summary>

**答案：**
1. `sys.path[0]`：`-m` 是当前工作目录，直接运行文件时是 `cli.py` 所在目录 `myproject/`。
2. `-m` 会先把包 `myproject` 导入，并把 `__name__` 设为 `"__main__"`，支持相对导入；直接运行文件时没有包上下文，`from . import x` 会报"attempted relative import"。
3. `-m` 不会把包自身的 `__init__.py` 所在目录当脚本目录，减少同名模块误导入风险。
</details>
