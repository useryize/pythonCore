# 01 · 环境与工具链

> 面向零基础。目标是把「能写代码」变成「能稳定、舒服地写代码」。这一节不产出业务代码，但它是后面每一节能否跑起来的地基。

## 学习目标

学完本节，你应该能够：

1. 在 Windows 上安装 Python，并把 `python` / `pip` 加入 PATH。
2. 独立创建、使用、删除 `venv` 虚拟环境，养成「一个项目一个环境」的习惯。
3. 用 `pip` 安装包、查看包、卸载包，并理解 `requirements.txt` 与 `pyproject.toml` 各自解决什么问题。
4. 配置 VS Code，选对解释器，装上真正有用的插件。
5. 用三种方式运行 Python 代码（交互式、脚本、VS Code 运行）。
6. 独立排查三大高频环境问题：PATH 报错、`ModuleNotFoundError`、中文乱码。
7. 理解虚拟环境本质上是「一个装了独立包目录的 Python 解释器」。

## 1. 安装 Python（Windows）

### 1.1 下载与安装

访问官网 `https://www.python.org/downloads/windows/`。

安装向导的第一个界面是关键：

```
☑ Add python.exe to PATH
```

**必须勾选。** 这是新手 90% 环境问题的根源。没勾选的后果是：以后在命令行里敲 `python` 找不到命令，而 Python 本体装得毫无问题。

其余选项：

- Customize installation → 可勾选 `pip`、`py launcher`、`IDLE`、`tcl/tk and test suite`
- 建议安装路径保持默认 `C:\Users\<你>\AppData\Local\Programs\Python\Python3xx`
- `py launcher` 值得装：以后敲 `py -3.12` 可以指定版本，多版本共存不打架

### 1.2 验证安装

打开 **PowerShell**（Windows Terminal 里也行），执行：

```powershell
python --version
# 输出示例：Python 3.12.4
```

如果这条命令失败，再试：

```powershell
py --version
# 输出示例：Python 3.12.4
```

两条都失败，说明 PATH 没配或没重启终端。**改完 PATH 必须重开终端**，旧终端的环境变量是进程启动时快照的，不会自动刷新。

### 1.3 升级 pip

```powershell
python -m pip install --upgrade pip
```

注意这里用的是 `python -m pip` 而不是裸 `pip`。原因见 1.4。

### 1.4 为什么推荐 `python -m pip` 而不是 `pip`

`pip` 是一个独立的 exe 脚本，调用时它自己去找「属于哪个 Python」。`python -m pip` 是显式告诉当前解释器：「用我自己的 pip」。

在多环境、多版本机器上，`pip` 有可能装错地方，装到 A 环境，你却在 B 环境里 import ——于是就出现了经典报错：

```
ModuleNotFoundError: No module named 'xxx'
```

此时包其实**装上了，只是装在了另一个解释器里**。

**结论：养成写 `python -m pip` 的习惯。** 这是让脚本在新同事电脑上能跑起来的基本礼貌。

### 1.5 认识解释器

```python
import sys

print(sys.version)      # 完整版本号 + 编译信息
print(sys.executable)   # 当前正在用的解释器路径
print(sys.platform)     # win32 / linux / darwin
```

在虚拟环境里 `sys.executable` 会指向 venv 目录下的那个 python ——这是判断「我到底用的是谁」最直接的方法。

## 2. 虚拟环境 venv

### 2.1 为什么需要虚拟环境

假设项目 A 需要 `django==2.2`（老项目），项目 B 需要 `django==5.0`。Python 的包是**全局共享**的目录，如果都装进系统 Python，最后装的会把先装的覆盖掉，项目直接崩。

虚拟环境的思路：**给每个项目一份独立的包目录**。

### 2.2 创建 / 激活 / 退出

在项目根目录下：

```powershell
# 创建（Python 3.3+ 内置，无需额外安装）
python -m venv .venv

# 激活（PowerShell）
.\.venv\Scripts\Activate.ps1
```

激活成功后，命令行提示符前会出现 `(.venv)`：

```
(.venv) PS E:\github\pythonCore>
```

此时敲的 `python` 和 `pip` 都自动指向 venv 内的版本。验证：

```powershell
python -c "import sys; print(sys.executable)"
# 输出：E:\github\pythonCore\.venv\Scripts\python.exe
```

**看到路径里带 `.venv`，说明激活成功了。** 这是唯一可靠的判断方式。

退出：

```powershell
deactivate
```

VS Code 里通常不手动激活，选对解释器即可（见第 4 节）。

### 2.3 CMD 与 PowerShell 脚本策略

如果激活时报「禁止运行脚本」：

```
无法加载文件 ...Activate.ps1，因为在此系统上禁止运行脚本
```

这是 PowerShell 的执行策略限制，**不要**去改全局 `Set-ExecutionPolicy RemoteSigned`（影响整台机器，需要管理员）。两个更轻的方案：

```powershell
# 方案 A：本次会话临时放开
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
```

```powershell
# 方案 B：直接在 CMD 里用
.venv\Scripts\activate.bat
```

VS Code 默认选 `PowerShell` 终端，也可以在 `settings.json` 里改成 `CMD` 或 `Git Bash`：

```json
{
  "terminal.integrated.defaultProfile.windows": "PowerShell"
}
```

### 2.4 在 VS Code 里选解释器（推荐做法）

`Ctrl+Shift+P` → 输入 `Python: Select Interpreter` → 选择带 `.venv` 字样的那一项。

选对后，VS Code 底部的状态栏会显示当前解释器；编辑 `.py` 文件时，右下角的运行按钮会自动用它启动。

选错的典型症状：VS Code 里能 import，命令行里报 `ModuleNotFoundError`。原因就是 IDE 用 A 环境、终端用 B 环境。

### 2.5 .gitignore

`.venv` 目录不该进版本库：

```gitignore
.venv/
venv/
__pycache__/
*.py[cod]
.env
```

`__pycache__` 是 Python 的字节码缓存（`.pyc`），是纯派生产物，同样不要提交。

### 2.6 复现别人环境：requirements.txt

见第 3 节。核心命令：

```powershell
python -m pip freeze > requirements.txt
python -m pip install -r requirements.txt
```

### 2.7 常见误区

| 误区 | 事实 |
|---|---|
| 项目建在 `C:\Program Files` 下 | 权限问题高发（pip 写不进去），务必避免 |
| 一台机器只建一个 venv 放家里复用 | 正是虚拟环境要解决的问题，每个项目一份 |
| 删了项目文件夹还要删 venv | venv 就在项目文件夹里，删项目即删环境 |
| venv 能替代 Docker | 不能，venv 不隔离系统库和 Python 版本 |
| 提交的应该是 `.venv` | 提交的是 `requirements.txt` / `pyproject.toml` |

## 3. pip 与依赖管理

### 3.1 pip 基本命令

```powershell
# 安装
python -m pip install requests
python -m pip install requests==2.31.0        # 锁定版本
python -m pip install "requests>=2.28,<3.0"   # 版本区间
python -m pip install -U requests            # 升级到最新版

# 查看
python -m pip list                # 全部已安装
python -m pip show requests      # 某个包的详细信息（版本、路径、依赖）
python -m pip list --outdated     # 列出可升级的包

# 卸载
python -m pip uninstall requests

# 换源（国内网络）
python -m pip install requests -i https://pypi.tuna.tsinghua.edu.cn/simple
```

**推荐：把换源写进配置，而不是每次敲 `-i`。**

Windows 配置位置：`%APPDATA%\pip\pip.ini`

```ini
[global]
index-url = https://pypi.tuna.tsinghua.edu.cn/simple
timeout = 120
```

### 3.2 requirements.txt 的问题

`pip freeze` 生成的 requirements.txt 是「**扁平快照**」，它会把你依赖的依赖也全写出来：

```
requests==2.31.0
certifi==2024.2.2        # requests 拉的
charset-normalizer==3.3.2 # requests 拉的
idna==3.6                # requests 拉的
urllib3==2.2.0           # requests 拉的
```

问题很实际：文件里分不清哪些是**你真正需要的**，哪些是传递依赖；别人升级了 `requests` 内部的 `urllib3`，你的文件就过期了，而且你根本不知道该改哪一行。

**最佳实践：只写直接依赖，手工维护。**

```txt
# requirements.txt
requests==2.31.0
pandas>=2.0
```

### 3.3 pyproject.toml —— 现代标准

`pyproject.toml` 是现在（2026 年）应当默认采用的方案。它用 TOML 表达结构化依赖，还能声明项目元数据、构建方式和工具配置。

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "my-project"
version = "0.1.0"
description = "一个示例项目"
requires-python = ">=3.10"
dependencies = [
    "requests>=2.31",
    "pandas>=2.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.0",
    "ruff>=0.5",
]

[tool.ruff]
line-length = 100
target-version = "py310"
```

直接依赖写在 `dependencies`，测试/格式化工具写在 `optional-dependencies.dev`，配置文件按 `[tool.xxx]` 分区——**依赖声明和工具配置在同一个文件里，信息密度远高于 requirements.txt**。

安装本地项目（可编辑模式，源码改了立即生效）：

```powershell
python -m pip install -e ".[dev]"
```

现代同步器（pip 24.1+ 内置，推荐给新项目）：

```powershell
python -m pip install uv
uv init            # 生成 pyproject.toml
uv add requests
uv sync            # 按 pyproject.toml + uv.lock 建环境
```

### 3.4 依赖版本策略

| 场景 | 策略 |
|---|---|
| 复现别人的 bug / 部署生产 | 精确锁版本 `==`，配合 lock 文件 |
| 个人开发工具链 | 宽松 `>=`，方便吃 bugfix |
| 自己写的库 | 下限宽松 + 上限约束 `>=1.0,<2.0`，防止未来大版本 breaking |
| 应用（不是库） | 全部锁死，有 lock 文件就无条件用 lock |

口诀：**你能控制升级节奏，就用宽区间；你不能控制，就锁死。**

### 3.5 导入失败时怎么定位

```python
import sys
print(sys.executable)   # 1. 到底用的哪个解释器
import requests
print(requests.__file__)  # 2. 包从哪个路径加载
```

这两行能解决 90% 的「明明装了却 import 不到」。

## 4. VS Code 配置

### 4.1 必装插件

| 插件 | ID | 作用 |
|---|---|---|
| Python | `ms-python.python` | 语法高亮、调试、Lint 基础 |
| Pylance | `ms-python.vscode-pylance` | 智能补全、类型提示、跳转定义（基于 Pyright） |
| Jupyter | `ms-toolsai.jupyter` | 直接在 `.py` 顶部执行单元格 |
| Python Debugger | `ms-python.debugpy` | 新版调试器 |
| Ruff | `charliermarsh.ruff` | Lint + 格式化，快如闪电，可替代 flake8+black |
| Error Lens | `AlexanderSosnovsky.errorlens` | 把报错直接显示在出错那一行 |

只想装一个的话，装 **Python + Pylance + Ruff** 三个，够用一整年。

### 4.2 关键设置

`Ctrl+Shift+P` → `Preferences: Open User Settings (JSON)`：

```json
{
  "python.defaultInterpreterPath": "${workspaceFolder}/.venv/Scripts/python.exe",
  "python.terminal.activateEnvironment": true,
  "python.analysis.typeCheckingMode": "basic",
  "python.testing.pytestEnabled": true,
  "[python]": {
    "editor.codeActionsOnSave": {
      "source.fixAll.ruff": "explicit",
      "source.organizeImports.ruff": "explicit"
    }
  },
  "files.exclude": {
    "**/__pycache__": true
  }
}
```

几个高价值项：

- `defaultInterpreterPath` 指向项目内 `.venv`，新项目默认就对
- `activateEnvironment: true` 让终端自动激活 venv，终端和 IDE 用同一个解释器
- `typeCheckingMode`：入门用 `basic`，熟了上 `strict`
- Ruff 的 `onSave` 自动修复，让代码风格不用你操心

### 4.3 运行代码的三种方式

**方式 A：REPL（最省事，适合试错）**

```powershell
python
>>> 2 ** 10
1024
>>> exit()
```

**方式 B：脚本（生产方式）**

```powershell
python hello.py
```

**方式 C：VS Code 运行**

编辑器右上角 ▷ 按钮，或终端里：

```powershell
python hello.py
```

### 4.4 三种运行方式的差异（面试常考）

| 方式 | 是否阻塞当前目录 | `__name__` | 用途 |
|---|---|---|---|
| `python a.py` | CWD 保持不变 | `__main__` | 日常写脚本 |
| `python -m pkg.mod` | CWD 保持不变 | `__main__` | 按包路径运行，支持相对导入 |
| REPL | CWD 保持不变 | `__main__` | 快速验证 |

`python -m` 的关键优势：它会把**当前目录**放进 `sys.path[0]`，而 `python a.py` 是把**脚本所在目录**放进去。所以项目里跑测试必须用：

```powershell
python -m pytest
python -m mypkg
```

而不是 `pytest` 或 `python mypkg`，否则你精心设计的相对导入会全部报错。

## 5. 常见环境问题排查

### 5.1 `'python' 不是内部或外部命令`

逐条自查：

1. PATH 里有没有 Python 的目录（`C:\Users\xxx\AppData\Local\Programs\Python\Python312\` 和它的 `Scripts\`）
2. 改完 PATH **重开终端**
3. 有没有 `python3` / `py` 可以用（某些安装只暴露其中一个）
4. 是不是装的时候没勾 `Add to PATH`——**最省事的办法是重装并勾上**

临时绕过（当前会话有效）：

```powershell
$env:Path += ";C:\Users\xxx\AppData\Local\Programs\Python\Python312;C:\Users\xxx\AppData\Local\Programs\Python\Python312\Scripts"
```

### 5.2 `ModuleNotFoundError: No module named 'xxx'`

四个原因，从高到低排查：

```python
import sys
print(sys.executable)      # ① 用的是哪个解释器？装包时用的是不是同一个？
import sysconfig
print(sysconfig.get_paths()["purelib"])  # ② 包应该装在哪个目录
import xxx                  # ③ 报错的包，本地是不是有个同名文件夹把标准库/真包遮住了？
```

```powershell
python -m pip show xxx        # ④ 到底装没装上
```

第③点值得单独说：如果你在项目根目录有个叫 `random.py`、`json.py`、`time.py` 的文件，或者有个叫 `utils` 的包，**它会遮蔽标准库或同名第三方库**，报错信息还特别迷惑人。这类坑叫「命名遮蔽」，排查方法：

```powershell
python -c "import xxx; print(xxx.__file__)"
```

输出的路径如果指向你项目里的文件，那就是遮蔽了，改名即可。

### 5.3 中文乱码

三个层面，分别处理：

**文件本身存成 UTF-8**

VS Code 右下角点编码 → Save with Encoding → UTF-8。老项目可能是 GBK（显示为 `GB2312`/`GBK`）。

**Windows 控制台输出中文**

Windows 旧版控制台默认 GBK 编码，会出现 `UnicodeEncodeError` 或问号乱码。三种解法：

```python
import sys

# 方案 1：强制标准输出为 UTF-8（Py 3.7+）
sys.stdout.reconfigure(encoding="utf-8")

# 方案 2：改变控制台代码页（执行前）
# chcp 65001

# 方案 3：最实用的一招——把报错也一起收走
print("中文测试")
```

更彻底的方案是在 Windows Terminal 或 PowerShell 7 里跑，它们默认支持 UTF-8。也可以直接升级到 Windows 终端 + `chcp 65001`。

**读文件时显式指定编码**

```python
# 反面教材：依赖操作系统默认值，换台机器就炸
with open("data.txt") as f:
    text = f.read()

# 正确
with open("data.txt", encoding="utf-8") as f:
    text = f.read()
```

`encoding="utf-8"` 应当成为你写 `open()` 时的肌肉记忆。

### 5.4 其他高频坑

| 现象 | 原因 | 解决 |
|---|---|---|
| `pip install` 报权限拒绝 | 装到了系统 Python | 用 venv，或 `--user` |
| 明明装了包却报找不到 | 装到了别的解释器 | `python -m pip`，核对 `sys.executable` |
| 下载超时 / 特别慢 | 网络 | 换国内源 |
| `pip install` 编译报错 | 缺 C 编译器，装不了带 C 扩展的包 | 优先找预编译轮子（wheel），或用 conda/uv |
| `SyntaxError: invalid character` | 中文全角符号（`“”` `（）` `：`） | 检查是否误用了中文标点 |

最后一条特别高频：中文输入法状态下打的括号、冒号、逗号全是全角的，Python 会报语法错误而不是提示「你是不是用了中文标点」。报错行号往上找一行，往往就能看到那个全角符号。

## 6. 验证环境是否就绪

新建 `check.py`：

```python
"""环境自检脚本：python check.py"""
import sys
import sysconfig

print(f"Python 版本 : {sys.version.split()[0]}")
print(f"解释器路径   : {sys.executable}")
print(f"解释器名称   : {sysconfig.get_platform()}")
print(f"包安装目录   : {sysconfig.get_paths()['purelib']}")
print(f"虚拟环境中   : {'venv' in sys.executable or sys.prefix != sys.base_prefix}")
print(f"标准输出编码 : {sys.stdout.encoding}")
print("环境自检完成 ✓")
```

第一行和第三行是重点：

- 解释器路径里**应该**包含项目路径或 `.venv`；如果指向 `C:\Windows\System32\`，说明 venv 没激活、VS Code 选错解释器了
- `sys.stdout.encoding` 若是 `cp936`，输出中文到终端会出问题，参考 5.3

## 本节小结

1. **PATH**：安装时勾 `Add python.exe to PATH`，改完必须重开终端；`python --version` 是唯一验证标准。
2. **venv**：一个项目一个环境，`python -m venv .venv`，判断激活成功的标志是 `sys.executable` 里出现 `.venv`。别提交 `.venv` 到 git。
3. **pip**：坚持写 `python -m pip` 而不是裸 `pip`，这一步能避免掉进「装在 A 环境、import 在 B 环境」的大坑。查询用 `pip show`，升级用 `-U`。
4. **依赖管理**：`requirements.txt` 是扁平快照，只写直接依赖；`pyproject.toml` 是现代标准，能同时管依赖和工具配置，新项目优先用它。
5. **VS Code**：Python + Pylance + Ruff 是最小可用组合；关键是选对解释器，并开启 `activateEnvironment` 让终端与 IDE 保持一致。
6. **运行方式**：`python a.py` vs `python -m pkg.mod` vs REPL，三者的 `sys.path` 和 `__name__` 行为不同，`-m` 才是运行包内模块的正确姿势。
7. **排查三板斧**：PATH 报错 → 查安装和终端；`ModuleNotFoundError` → 查 `sys.executable`、查同名文件遮蔽；乱码 → 查文件编码、`open(..., encoding="utf-8")`、控制台代码页。
8. **编码规范**：文件存 UTF-8、`open()` 永远显式写 `encoding="utf-8"`、类型标识符只用 ASCII。

7. 你写了 `def func(): return x`，然后在文件末尾执行 `del x` 并再次调用 `func()`，会发生什么？请解释 Python 变量绑定的本质。

   <details>
   <summary>参考答案</summary>

   1. `pip` 是独立 exe，自己去找解释器；`python -m pip` 强制用当前 `python` 对应的 pip。多版本/多虚拟环境下裸 `pip` 可能装到系统 Python，而运行时用的是 venv/另一个版本，于是包"装上了"却 import 不到。

   2. 排查步骤：① 确认 VS Code 右下角/`Python: Select Interpreter` 选的是 `.venv`；② 在终端执行 `python -c "import sys; print(sys.executable)"` 确认是 venv 解释器；③ 确认终端已激活 venv（提示符有 `(.venv)`），或改用 `.\.venv\Scripts\python.exe -m pip install xxx` 直接指定解释器；④ 检查项目里是否有与包同名的本地文件造成遮蔽（`print(xxx.__file__)`）。最常见原因是 VS Code 解释器和终端解释器不一致。

   3. `，` 是中文全角逗号，Python 不认识。应使用半角 `,`。避免方法：写代码时切英文输入法；报错时检查语法错误行的上一行附近是否有中文标点。

   4. 缺点：① 混入大量传递依赖，分不清哪些是直接依赖；② 版本可能过旧/过新，与真实需求脱节；③ 没有范围约束、无法表达开发依赖分组。改进：手工只写直接依赖及合理区间；更推荐改用 `pyproject.toml`。

   5. 优势：① 结构化，可区分运行依赖、开发依赖、可选依赖；② 可声明项目元数据与构建后端，能直接打包发布；③ 能集中配置工具（`[tool.ruff]`、`[tool.pytest]` 等）；④ 配合 lock 文件可精确复现环境。

   6. `python a.py` 把脚本所在目录放入 `sys.path[0]`，CWD 不在其中，包内相对导入（`from . import x`）会失败；`python -m a` 会把 CWD 放入 `sys.path[0]` 并按包路径执行，支持相对导入。pytest 采用 rootdir 相对导入约定，用 `python -m pytest` 可保证 CWD 在路径中。

   7. 报 `NameError: name 'x' is not defined`（若 x 是全局）。Python 变量名本质是「对象 → 名字」的绑定，`del` 只是解除绑定、回收引用；函数体在调用时才查名字，此时已无绑定，故报错。
