## 1. 并发 vs 并行

| 概念 | 含义 | 关注点 |
|---|---|---|
| **并发 (concurrency)** | 多个任务在时间上交替推进 | 「怎么」——结构问题，不要求同时执行 |
| **并行 (parallelism)** | 多个任务在同一时刻真正执行 | 「在哪里」——物理问题，需要多核/多机 |

一个直观比喻：并发像单核 CPU 上 multitasking（快速切换），并行像多核同时干活。

```python
# 10-01_concurrency_vs_parallelism.py
import time
import threading
import multiprocessing


def io_task(n):
    """模拟 IO 等待：计算量极小，等待时间很长。"""
    time.sleep(0.5)
    return n


def cpu_task(n):
    """模拟纯计算：占满 CPU。"""
    total = 0
    for i in range(8_000_000):
        total += i * n
    return total


def run_sequential(tasks):
    start = time.perf_counter()
    for t in tasks:
        t()
    return time.perf_counter() - start


def run_threads(tasks):
    start = time.perf_counter()
    threads = [threading.Thread(target=t) for t in tasks]
    for th in threads:
        th.start()
    for th in threads:
        th.join()
    return time.perf_counter() - start


def run_processes(tasks):
    start = time.perf_counter()
    with multiprocessing.Pool(processes=4) as pool:
        for t in tasks:
            pool.apply_async(t)
        pool.close()
        pool.join()
    return time.perf_counter() - start


tasks_io = [lambda: io_task(1) for _ in range(4)]
tasks_cpu = [lambda: cpu_task(1) for _ in range(4)]

print(f"IO 型 - 串行:   {run_sequential(tasks_io):.2f}s")
print(f"IO 型 - 线程:   {run_threads(tasks_io):.2f}s")
print(f"计算型 - 串行:   {run_sequential(tasks_cpu):.2f}s")
print(f"计算型 - 进程:   {run_processes(tasks_cpu):.2f}s")
```

**预期输出（数值因机器而异，趋势如下）**

```
IO 型 - 串行:   2.01s
IO 型 - 线程:   0.51s      <- IO 等待时释放 GIL，线程大幅提速
计算型 - 串行:   1.85s
计算型 - 进程:   0.52s      <- 纯计算必须靠多进程绕过 GIL
```

**结论**

- **IO 密集型**（网络请求、数据库、文件读写）：用线程或协程。
- **CPU 密集型**（数值计算、图像处理、加密）：用多进程，或用 C 扩展（numpy、gmpy）释放 GIL。
- Python 3.13 起有实验性 free-threading（无 GIL）构建，但生产环境仍以多进程/协程为主。

## 2. 线程（threading）

### 2.1 基本用法

```python
# 10-02_threading_basic.py
import threading
import time


def worker(name, delay):
    for i in range(3):
        print(f"{name} 第 {i + 1} 次")
        time.sleep(delay)


t1 = threading.Thread(target=worker, args=("线程A", 0.3), name="A")
t2 = threading.Thread(target=worker, args=("线程B", 0.3), name="B")

t1.start()     # 启动
t2.start()
print("主线程继续执行 ...")

t1.join()      # 等它结束
t2.join()
print("所有线程已结束")
```

**关键点**

- `start()` 才真正创建线程；直接调用 `worker(...)` 只是普通函数调用。
- `join(timeout)` 等待线程结束，不传参则无限等待。
- `daemon=True` 设置守护线程，主线程退出时它会被粗暴终止（不推荐，除非明确知道后果）。
- 线程间**不共享内存**，通过全局变量共享有竞态风险（见下文同步原语）。

### 2.2 线程池：ThreadPoolExecutor

手动建线程太啰嗦，用线程池统一调度。**这是处理 IO 并发的首选**。

```python
# 10-03_thread_pool.py
import time
from concurrent.futures import ThreadPoolExecutor, as_completed


def fetch(name, delay):
    """模拟一次网络请求。"""
    time.sleep(delay)
    return f"{name}@{(delay)}s"


def main():
    # as_completed：谁先完成先返回
    t0 = time.perf_counter()
    with ThreadPoolExecutor(max_workers=3, thread_name_prefix="fetch") as pool:
        futures = {pool.submit(fetch, f"url{i}", 0.3 * (3 - i)): i for i in range(3)}
        for fut in as_completed(futures):
            print("完成:", fut.result())
    print(f"总耗时 {time.perf_counter() - t0:.2f}s（并发约 0.9s，串行需 1.8s）")

    # 顺序返回：按提交顺序
    with ThreadPoolExecutor(max_workers=3) as pool:
        results = pool.map(lambda i: fetch(f"u{i}", 0.1), range(3))
        print(list(results))

    # 单个任务：直接拿返回值
    with ThreadPoolExecutor(max_workers=1) as pool:
        print(pool.submit(fetch, "single", 0.1).result())


if __name__ == "__main__":     # 多进程版本必须加这行保护（Windows/spawn）
    main()
```

**预期输出**

```
完成: url0@0.9s
完成: url1@0.6s
完成: url2@0.3s
总耗时 0.90s（并发约 0.9s，串行需 1.8s）
['url0@0.1s', 'url1@0.1s', 'url2@0.1s']
single@0.1s
```

`max_workers` 默认是 `min(32, os.cpu_count() + 4)`，对 IO 密集型可以设得比 CPU 数大得多（如 50~100）。

### 2.3 异常处理与取消

```python
# 10-04_pool_exception.py
from concurrent.futures import ThreadPoolExecutor, TimeoutError as FutureTimeout


def may_fail(n):
    if n % 2 == 1:
        raise ValueError(f"任务 {n} 出错")
    return n * 10


with ThreadPoolExecutor(max_workers=3) as pool:
    futures = [pool.submit(may_fail, i) for i in range(4)]

    for fut in futures:
        try:
            print("结果:", fut.result(timeout=5))
        except ValueError as e:
            print("失败:", e)

# done() / cancel()
with ThreadPoolExecutor(max_workers=2) as pool:
    fut = pool.submit(may_fail, 2)
    print("完成了吗:", fut.done())
    print("结果:", fut.result())
    print("还能取消吗:", fut.cancel())     # 已完成的任务无法取消 -> False
```

**预期输出**

```
结果: 0
失败: 任务 1 出错
结果: 20
失败: 任务 3 出错
完成了吗: True
结果: 20
还能取消吗: False
```

## 3. GIL：为什么线程对 CPU 密集无效

### 3.1 GIL 是什么

**GIL（Global Interpreter Lock，全局解释器锁）** 是 CPython 解释器内部的一把全局互斥锁。同一时刻只允许**一个线程**执行 Python 字节码。

```python
# 10-05_gil_demo.py
import threading
import time


def cpu_work(n):
    total = 0
    for i in range(n):
        total += i * i
    return total


N = 10_000_000


def run(mode):
    start = time.perf_counter()
    if mode == "serial":
        cpu_work(N); cpu_work(N)
    else:
        ts = [threading.Thread(target=cpu_work, args=(N,)) for _ in range(2)]
        for t in ts: t.start()
        for t in ts: t.join()
    return time.perf_counter() - start


print(f"串行: {run('serial'):.3f}s")
print(f"双线程: {run('thread'):.3f}s")
```

**预期输出**

```
串行: 2.996s
双线程: 5.986s      <- 反而更慢！线程切换有开销，且没带来任何并行
```

### 3.2 GIL 到底限制了什么

关键澄清：GIL **不限制**这些情况——
- 等待 IO 时（GIL 会被释放）
- 调用 C 扩展且该扩展自己释放了 GIL（如 `numpy` 大数组运算、`hashlib`、`zlib`、`ssl` 加密）

GIL 限制的是——**纯 Python 字节码的 CPU 并行计算**。

### 3.3 绕过 GIL 的三种方式

```python
# 10-06_bypass_gil.py
import time


def pure_python_sum(n):
    return sum(i * i for i in range(n))


def numpy_sum(n):
    import numpy as np          # numpy 在 C 层释放 GIL
    return int((np.arange(n) ** 2).sum())


N = 8_000_000

t = time.perf_counter(); pure_python_sum(N); print(f"纯 Python: {time.perf_counter() - t:.3f}s")

try:
    t = time.perf_counter(); numpy_sum(N); print(f"numpy:      {time.perf_counter() - t:.3f}s")
except ImportError:
    print("未安装 numpy")
```

**预期输出**

```
纯 Python: 0.851s
numpy:      0.058s
```

另外两种方式：**多进程**（下节）和**编写 C 扩展**（`ctypes` / `Cython` / `pybind11`，在调用前用 `Py_BEGIN_ALLOW_THREADS` 释放 GIL）。

## 4. 多进程（multiprocessing）

### 4.1 基本用法

```python
# 10-07_multiprocessing_basics.py
import multiprocessing as mp
import time
import os


def worker(n):
    """子进程执行：能看到自己的 PID。"""
    return f"子进程 pid={os.getpid()} 处理了 {n}"


def square(x):
    return x * x


def main():
    print(f"主进程 pid={os.getpid()}")

    # 方式 1：spawn 一个进程执行一次
    p = mp.Process(target=worker, args=(1,))
    p.start()
    p.join()
    print("子进程已结束, exitcode =", p.exitcode)

    # 方式 2：直接当函数调用（内部会起进程并通过管道回传结果）
    with mp.Pool(processes=2) as pool:
        print(pool.map(square, [1, 2, 3, 4]))
        print(pool.apply(square, (5,)))
        print(pool.apply_async(square, (6,)).get(timeout=5))
        print(pool.map(square, range(5, 9), chunksize=1))

    # 方式 3：Queue 在进程间通信
    q = mp.Queue()
    procs = [mp.Process(target=worker, args=(i,), kwargs={}, daemon=False) for i in range(0)]
    p1 = mp.Process(target=lambda: q.put(worker(100)))
    p2 = mp.Process(target=lambda: q.put(worker(200)))
    p1.start(); p2.start()
    p1.join(); p2.join()
    results = [q.get() for _ in range(2)]
    for r in results:
        print(r)
    q.close()


if __name__ == "__main__":
    main()
```

**关键点：必须写 `if __name__ == "__main__":`**

- Linux 默认 `fork` 启动方式，继承父进程内存，创建快；
- Windows/macOS（Python 3.8+）默认 `spawn`，会**重新导入主模块**。没有 main 保护会无限递归创建进程。

### 4.2 进程池 Executor 写法（推荐）

```python
# 10-08_process_pool_executor.py
from concurrent.futures import ProcessPoolExecutor, as_completed
import os


def compute(n):
    total = 0
    for i in range(n):
        total += i
    return os.getpid(), n, total


def main():
    # 用 max_workers 明确指定，别依赖默认值
    with ProcessPoolExecutor(max_workers=3) as ex:
        results = list(ex.map(compute, [1_000_000, 2_000_000, 3_000_000]))
    for pid, n, total in results:
        print(f"pid={pid} n={n} sum={total}")

    # 需要处理单个任务的异常
    with ProcessPoolExecutor(max_workers=2) as ex:
        fut = ex.submit(compute, 1_000)
        print(fut.result())


if __name__ == "__main__":
    main()
```

### 4.3 pickle 限制（重要面试点）

进程间通信靠 **pickle 序列化**。以下类型**无法** pickle，传入会报 `TypeError` / `AttributeError`：

- 局部函数、`lambda`（但模块顶层函数可以）
- 打开的文件对象、socket、线程锁 `Lock`
- 数据库连接、生成器
- lambda 定义的函数在子进程里无法反序列化（因为模块里没有这个名字）

```python
# 10-09_pickle_limits.py
import multiprocessing as mp
import pickle


def top_level_ok(x):
    """模块顶层函数：可 pickle，能被子进程找到。"""
    return x * 3


def try_pickle(obj, name):
    try:
        data = pickle.dumps(obj)
        print(f"{name}: OK，{len(data)} 字节")
    except Exception as e:
        print(f"{name}: 失败 -> {type(e).__name__}: {e}")


def run_lambda(x):
    return x          # 这个 run_lambda 本身没问题


if __name__ == "__main__":
    # 可序列化的
    try_pickle(top_level_ok, "顶层函数")
    try_pickle([1, 2, 3], "list")
    try_pickle({"a": 1}, "dict")
    try_pickle((1, 2), "tuple")

    # 不可序列化的
    try_pickle(lambda x: x, "lambda")
    try_pickle(open(__file__), "文件对象")
    try_pickle(mp.Lock(), "多进程锁")
    try_pickle((x for x in range(3)), "生成器")
```

**预期输出**

```
顶层函数: OK，33 字节
list: OK，14 字节
dict: OK，12 字节
tuple: OK，11 字节
lambda: 失败 -> AttributeError: Can't pickle local object '<lambda>'
文件对象: 失败 -> TypeError: cannot pickle '_io.TextIOWrapper' object
多进程锁: 失败 -> TypeError: cannot pickle 'multiprocessing.synchronize.SemLock' object
生成器: 失败 -> TypeError: cannot pickle 'generator' object
```

**规避方式**

1. 用 `mp.Pool(initializer=init_worker, initargs=(data,))` 预先把全局数据放到子进程内；
2. 共享内存 `mp.Array` / `mp.Value` / `mp.shared_memory.SharedMemory`；
3. 用文件 / socket 自己传数据；
4. 把 lambda 替换为顶层函数。

```python
# 10-10_pool_initializer.py
import multiprocessing as mp


DATA = None      # 子进程内的全局变量

def init_worker(data):
    global DATA
    DATA = data

def process(chunk):
    return sum(x * 2 for x in chunk)


if __name__ == "__main__":
    big = list(range(100_000))
    chunks = [big[i:i+25_000] for i in range(0, len(big), 25_000)]
    with mp.Pool(4, initializer=init_worker, initargs=(big,)) as pool:
        print(sum(pool.map(process, chunks)))
    # 9999900000
```

## 5. 协程与 asyncio

### 5.1 为什么需要协程

线程池再轻量，每个线程也有 ~8MB 栈开销 + 上下文切换成本。协程是**用户态**的轻量任务，一个事件循环就能跑成千上万个。

| 方案 | 切换成本 | 并发数量级 | 适用 |
|---|---|---|---|
| 线程 | 高（内核态） | 数千 | 已有同步库、阻塞 C 扩展 |
| 协程 | 极低（用户态） | 数万~十万 | 高并发 IO（Web 服务、爬虫、网关） |
| 进程 | 最高 | 几十~几百 | CPU 密集 |

### 5.2 基本语法：async / await

```python
# 10-11_async_basic.py
import asyncio
import time


async def task(name, delay):
    """协程：遇到 await 就让出控制权。"""
    print(f"{name} 开始")
    await asyncio.sleep(delay)          # 模拟异步 IO，释放事件循环
    print(f"{name} 完成")
    return f"{name} result"


async def main():
    # 顺序执行（await 逐个等待）
    t0 = time.perf_counter()
    r1 = await task("A", 0.3)
    r2 = await task("B", 0.3)
    print(f"顺序耗时 {time.perf_counter() - t0:.2f}s, {r1} {r2}")   # 约 0.6s

    # 并发执行（asyncio.gather）
    t0 = time.perf_counter()
    results = await asyncio.gather(task("C", 0.3), task("D", 0.3))
    print(f"并发耗时 {time.perf_counter() - t0:.2f}s, {results}")      # 约 0.3s

    # 带超时的等待
    try:
        await asyncio.wait_for(task("E", 1.0), timeout=0.3)
    except asyncio.TimeoutError:
        print("E 超时了，被取消")

    # 创建后台任务，不 await
    bg = asyncio.create_task(task("BG", 0.5))
    await asyncio.sleep(0.1)
    print("主逻辑结束，BG 还在跑")
    await bg            # 必须等待，否则协程结束时会被警告


# Python 3.7+：asyncio.run 是推荐的入口
if __name__ == "__main__":
    asyncio.run(main())
```

**预期输出**

```
A 开始
A 完成
B 开始
B 完成
顺序耗时 0.60s, A result B result
C 开始
D 开始
C 完成
D 完成
并发耗时 0.30s, ['C result', 'D result']
E 开始
E 超时了，被取消
主逻辑结束，BG 还在跑
BG 完成
```

### 5.3 事件循环是怎么工作的

```
            ┌──────────────────────────────┐
   创建 →   │        事件循环 (EventLoop)     │
  Task  ┌──►│  就绪队列  →  回调 →  I/O 等待  │
        │   │  (select/poll/epoll/IOCP)     │
        │   └──────────────────────────────┘
        │        │await 时挂起，│完成后回调唤醒
        └────────┘
```

关键点：

- **单线程**，所有协程在同一线程上跑；
- `await` 会把当前协程挂起并注册回调，事件循环去处理别的就绪任务；
- 当 IO 就绪，回调把协程重新放回就绪队列；
- 所以**协程里绝不能写阻塞代码**（`time.sleep`、`requests.get`），否则整个循环卡死。

```python
# 10-12_event_loop_demo.py
import asyncio


async def worker(i):
    await asyncio.sleep(0.1)
    return i


async def main():
    loop = asyncio.get_running_loop()
    print("事件循环对象:", type(loop).__name__)
    print("是否在运行中:", loop.is_running())

    # Task 是「被事件循环调度的协程」，可以并发执行并管理生命周期
    tasks = [asyncio.create_task(worker(i)) for i in range(3)]
    print("任务状态:", [t.done() for t in tasks])
    results = await asyncio.gather(*tasks)
    print("任务结果:", results)
    print("任务状态:", [t.done() for t in tasks])

    # 取消任务
    t = asyncio.create_task(asyncio.sleep(10))
    await asyncio.sleep(0.05)
    t.cancel()
    try:
        await t
    except asyncio.CancelledError:
        print("任务已取消")

    # 异常不会被静默吞掉
    async def bad():
        raise ValueError("协程炸了")

    r = await asyncio.gather(bad(), return_exceptions=True)
    print("gather 捕获:", type(r[0]).__name__, r[0])


asyncio.run(main())
```

**预期输出**

```
事件循环对象: ProactorEventLoop
是否在运行中: True
任务状态: [False, False, False]
任务结果: [0, 1, 2]
任务状态: [True, True, True]
任务已取消
gather 捕获: ValueError 协程炸了
```

### 5.4 实战：并发请求 URL

用 `asyncio` + `aiohttp`（或 `httpx`）并发抓取。注意 `aiohttp` 需额外安装；没装时下面代码会自动降级为模拟请求，保证可直接运行。

```python
# 10-12_concurrent_http.py
import asyncio
import time


try:
    import aiohttp
    HAS_AIOHTTP = True
except ImportError:
    HAS_AIOHTTP = False


URLS = [
    "https://httpbin.org/get?i=1",
    "https://httpbin.org/get?i=2",
    "https://httpbin.org/get?i=3",
    "https://httpbin.org/get?i=4",
]


# ---------- 真实 HTTP 版本（需 pip install aiohttp） ----------
async def fetch_real(session, url):
    async with session.get(url, timeout=aiohttp.ClientTimeout(total=10)) as resp:
        return url, resp.status, len(await resp.text())


async def main_real():
    async with aiohttp.ClientSession() as session:
        # 1) gather：并发全部发起，按顺序返回
        t0 = time.perf_counter()
        results = await asyncio.gather(*[fetch_real(session, u) for u in URLS])
        print(f"gather 耗时 {time.perf_counter() - t0:.2f}s")
        for url, status, size in results:
            print(f"  {status} {size}B {url}")

        # 2) 限制并发数：用信号量防止打爆对方
        sem = asyncio.Semaphore(2)      # 最多同时 2 个

        async def limited(url):
            async with sem:            # 拿不到令牌就等待
                await asyncio.sleep(0.2)
                return f"完成 {url[-1]}"

        t0 = time.perf_counter()
```

### 6.1 Lock 与 RLock

```python
# 10-14_lock_rlock.py
import threading
import time

counter = 0
lock = threading.Lock()
rlock = threading.RLock()


def unsafe_add(n):
    global counter
    for _ in range(n):
        counter += 1          # 读-改-写，非原子，可能丢更新


def safe_add(n):
    global counter
    for _ in range(n):
        with lock:            # 临界区：同一时刻只有一个线程能进
            counter += 1


ts = [threading.Thread(target=unsafe_add, args=(100_000,)) for _ in range(5)]
for t in ts: t.start()
for t in ts: t.join()
print(f"不加锁: {counter}（预期 500000，可能偏小）")   # 结果不稳定

counter = 0
ts = [threading.Thread(target=safe_add, args=(100_000,)) for _ in range(5)]
for t in ts: t.start()
for t in ts: t.join()
print(f"加锁后: {counter}（一定是 500000）")


# RLock：可重入锁，同一线程可重复获取
def reentrant():
    with rlock:
        with rlock:          # 普通 Lock 在这里会死锁
            print("RLock 允许嵌套获取")
    print("RLock 释放后，别的线程可以进入")


reentrant()


# try/finally 手动管理锁
lock2 = threading.Lock()
lock2.acquire()
print("已获取锁")
lock2.release()
with lock2:
    print("with 语句自动释放")
```

### 6.3 Condition：更精细的等待/通知

```python
# 10-16_condition.py
import threading
import time

# 简单生产者消费者：有值才能取，取完通知生产者
buffer = []
full = threading.Semaphore(0)     # 消费者拿到 permit 才能取
empty = threading.Semaphore(1)    # 生产者拿到 permit 才能放


def produce():
    for i in range(3):
        empty.acquire()            # 等空位
        buffer.append(i)
        print(f"生产 {i}")
        full.release()             # 通知有货
        time.sleep(0.05)


def consume():
    for _ in range(3):
        full.acquire()             # 等货
        item = buffer.pop(0)
        print(f"消费 {item}")
        empty.release()            # 释放空位


p = threading.Thread(target=produce)
c = threading.Thread(target=consume)
p.start(); c.start(); p.join(); c.join()

print("剩余:", buffer)

# Condition 版：更常用的写法（notify 必须放在 with 内）
cv = threading.Condition()
state = {"ready": False}

def waiter():
    with cv:                        # 进入条件变量的锁保护范围
        while not state["ready"]:   # 必须用 while 而不是 if（防止虚假唤醒）
            cv.wait()               # 释放锁并等待
        print("被唤醒，state =", state)

w = threading.Thread(target=waiter)
w.start()
time.sleep(0.1)
with cv:
    state["ready"] = True
    cv.notify_all()                 # 唤醒所有等待者；notify() 只唤醒一个
w.join()
```

```
剩余: []
```

### 6.5 Queue：线程安全的任务队列（最实用）

生产消费的标准解法，比手写 `Lock` 可靠得多。

```python
# 10-18_queue.py
import queue
import threading
import time

# queue.Queue(maxsize=0)  无界；maxsize>0 满了 put 会阻塞
q = queue.Queue(maxsize=10)


def producer():
    for i in range(5):
        q.put(f"item-{i}")
        print(f"生产 item-{i}（队列长度 {q.qsize()}）")
        time.sleep(0.05)
    q.put(None)          # 毒丸：通知消费者结束


def consumer(name):
    while True:
        item = q.get()               # 取出并计数
        if item is None:
            q.task_done()
            break
        print(f"{name} 消费 {item}")
        time.sleep(0.02)
        q.task_done()                # 标记处理完成


consumers = [threading.Thread(target=consumer, args=(f"C{i}",)) for i in range(2)]
for c in consumers: c.start()

producer()
q.join()                 # 等待所有 task_done 被调用
for c in consumers: c.join()
print("队列处理完毕")

# 其他队列类型
dq = queue.deque(maxlen=3)            # 双端队列，满了丢最旧的
dq.append(1); dq.append(2); dq.append(3); dq.append(4)
print("deque:", list(dq))             # [2, 3, 4]

pq = queue.PriorityQueue()
for item in [(3, "c"), (1, "a"), (2, "b")]:
    pq.put(item)
while not pq.empty():
    print("优先队列取出:", pq.get()[1])   # a b c
```

### 6.6 原语速查表

| 原语 | 用途 | 关键 API | 注意 |
|---|---|---|---|
| `Lock` | 互斥访问共享资源 | `acquire/release`、`with` | 不可重入，重复获取会死锁 |
| `RLock` | 可重入的互斥 | 同上 | 记录持有者线程，需配对 release |
| `Event` | 一个/多个线程等待信号 | `set/clear/is_set/wait` | 一次性/可复位的布尔标志 |
| `Condition` | 条件等待（生产者消费者） | `wait/notify/notify_all` | 必须配 `with`，循环用 `while` |
| `Semaphore` | 限制同时访问资源的数量 | `acquire/release` | `BoundedSemaphore` 防超发 |
| `Barrier` | 让 N 个线程在一点会合 | `wait` | 全部到达才继续 |
| `Queue` | 线程安全任务队列 | `put/get/task_done/join` | **首选**，少手写锁 |

## 7. 实际选型建议

### 7.1 决策表

| 场景 | 推荐方案 | 理由 |
|---|---|---|
| HTTP 请求 / 数据库查询等 IO 并发（几十~几百） | **协程 + aiohttp/httpx** | 单线程、切换成本低、能开上万连接 |
| IO 并发但只有几个，且必须用同步库 | **线程池 ThreadPoolExecutor** | 依赖现成同步代码，改造成本最低 |
| 爬取大量网页，需高并发 | **协程 + 限流信号量** | 协程适合万级连接，配合 `Semaphore` 防止被封 |
| CPU 密集计算（数值、图像、加解密） | **多进程 ProcessPoolExecutor** | 绕过 GIL 获得真并行 |
| 既有 CPU 又既有 IO 的混合任务 | **进程 + 进程内协程/线程池** | 两级并发 |
| 已有 C 扩展能释放 GIL（numpy、cryptography） | **线程池** | GIL 已释放，线程即可并行 |
| 需求简单（并发 5 个 sleep） | **线程池**，别上协程 | 复杂度不值当 |
| Web 高并发服务（FastAPI/aiohttp） | **协程** | 单进程即可支撑高 QPS |
| 定时任务 / 简单脚本并发调用 | **concurrent.futures** | 一行代码搞定 |

### 7.2 选型口诀

```
IO 密集 + 高并发 + 异步库可用  → 协程
IO 密集 + 依赖同步库 / 数量少  → 线程池
CPU 密集                       → 多进程（或用 C 扩展释放 GIL）
别写 async 函数里调 time.sleep / requests —— 会卡死整个事件循环
```

### 7.3 常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 协程里调同步阻塞库 | 整个服务卡死 | 用异步库，或 `loop.run_in_executor` 包线程池 |
| 线程返回 Future 但没 `result()` | 异常被静默吞掉 | 必须 `.result()` 或用 `as_completed` |
| 多进程没写 main 保护 | Windows 上无限创建进程崩溃 | `if __name__ == "__main__":` |
| 传 lambda 给进程池 | pickle 失败 | 改用顶层函数 |
| 无限制地提交任务 | 内存爆炸 | `max_workers` + 队列背压 |
| 线程里直接改共享 dict | 竞态、丢数据 | 用 `Lock` 或 `Queue` |
| `asyncio.run()` 里再调 `asyncio.run()` | RuntimeError | 一个事件循环用到底 |
| 创建事件循环后忘记关闭 | 警告、资源泄漏 | 用 `async with` 或 `try/finally: loop.close()` |

## 本节小结

- **并发 ≠ 并行**：并发是结构（怎么交替），并行是物理（同时跑）。IO 等待靠并发，CPU 计算靠并行。
- **线程**轻量但受 **GIL** 限制：纯 Python 字节码无法并行；`ThreadPoolExecutor` 是 IO 并发的首选工具。
- **多进程**靠真并行绕开 GIL，但进程间通信依赖 **pickle**，lambda / 文件对象 / 锁 / 生成器都无法序列化。
- **协程**用 `async`/`await` 实现用户态并发，`asyncio.run()` 是入口，`Task` 是调度单位，`gather` 聚合结果，`Semaphore` 限流。
- **同步原语**：`Lock`（互斥）、`RLock`（可重入）、`Event`（信号）、`Condition`（条件等待，循环必须用 `while`）、`Semaphore`（限并发）、`Queue`（生产消费首选）。
- 记住两条铁律：协程内绝不阻塞；进程池必须写 main 保护。

## 自测题

1. 什么是 GIL？为什么多线程做 CPU 密集任务反而比单线程慢？什么情况下 GIL 不会成为瓶颈？

<details>
<summary>参考答案</summary>

GIL（全局解释器锁）是 CPython 解释器级别的互斥锁，保证同一时刻只有一个线程在执行 Python 字节码，因此 CPython 层面无法做 CPU 并行。

多线程更慢的原因有两点：① 没有并行收益，总执行时间不变；② 线程切换（GIL 的获取/释放）本身有开销，加上频繁切换破坏了 CPU 缓存局部性。

GIL 不构成瓶颈的情况：
- 线程在等待 IO（GIL 被主动释放）；
- 调用了会主动释放 GIL 的 C 扩展（如 `numpy` 大数组运算、`hashlib.sha1`、`zlib` 压缩、`ssl` 加密、文件读写）。

</details>

2. 写出用 `ThreadPoolExecutor` 并发执行 10 个任务、打印完成顺序的代码，并说明 `as_completed` 与 `map` 的区别。

<details>
<summary>参考答案</summary>

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time

def task(i):
    time.sleep(0.1 * (10 - i))
    return i

with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(task, i) for i in range(10)]
    for fut in as_completed(futures):
        print("完成:", fut.result())
```

区别：

- `map(fn, iterable)` 惰性产出结果，**严格按提交顺序**返回；某个任务慢会阻塞后续取结果，但任务本身仍并发执行；无法为单个任务设超时。
- `as_completed(futures)` 按**实际完成顺序**产出 `Future`，适合流式处理、设超时、逐个检查异常。

配合 `pool.submit` 拿到的 `Future` 支持 `.result(timeout=)`、`.done()`、`.cancel()`、`.exception()`。

</details>

3. 为什么 Windows 上使用 `multiprocessing` 必须写 `if __name__ == "__main__":`？Linux 上呢？

<details>
<summary>参考答案</summary>

Windows 和 macOS（Python 3.8+）默认使用 `spawn` 启动方式：子进程会**重新导入主模块**来构造自己。如果创建进程的代码不在 `if __name__ == "__main__":` 保护下，子进程导入主模块时会再次执行创建进程的代码，导致无限递归创建进程，程序崩溃或报 `RuntimeError`。

Linux 默认是 `fork`，子进程直接 fork 父进程的内存快照，不重新导入，所以不加保护也能跑——但**仍建议统一加上**，因为代码要跨平台，而且 `fork` 出的子进程可能继承已加锁的锁导致死锁。

</details>

4. 列举 4 种不能被 pickle 的对象，并说明 `ProcessPoolExecutor` 传 `lambda` 会怎样。如何绕过？

<details>
<summary>参考答案</summary>

不能 pickle 的典型对象：

1. `lambda` 表达式和局部函数（局部函数在模块中找不到同名对象）
2. 文件对象（open 的返回值）、socket
3. 线程/进程锁（`threading.Lock`、`multiprocessing.Lock`）
4. 生成器、迭代器对象
5. 数据库连接、C 扩展对象

传 lambda 给进程池会在**提交任务时**抛 `TypeError: cannot pickle 'function' object`。

绕过方式：

- 把逻辑改为**模块顶层函数**（最常用）；
- 用闭包/工厂函数代替 lambda，或用 `functools.partial`（可 pickle，前提是 bound 的东西可 pickle）；
- 大对象不要当参数传，改用 `Pool(initializer=..., initargs=...)` 在子进程初始化时注入；
- 用 `mp.shared_memory.SharedMemory` / `mp.Array` / `mp.Value` 共享数据。

</details>

5. 用 asyncio 写出"同时请求 20 个 URL，最多 5 个并发，单个超时 3 秒，全部完成或超时后返回结果"的代码。

<details>
<summary>参考答案</summary>

```python
import asyncio

async def fetch(url, sem):
    async with sem:                       # 令牌控制并发数
        return await asyncio.wait_for(
            do_request(url), timeout=3.0
        )

async def do_request(url):
    await asyncio.sleep(0.1)
    return f"OK {url}"

async def main():
    urls = [f"http://x.com/{i}" for i in range(20)]
    sem = asyncio.Semaphore(5)            # 最多 5 个并发
    results = await asyncio.gather(
        *[fetch(u, sem) for u in urls],
        return_exceptions=True            # 单个失败不影响整体
    )
    ok = [r for r in results if isinstance(r, str)]
    err = [r for r in results if isinstance(r, Exception)]
    print(f"成功 {len(ok)}，失败 {len(err)}")
    for e in err:
        print(type(e).__name__, e)
```

要点：`Semaphore` 限制并发，`wait_for` 实现单任务超时，`return_exceptions=True` 让一个失败不至于带崩全部。

</details>

6. `Condition.wait()` 后面的判断为什么必须写 `while cond` 而不能写 `if cond`？`notify` 和 `notify_all` 有什么区别？

<details>
<summary>参考答案</summary>

因为 `wait()` 存在**虚假唤醒**（spurious wakeup）的可能：即使没有收到通知，线程也可能被唤醒。同时，唤醒后条件可能已被其他线程抢走（多个线程被唤醒，只有一个能抢到资源，其他必须重新等待）。

正确写法：

```python
with cond:
    while not state["ready"]:
        cond.wait()
```

用 `while` 会在醒来后重新检查条件，不满足就继续等，用 `if` 则会直接往下执行导致逻辑错误。

区别：

- `notify()`：只唤醒**一个**等待线程，适合"多个线程处理同一个资源池"的场景（谁醒谁抢）。
- `notify_all()`：唤醒**所有**等待线程，适合"状态变化，所有人条件都变了"的场景。生产环境用 `notify_all` 更安全，`notify` 只在明确知道只需唤醒一个时使用。

</details>

7. `queue.Queue` 的 `put` / `get` / `task_done` / `join` 分别做什么？为什么 `task_done` 不能漏？

<details>
<summary>参考答案</summary>

- `put(item)`：放入元素；若队列达到 `maxsize` 会阻塞，直到有空位。
- `get()`：取出元素；队列为空时阻塞，直到有元素。
- `task_done()`：声明"刚取出的那个元素处理完了"，把内部未完成任务计数减一。
- `join()`：阻塞直到队列中**所有元素都被 `task_done` 标记完成**。

`task_done` 不能漏，因为它驱动 `join()` 的完成条件。如果 `get()` 之后不调用 `task_done()`，`join()` 会永远阻塞（即使队列已经空了）；反过来多调用会抛 `ValueError: task_done() called too many times`。

典型用法：生产者 `put`，消费者 `get` 后处理完再 `task_done`，主线程 `join()` 等全部处理完毕。

</details>

8. 一个 FastAPI 服务上线后 P99 延迟从 20ms 涨到 2s，日志显示大量请求卡在同一个数据库查询上。你会怎么排查和优化？

<details>
<summary>参考答案</summary>

排查步骤：

1. **确认瓶颈类型**：CPU 使用率是否打满？如果 CPU 很高 → GIL/单线程瓶颈（典型是纯 Python 计算，或事件循环里跑了阻塞代码）；如果 CPU 不高、延迟高 → 等待 IO（数据库、外部 API）。
2. **profile 异步代码**：用 `py-spy dump --pid`，或 FastAPI 生态的 `asyncio` 慢回调日志；也可临时开启 `loop.set_debug(True)` + `slow_callback_duration`。
3. **定位阻塞点**：检查协程里是否误用了 `requests` / `time.sleep` / 同步 DB 驱动（psycopg2、pymysql），这些会阻塞整个事件循环。应换 `asyncpg` / `aiomysql` + `httpx.AsyncClient`。

优化方向：

- 数据库：**连接池**（`asyncpg.create_pool(min_size=5, max_size=20)`）、加索引、为常用查询加缓存（Redis / `functools.lru_cache`）、`asyncio.gather` 合并可并行的查询、启用慢查询日志。
- 加超时与熔断，防止慢查询堆积导致雪崩；`asyncio.wait_for` + `Semaphore` 限制下游并发。
- 多副本部署 + 负载均衡，缓解单实例压力。

</details>
