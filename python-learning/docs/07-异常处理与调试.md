# 07 · 异常处理与调试

## 学习目标

学完本节，你应该能够：

1. 熟练书写 `try / except / else / finally`，并说清每块的执行时机。
2. 知道该捕获哪些异常、哪些异常绝不能吞掉，理解"捕获具体异常"的价值。
3. 使用异常链（`raise ... from ...`）保留根本原因，用自定义异常表达业务错误。
4. 用 `assert` 表达"绝不应发生"的前置条件。
5. 背下常见内置异常的语义，遇到报错能立刻定位。
6. 用 `pdb` 单步、断点、观察变量与调用栈。
7. 配置 `logging`，正确使用日志分级与 `__name__` 约定。
8. 用 ruff / pyflakes / pylint / mypy 做静态检查，替代满屏 `print` 的调试方式。

## 一、异常的基本模型

Python 中所有异常都继承自 `BaseException`：

```
BaseException
├── KeyboardInterrupt      # Ctrl+C
├── SystemExit             # sys.exit()
├── GeneratorExit
└── Exception               # 日常业务异常，全部继承自它
    ├── ArithmeticError
    │   ├── ZeroDivisionError
    │   ├── OverflowError
    │   └── FloatingPointError
    ├── LookupError
    │   ├── IndexError
    │   └── KeyError
    ├── ValueError
    │   └── UnicodeError
    ├── TypeError
    ├── AttributeError
    ├── OSError / IOError
    │   ├── FileNotFoundError
    │   ├── PermissionError
    │   └── IsADirectoryError
    ├── NameError
    │   └── UnboundLocalError
    ├── RuntimeError
    ├── StopIteration
    ├── RecursionError
    └── ...
```

> **实践规则：只捕获 `Exception`，永远不要捕获 `BaseException`。**
> `KeyboardInterrupt` 和 `SystemExit` 属于 `BaseException`，捕获它们会让你的程序无法被 Ctrl+C 中断。

## 二、try / except / else / finally

```python
def parse_number(text):
    try:
        value = int(text)          # 可能抛 ValueError
    except ValueError:
        return None                # 已知且可恢复的错误
    else:
        print("转换成功")           # 没有异常时才执行
    finally:
        print("总是执行")           # 无论成败都执行
        # 适合放：关闭资源、清理临时状态

print(parse_number("123"))
# 预期输出:
# 转换成功
# 总是执行

print(parse_number("abc"))
# 预期输出:
# 总是执行

print(parse_number("123"))
# 预期输出:
# 转换成功
# 总是执行
```

**注意 `else` 的意义**：把"可能失败的最小代码"放在 `try`，把"成功才走的逻辑"放 `else`，可以避免把不该捕获的异常也包进来。

反例：

```python
# 不好：try 范围过大，会把 else 里的错误也当 ValueError 处理
try:
    value = int(text)
    print(10 / value)          # 这里抛 ZeroDivisionError，except ValueError 抓不到
except ValueError:
    ...
finally:
    ...
```

### 2.1 各块执行时机总结

| 情况 | try | except | else | finally |
| --- | --- | --- | --- | --- |
| 正常完成 | ✅ | ❌ | ✅ | ✅ |
| 捕获并处理 | ✅ | ✅ | ❌ | ✅ |
| 未被捕获，向上抛 | ✅ 部分 | ❌ | ❌ | ✅ |
| `return` / `break` | ✅ | ❌ | ❌ | ✅（**仍会执行**） |
| `sys.exit()` | ✅ 部分 | ❌ | ❌ | ✅ |

**陷阱：`finally` 里写 `return` 会吞掉返回值甚至异常。**

```python
def bad():
    try:
        return "正常返回"
    finally:
        return "被 finally 覆盖"   # 错误！会吞掉 try 的返回值

print(bad())     # 预期输出: 被 finally 覆盖
```

同理不要在 `finally` 里抛异常。

## 三、捕获具体异常

### 3.1 永远不要写裸 `except:`

```python
try:
    risky()
except:                      # 危险：连 Ctrl+C 都吃掉
    pass
```

改写顺序：从具体到宽泛。

```python
def load(path):
    try:
        with open(path) as f:
            return f.read()
    except FileNotFoundError:
        return ""            # 文件不存在，返回空
    except PermissionError as e:
        print(f"无权限: {e}")
        raise                  # 记录不了就往上抛，别静默吞
    except UnicodeDecodeError:
        return open(path, encoding="gbk").read()
```

### 3.2 多个异常元组

```python
try:
    f()
except (ValueError, TypeError) as e:
    print("参数有问题:", e)
```

### 3.3 `NotImplementedError` 与 `NotImplemented`

- `NotImplementedError`：**异常类**，用于"这个功能本该实现但没实现"，比如抽象方法。
- `NotImplemented`：**返回值**，用于"我不知道怎么和对方比较，请对方试试"，见 `__eq__` / `__lt__`。

### 3.4 什么时候该捕获，什么时候该抛

| 场景 | 做法 |
| --- | --- |
| 底层库不知道上层想怎么处理 | 向上抛，让调用方决定 |
| 函数边界（API / 对外接口） | 捕获并转成业务异常或返回默认值 |
| 第三方代码你无法修改 | 包一层 try，转换成自己的异常类型 |
| 循环里处理大量数据 | 跳过坏记录并记录日志，不要中断整批 |

## 四、异常链与 `raise ... from ...`

Python 3 自动维护 `__cause__`（显式）与 `__context__`（隐式）。

```python
def parse_config(text):
    import json
    return json.loads(text)          # 内部抛 JSONDecodeError


def load_config(path):
    with open(path) as f:
        return parse_config(f.read())


try:
    load_config("config.json")
except Exception as e:
    print("类型:", type(e).__name__)        # JSONDecodeError
    print("原因:", type(e.__cause__).__name__)   # None
    print("上下文:", type(e.__context__).__name__)  # FileNotFoundError
```

```python
class ConfigError(Exception):
    """配置文件无效。"""


def load_config_v2(path):
    with open(path, encoding="utf-8") as f:
        raw = f.read()
    try:
        return parse_config(raw)
    except Exception as e:
        raise ConfigError(f"配置文件 {path} 解析失败") from e   # 显式指定原因


try:
    load_config_v2("缺失.json")
except ConfigError as e:
    print(e)                      # 预期输出: 配置文件 缺失.json 解析失败
    print("根因:", type(e.__cause__).__name__)   # 预期输出: 根因: FileNotFoundError
```

用 `from e` 能把"业务上下文"和"技术根因"清晰分开，排错时价值极大。

抑制上下文噪音：

```python
try:
    ...
except Exception:
    raise ConfigError("格式不对") from None    # 不显示 __context__
```

## 五、自定义异常

```python
class AppError(Exception):
    """所有业务异常的基类。"""

class ConfigError(AppError):
    """配置相关。"""

class PaymentError(AppError):
    """支付失败。"""

    def __init__(self, message, order_id=None):
        super().__init__(message)
        self.order_id = order_id


try:
    raise PaymentError("余额不足", order_id="ORD-20240101")
except AppError as e:
    print(f"[{type(e).__name__}] {e} (order={e.order_id})")
# 预期输出: [PaymentError] 余额不足 (order=ORD-20240101)
```

**设计建议：**
- 自定义异常继承自 `Exception`（或业务基类），不要继承 `BaseException`；
- 保持简单：一般只需要一个消息属性；
- 按业务分层建基类，方便调用方一次性捕获整类。

## 六、raise 与断言

### 6.1 主动抛出

```python
def divide(a, b):
    if b == 0:
        raise ValueError("除数不能为 0")
    return a / b
```

自定义异常便于精确捕获：

```python
def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError("取款金额必须为正")
    if amount > balance:
        raise PaymentError("余额不足", order_id=None)
    return balance - amount
```

### 6.2 `assert` 断言

```python
def calc_area(w, h):
    assert w > 0 and h > 0, "宽高必须为正"      # 表达"绝不应发生"
    return w * h

print(calc_area(3, 4))      # 预期输出: 12
try:
    calc_area(-1, 4)
except AssertionError as e:
    print("断言失败:", e)    # 预期输出: 断言失败: 宽高必须为正
```

**断言的三条铁律：**

1. **不用于校验用户输入**。用户传 `-1` 是正常业务错误，应抛 `ValueError`。
2. **`python -O` 会关闭断言**，所以绝不能把安全检查写进 `assert`。
3. **不要写 `assert x is not None` 这种空断言**，它不告诉读者任何东西。

正确分工：

```python
# 用来检查内部不变量、类型前提
assert isinstance(config, dict), "config 必须是 dict"

# 用来校验外部输入
if not isinstance(raw, dict):
    raise TypeError(f"期望 dict，得到 {type(raw).__name__}")
```

## 七、常见异常速查表

| 异常 | 触发原因 | 典型排查 |
| --- | --- | --- |
| `SyntaxError` | 语法错误 | 检查缩进、括号、冒号 |
| `IndentationError` | 缩进不一致 | Tab 与空格混用，统一用 4 空格 |
| `NameError` | 使用未定义的变量 | 拼写、是否在函数内赋值后才使用 |
| `UnboundLocalError` | 局部变量在赋值前使用 | 函数内引用全局同名变量需 `global` |
| `AttributeError: 'X' object has no attribute 'y'` | 属性不存在 | 拼写、`None` 上取属性（先判空） |
| `TypeError` | 类型不匹配 | 打印 `type()`；注意 `None` 参与运算 |
| `ValueError` | 类型对但值非法 | `int("abc")`、`json.loads` 失败 |
| `KeyError` | 字典键不存在 | 用 `.get()` 或检查 `in` |
| `IndexError` | 序列越界 | 检查长度、循环边界 |
| `ZeroDivisionError` | 除以 0 | 检查分母 |
| `ModuleNotFoundError` | 模块找不到 | 检查安装、相对导入是否在包内 |
| `ImportError` | 导入过程出错 | 循环导入、版本不兼容 |
| `FileNotFoundError` | 文件不存在 | 检查路径拼写与工作目录 |
| `PermissionError` | 无权限 | 权限或文件被占用 |
| `UnicodeDecodeError` | 解码失败 | 换正确 encoding（utf-8 / gbk） |
| `IsADirectoryError` / `NotADirectoryError` | 路径类型不对 | 检查路径 |
| `RecursionError` | 递归过深 | 检查终止条件、改迭代 |
| `StopIteration` | 生成器/迭代器耗尽 | 在生成器内用 `return`，不要 raise |
| `MemoryError` | 内存耗尽 | 处理大文件用流式读写 |
| `KeyboardInterrupt` | 用户 Ctrl+C | 别捕获它 |
| `BrokenPipeError` | 对端关闭管道 | `head` 管道命令常见 |

### 7.1 读 traceback 的顺序

```
Traceback (most recent call last):
  File "app.py", line 10, in <module>          ← 文件:行号:函数
    main()
  File "app.py", line 6, in main               ← ① 从下往上找到自己写的第一行
    return int(text)
  File "app.py", line 1, in <module>           ← ② 再看它调了什么
ValueError: invalid literal for int() with base 10: 'abc'   ← ③ 最后一条是异常类型和消息
```

读法：**从最后一行读异常类型与消息，然后往上找到第一个属于你自己代码的位置。**

## 八、pdb 断点调试

### 8.1 三种启动方式

```python
# ① 在代码里写死断点（用完记得删）
def calc(x):
    breakpoint()      # Python 3.7+ 内置，等价于 import pdb; pdb.set_trace()
    return x * 2

calc(21)
```

```bash
# ② 命令行直接进入 pdb
python -m pdb myscript.py

# ③ 用 pdb 运行并在异常处自动停下（无需改代码）
python -m pdb -c continue myscript.py
# 或者从 3.2 起：
python -X dev -m pdb --post-mortem myscript.py
```

### 8.2 pdb 常用命令速查

| 命令 | 作用 |
| --- | --- |
| `n` / `next` | 执行下一行（不进函数） |
| `s` / `step` | 进入函数内部 |
| `c` / `continue` | 继续执行到下一个断点 |
| `r` / `return` | 执行到当前函数返回 |
| `l` / `list` | 显示当前位置附近源码 |
| `ll` | 显示整个函数的源码 |
| `u` / `d` | 在调用栈中上移 / 下移一层 |
| `p expr` | 打印表达式 |
| `pp expr` | 美化打印（`p` 的 pretty 版） |
| `a` | 打印当前函数的所有参数 |
| `w` | 打印当前调用栈 |
| `b file:line` / `b func` | 设置断点 |
| `tbreak` / `cl` / `cl all` | 临时断点 / 清除断点 |
| `!stmt` | 在调试器里执行 Python 语句 |
| `display` | 查看当前显示的所有变量 |
| `interact` | 进入交互模式任意求值 |
| `q` / `exit` | 退出调试器 |

完整示例：

```python
def calculate(items):
    total = 0
    for item in items:
        if item < 0:
            breakpoint()          # 在这里停住
        total += item
    return total

print(calculate([1, 2, -3]))
```

在 pdb 中：

```
(Pdb) n              # 逐步执行
(Pdb) p item        # 预期输出: -3
(Pdb) p total       # 预期输出: 3
(Pdb) pp total      # 预期输出(美化): 3
(Pdb) a             # 打印函数参数: items = [1, 2, -3]
(Pdb) l             # 显示附近源码
(Pdb) c             # 继续，输出 0
```

### 8.3 条件断点与事后调试

```python
def process(n):
    if n == 3:
        breakpoint()
    return n * n

for i in range(5):
    process(i)
```

只关心出错时的状态，用 **post-mortem**：

```bash
python -X dev script.py     # 出错后自动 dump 堆栈和局部变量
```

配合异常钩子自动进 pdb：

```python
import pdb, sys

def hook(exc_type, exc_val, exc_tb):
    pdb.post_mortem(exc_tb)

sys.excepthook = hook
```

### 8.4 IDE 断点调试更高效

VS Code / PyCharm 支持"在任意行下断点""鼠标悬停看变量""调用栈可视化""条件断点"，比 pdb 更快。但要熟悉 pdb —— 无 IDE 环境（服务器、Docker）里它救你。

## 九、logging 日志

### 9.1 为什么不用 print

| print | logging |
| --- | --- |
| 没有级别 | 五级：DEBUG/INFO/WARNING/ERROR/CRITICAL |
| 没法统一开关 | 一处配置，全局生效 |
| 没有时间戳 | 自动带 |
| 输出格式随意 | 格式化器统一 |
| 只能输出到终端 | 文件、多文件、远程收集 |
| 不会自动写到 stderr | 出错日志不易被吞 |

**结论：项目里永远不要用 `print` 记日志。** 用 `logging`。

### 9.2 基本用法

```python
import logging

# 模块内使用（不要用 basicConfig，放在应用入口配置一次）
logger = logging.getLogger(__name__)     # 命名约定：__name__

logger.debug("调试细节: %s", value)        # 惰性格式化，不浪费性能
logger.info("用户登录: user=%s", "alice")
logger.warning("磁盘使用率 %d%%", 85)
logger.error("写入失败: %s", "disk full")
logger.critical("数据库完全不可用")
```

**用 `%s` 占位而不是 f-string**：只有这条日志真正输出时才做格式化，被过滤掉的日志零开销。

### 9.3 在入口处统一配置

```python
# app.py —— 程序入口
import logging
import sys

def setup_logging(level=logging.DEBUG, logfile="app.log"):
    fmt = logging.Formatter(
        fmt="%(asctime)s [%(levelname)-8s] %(name)s:%(lineno)d - %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S",
    )

    # 控制台
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(fmt)
    handler.setLevel(level)

    # 文件
    file_handler = logging.FileHandler(logfile, encoding="utf-8")
    file_handler.setFormatter(fmt)
    file_handler.setLevel(logging.INFO)

    root = logging.getLogger()          # 配置根 logger
    root.setLevel(logging.DEBUG)
    root.addHandler(handler)
    root.addHandler(file_handler)


if __name__ == "__main__":
    setup_logging()
    logger = logging.getLogger(__name__)
    logger.info("程序启动")
    logger.warning("这是一个警告")
```

预期控制台输出：

```
2026-01-01 12:00:00 [INFO    ] __main__:6 - 程序启动
2026-01-01 12:00:00 [WARNING ] __main__:7 - 这是一个警告
```

### 9.4 `logger` 命名层级

`getLogger("a.b.c")` 时：

- `logger` 自身的级别是 **NOTSET（0）**，表示"交给父级决定"；
- 消息先过 **logger 有效级别**，通过后再被**各级 handler 的级别**过滤。

所以给模块用 `getLogger(__name__)` 就能自动继承根配置。

### 9.5 常用配置速查

```python
# 简化配置
logging.basicConfig(level=logging.INFO)

# 只在命令行切换级别
#   python app.py --log-level=DEBUG
level = getattr(logging, args.log_level.upper())
logging.basicConfig(level=level)

# 屏蔽第三方库的噪音
logging.getLogger("urllib3").setLevel(logging.WARNING)
logging.getLogger("matplotlib").setLevel(logging.ERROR)

# 写入结构化日志（便于采集）
import json
logger.info("下单成功", extra={"order_id": "A123", "amount": 99})

# 不重复添加 handler（导入多次时的经典 bug）
logger = logging.getLogger(__name__)
if not logger.handlers:
    logger.addHandler(logging.StreamHandler())
```

### 9.6 `logging.exception` 与 `exc_info`

```python
try:
    risky()
except Exception:
    logger.exception("执行失败")                  # 自动附带当前堆栈

try:
    risky()
except Exception:
    logger.error("执行失败", exc_info=True)       # 效果等价
```

## 十、warnings：不是错误，也不该忽略

`warnings` 用于"程序还能跑，但有点可疑"的提示（弃用、慢路径、参数可疑）。

```python
import warnings

# 触发弃用警告
def old_api():
    warnings.warn("old_api 已废弃，请改用 new_api", DeprecationWarning, stacklevel=2)

# 默认忽略 DeprecationWarning，主动打开
warnings.simplefilter("always", DeprecationWarning)

# 触发 UserWarning
warnings.warn("配置项 'timeout' 未显式设置，将使用默认值 30", UserWarning, stacklevel=2)
```

**重要区别：**

| | 异常 | 警告 |
| --- | --- | --- |
| 默认可见性 | 一定会显示 | 部分默认被忽略 |
| 影响控制流 | 是 | 否 |
| 用途 | 无法继续 | 仍可继续但需留意 |

`stacklevel=2` 让警告指向**调用者**而不是 `warnings.warn` 所在行，这是定位问题必需的习惯。

### 12.2 调试技巧清单

**定位类**

1. 二分法注释：用 `# print("到这里了")` 快速缩小范围，再升级为断点。
2. `traceback.print_stack()`：不确定是谁调用的函数时，打调用栈。
3. `id()` 和 `is`：怀疑变量不是你以为的那个对象时比较身份。
4. `sys.settrace`：想知道某函数被谁调用多少次。
5. `logging.exception()`：线上出问题时，异常日志比 print 有用得多。
6. `pip install icecream`：`ic(x)` 自动打印变量名与位置，比 `print("x:", x)` 省事。

**认知类**

7. 熟悉 5 个内置异常：`TypeError`（类型）、`ValueError`（值）、`KeyError`、`AttributeError`、`IndexError` —— 90% 的报错都在这五个里。
8. 报错信息从**最后一行**开始读。
9. 变量为空（`None`）是最常见的真实原因，任何 `xxx.yyy` 前先问一句"xxx 会不会是 None"。
10. 浮点数用 `==` 比较会失败，用 `math.isclose()`。
11. 可变默认参数是共享的，用 `None` 哨兵。

**预防类**

12. 提交前跑 `ruff check .`。
13. 关键路径用 `assert` 表达不变量（但不要用来校验用户输入）。
14. 危险操作前 `assert` / 显式检查，例如 `assert response.status_code == 200`。
15. 用 `mypy` 提前发现类型不匹配。

```python
from icecream import ic

def calc(a, b):
    result = ic(a + b)     # ic 会打印: ic| a: 1, b: 2, result: 3
    return result

calc(1, 2)
# 预期输出: ic| a: 1, b: 2, result: 3
```

## 本节小结

- 只捕获 `Exception`，永远不要捕获 `BaseException`（否则 Ctrl+C 失效）。
- `try` 只包可能失败的最少代码，`else` 放成功逻辑，`finally` 一定执行 —— 但**不要在 `finally` 里 return**。
- 从具体异常到宽泛异常依次捕获；处理不了就 `raise` 继续往上抛，别静默 `pass`。
- 用 `raise X from e` 建立异常链，保留"业务上下文 + 技术根因"。
- `assert` 用于内部不变量，不是用户输入校验，且会被 `python -O` 关闭。
- `pdb`：`breakpoint()` 起步，`n/s/c/u/d/p/pp/b/w/a/q` 是高频命令；无 IDE 环境靠它。
- `logging` 取代 print：`getLogger(__name__)` + 入口统一配置 + `%s` 惰性格式化 + `logger.exception` 记堆栈。
- `warnings` 管"可疑但能跑"，`assert` 管"绝不应发生"，`exception` 管"真的错了"。
- 静态检查首选 ruff（快），pylint 更全，mypy 管类型；提交前必须跑。

## 自测题

<details>
<summary>1. 为什么不应该写裸 `except:`？应该怎么写？</summary>

**答案：**
裸 `except:` 等价于 `except BaseException:`，会连 `KeyboardInterrupt`、`SystemExit`、`MemoryError` 都捕获，导致程序无法被 Ctrl+C 中断，`sys.exit()` 也失效，且会掩盖真正的错误原因。

正确做法：
```python
try:
    ...
except (ValueError, TypeError) as e:
    # 精确处理
    logger.exception("参数处理失败")
except Exception as e:
    # 兜底：记录并重新抛出或转成业务异常
    logger.exception("未知错误")
    raise
```
</details>

<details>
<summary>2. `try/except/else/finally` 中，`else` 和 `finally` 分别在什么时候执行？如果 `finally` 里写了 `return` 会怎样？</summary>

**答案：**
- `else`：仅在 `try` 没有抛异常时执行。
- `finally`：无论 `try` 是否抛异常、是否 `return`/`break`，都会执行。

如果 `finally` 里写了 `return`，它会**覆盖 `try` 中的返回值，甚至吞掉正在传播的异常**，导致 bug 极难发现：
```python
def bad():
    try:
        return "正常"
    finally:
        return "被覆盖"     # 函数永远返回 "被覆盖"
```
`finally` 里应当只做清理工作（关闭文件、释放锁），绝不 return 或抛新异常。
</details>

<details>
<summary>3. 代码在 `open("data.txt")` 处报 `FileNotFoundError`，但 `try` 里明明写了 `except Exception`。为什么有时捕获不到？</summary>

**答案：**
三种常见原因：
1. **异常不在 `try` 范围内**，比如 `open()` 写在 `try` 外面（常见于把 `with` 和业务代码分开时）。
2. **捕获顺序问题**：`except Exception` 写在前面，把 `FileNotFoundError` 抢先处理了，后面的更具体的 `except FileNotFoundError` 永远不可达。应把具体异常写在前面。
3. **异常发生在退出 `with` 块时**（如 `__exit__` 中抛错），此时已经不在 `try` 保护范围内。

另外若写的是 `except BaseException:` 之外的类型（如只捕获 `ValueError`），自然捕获不到 `FileNotFoundError`。
</details>

<details>
<summary>4. `raise ... from e` 解决了什么问题？`__cause__` 与 `__context__` 有什么区别？</summary>

**答案：**
`__context__` 是 Python 自动填的"当前正在处理的异常"（隐式上下文），`__cause__` 是程序员显式指定的根本原因。

- `raise ConfigError("解析失败") from e`：显式声明 `e`（如 `JSONDecodeError`）是根因，打印 traceback 时会显示 "The above exception was the direct cause of..."，信息最清晰。
- 不写 `from e`：Python 仍会把 `__context__` 设为 `e`，但打印为 "During handling of the above exception, another exception occurred"，容易被误读为无关异常。
- `raise X from None`：显式切断上下文，用于把底层细节完全隐藏（如向用户展示简化错误）。

价值在于把"业务语义错误"和"技术根因"分层，便于既给用户友好提示，又保留完整排错信息。
</details>

<details>
<summary>5. `assert` 和 `if ...: raise` 分别应该用在哪？`python -O` 有什么影响？</summary>

**答案：**
- `assert`：用于检查**内部不变量和开发者假设**，如"这里一定是 dict"、"这个函数返回的一定是 list"。失败意味着代码本身有 bug。
- `if ...: raise`：用于**校验外部输入**（用户传的参数、文件内容、网络返回），失败是正常的业务情况，需要友好处理。

`python -O`（或 `PYTHONOPTIMIZE=1`）会**移除所有 assert 语句**，所以绝不能把安全检查或权限校验写在 `assert` 里 —— 生产环境一开优化就失效。

```python
assert isinstance(config, dict), "内部契约被破坏"      # 可以
if age < 0: raise ValueError("年龄不能为负")            # 必须这样
```
</details>

<details>
<summary>6. 如何在代码中启动 pdb？列出 5 个最常用的命令及作用。以及如何只打印调用栈而不进入调试模式？</summary>

**答案：**
启动：直接在可疑行写 `breakpoint()`（Python 3.7+），或 `python -m pdb script.py`，或在 `except` 中用 `pdb.post_mortem()`。

常用命令：
- `n`（next）执行下一行，不进入函数
- `s`（step）进入函数内部
- `c`（continue）运行到下一个断点
- `p expr` 打印表达式值，`pp` 为美化打印
- `b file:line` 设置断点，`u` / `d` 在调用栈中上移/下移，`w` 查看调用栈

只打印调用栈：
```python
import traceback
traceback.print_stack()
```
这在"函数被意料之外的代码调用"时最有用。
</details>

<details>
<summary>7. `logging.warning("值是 %s" % x)` 和 `logging.warning("值是 %s", x)` 有什么区别？`getLogger(__name__)` 的作用是什么？</summary>

**答案：**
两者输出内容相同，但性能差别显著：
```python
logger.warning("值是 %s", x)     # 推荐：惰性格式化，级别不够被过滤时不做任何计算
logger.warning("值是 %s" % x)     # 不推荐：无论是否输出，都会先做字符串拼接
logger.warning(f"值是 {x}")       # 不推荐：f-string 在调用前就已求值，大对象转换很贵
```

`getLogger(__name__)`：`__name__` 是模块的完整路径（如 `myapp.services.order`），用它命名 logger 可以形成层级，配置根 logger 后各模块自动继承配置，也便于按模块单独调整级别和过滤。
</details>

<details>
<summary>8. 下面是这段代码的实际行为，请指出问题并给出修复方案。程序在 `logger.info(...)` 之后仍然会向控制台输出两次内容。

```python
# utils.py
import logging
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# main.py
from utils import logger
logging.basicConfig(level=logging.DEBUG)
logger.info("启动")
```

**答案：**
问题：`logging.basicConfig` 是全局一次性配置 —— 如果 root logger 已有 handler，再次调用**默认什么也不做**（`force=False`）。所以在 `main.py` 里调用的 `basicConfig(level=DEBUG)` 不会生效，实际级别仍是 INFO（或 utils 首次导入时设的值），行为混乱且难以预期。

另外，如果模块被多次 import，`logger.addHandler(...)` 会导致日志重复输出（经典 bug）。

修复：把日志配置集中在**应用入口**，其他模块只 `getLogger`：
```python
# main.py（入口）
def setup_logging():
    logging.basicConfig(
        level=logging.DEBUG,
        format="%(asctime)s [%(levelname)s] %(name)s - %(message)s",
        force=True,          # Python 3.8+，强制清空已有 handler 再配置
    )

if __name__ == "__main__":
    setup_logging()
```
```python
# utils.py（普通模块）
logger = logging.getLogger(__name__)   # 不要 basicConfig，不要 addHandler
```
</details>

<details>
<summary>9. ruff、pylint、mypy 各能发现什么类型的错误？为什么不能只靠运行测试？</summary>

**答案：**
- **ruff**（linter + formatter）：未使用的导入/变量、未定义名称、错误的 `== None`、循环里用 `except: pass`、可自动修复的现代化写法（`str | None` 替代 `Optional[str]`）。速度极快，适合每次提交前跑。
- **pylint**：更全面的代码质量检查 —— 缺失 docstring、设计问题（属性过多、参数过多）、命名规范、可能未处理的异常。可以定制规则。
- **mypy**：静态类型检查器，发现类型不匹配（给 int 传 str）、属性可能不存在、返回类型不符。

为什么不能只靠测试：测试只能覆盖**你想到的**路径，而静态检查能覆盖所有**写出来的**代码，包括从未被执行到的分支；而且静态检查在运行前完成，节省时间、也适合大项目的增量开发。
</details>
